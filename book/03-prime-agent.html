Harness Engineering · Chapter 3

3. The reference: Prime Agent

The harness every flavor in this book is measured against, and how it learns without rewriting its own code

Each harness in this book is scored against one baseline: Prime Agent. When the eval suite reports "98% overall, 100% vs prime", the second number is a ratio to this harness. The pass bar for a flavor is 80% of Prime Agent's overall pass rate. So before we look at Clojure namespaces or Forth words, we need to know the baseline.

Prime Agent also learns over time, but in a different way from the cmh flavors. Seeing that difference clearly is the main goal of this chapter.

Everything below comes from reading the source at github.com/PrimeIntellect-ai/prime-agent, HEAD ea9d9602e release: v0.10.2 (2026-10-28), without running it. Where I am guessing rather than reading, I say so.

What it is

The README calls it "Prime Agent: A Self-Improving RLM Harness", an "open-source coding and research agent for general and long-running work". Two ideas carry the design:

  • Recursive Language Model (RLM). In the README's words, it "treats context as variables (prompt-as-a-variable) and tools like recursive subagents as function calls (programmatic tool /sub-agent calling) inside a persistent REPL."
  • Continual Harness. It "stores supplemental prompts, memories, skill descriptions, and reusable subagent specifications as durable state that Prime Agent can refine through small, evidence-backed updates, local to the session by default."

Around those two ideas sits a full product: a daemon that keeps sessions alive, a TUI, agent-to-agent messaging, schedules, /goal and /autonomous modes, automatic compaction, and MCP support.

Who made it, and where it came from

Prime Intellect builds it, the company behind PRIME-RL and verifiers. The licence is MIT. A paper with the same title (arXiv 2608.23552) and a launch blog post (2026-08-05) describe it. The paper claims, among other results, an ARC-AGI-3 RHAE Best@1 rising from 30% to 95.5%. We did not reproduce any of its results. RLM comes from Alex L. Zhang (arXiv 2512.24601). Continual Harness is arXiv 2605.09998, by Seth Karten and colleagues, mostly at Princeton, and it grew out of the "Gemini Plays Pokémon" harness.

The first commit in the git history is a74c5da11 2025-08-09 Mario Zechner "Initial monorepo setup…", the start of Zechner's pi coding agent, and he is the largest contributor by far (3063 commits). AGENTS.md says "we are not a pi fork" and asks for pi names to be scrubbed from user-visible surfaces, with an exception for wire identifiers, and names like PI_CODING_AGENT_DIR survive in the code. My reading: historically it is a fork, and the project rebrands it on purpose. Version 0.9.8 was the last TypeScript release. The current 0.10.x line is a Rust rewrite, and its merge gate is parity with the old TypeScript binary.

Size and shape

The Rust host is a 10-crate workspace (a crate is Rust's unit of compilation, roughly a library). It forbids unsafe code and runs clippy pedantic with warnings as errors. Together that is about 617k lines of .rs, tests included. Next to it sits a Python package, prime-agent-runtime/, named rlm. It has about 13k lines of source and 19k lines of tests. A skills/ directory ships 13 bundled skills.

The cmh flavors in later chapters are far smaller: Prime Agent is a product, cmh a research substrate.

The process model has four layers in interactive use, and collapses to one in the mode our evals use:

Interactive: TUI ──► daemon (supervisor) ──► worker (one per session) ──► Python kernel │ └─ Rust session engine, turn loop, refine Print mode (-p, used by our evals): prime-agent -p ──► session engine in-process ──► Python kernel (no daemon; subagents run inline; exit after "RLM quiescence")

Sessions are stored as append-only JSONL files (one JSON object per line) under the agent directory.

One tool: python_repl

Most coding agents give the model a list of tools: read file, write file, run shell, search. Prime Agent gives it one. The base system prompt opens with this:

# prime-agent harness

The prime-agent harness has one tool: `python_repl`, a persistent CPython REPL. All other tools are "programmatic tools", functions inside the Python REPL called via "programmatic tool calling" (PTC). All programmatic tools are async unless described otherwise and can be run in the background. `await` works directly and globally in the REPL.
prime-agent: crates/pa-core/src/prompts/layers/core.md:1-3

A REPL (read-eval-print loop) is an interactive interpreter: you send it code, it runs it, and, when persistent, it keeps the variables for the next call. If the model loads a 50 MB log into a variable log in one call, it can filter log in the next call without the log ever entering the model's context window. This is "prompt-as-a-variable": the data the model works on lives in program variables, and only what the model chooses to print comes back as text.

The tool's schema is just {code: string}. Here is how the Rust host defines it:

    ToolDefinition {
        name: pa_types::ai::PYTHON_TOOL_NAME.to_string(),
        label: pa_types::ai::PYTHON_TOOL_NAME.to_string(),
        description: ipython_tool_description().to_string(),
        prompt_snippet:
            "python_repl - persistent Python REPL for code, state, and bash() orchestration"
                .to_string(),
        // The kernel is single-threaded; calls must not run in parallel.
        execution_mode: Some(ExecutionMode::Sequential),
        parameters: ipython_tool_schema(),
        prepare_arguments: None,
prime-agent: crates/pa-core/src/tools/ipython.rs:520-530

The Sequential line matters: there is one Python process per session, and it runs one thing at a time. The "kernel" here is that Python subprocess (python -m rlm.repl), which talks to the Rust host over a line-based JSON protocol. The cmh flavors use "kernel" for their own fixed core, so watch for the two meanings.

The host builds the kernel's virtual environment with uv and pre-imports the bundled skills. Variables are snapshotted and revived after restarts, best-effort: objects that cannot be serialized are dropped.

The README is direct about safety: "Prime Agent executes model-generated Python and project commands with your user permissions. Its worker and kernel processes improve lifecycle isolation and recovery; they are not a security sandbox."

The tools inside the REPL

The usage prompt layer sets house rules for this style, for example:

Agents do not keep the turn open by polling with `time.sleep()`, shell `sleep`, or repeated awaits of a still-running handle; they end the turn and collect the result on the done notification.
prime-agent: crates/pa-core/src/prompts/layers/usage.md:17

So bash() starts a background process and returns at once. When the command finishes after the calling python_repl block has returned, the harness sends the agent a [bash-done] notice as a new message.

Recursion: subagents as function calls

The "recursive" in RLM means a model can start another model as easily as it calls a function:

prime-agent is a recursive harness. Each session builds a tree of agents, starting at depth 0. Each agent up to a user-configured limit can launch subagents. These subagents are persistent, just like the root session. Each agent can communicate with its nuclear family: its singular parent (except for depth 0 sessions which have no parent), its siblings (other subagents under the same parent), and its children (its own subagents).
prime-agent: crates/pa-core/src/prompts/layers/core.md:29

Each child is a full session with its own kernel. await rlm.spawn(prompt, name=...) returns immediately with a handle, never with the child's answer. Answers come back only as agent_message replies or as files. /rlm-max-depth caps the depth of the tree.

depth 0 root session ── kernel │ await rlm.spawn("summarise logs", name="logs") ▼ depth 1 "logs" ── kernel ──► agent_message.send(result, receiver_role="parent") │ depth 2 … (up to /rlm-max-depth)

MCP tools are found by search, not listed

MCP (Model Context Protocol) is a standard way to plug external services into an agent as tools. Many harnesses add every MCP tool to the model's tool list, which can mean hundreds of schemas in every request. Prime Agent registers none with the model. The MCP client runs inside the Python kernel, where the model searches for a tool, reads its schema and calls it. The search is deliberately simple:

def _match_tools(generation: _Generation, query: str, limit: int) -> list[dict[str, Any]]:
    needle = query.lower()
    matches: list[dict[str, Any]] = []
    for name, tool in generation.tools.items():
        if not generation.allows(name):
            continue
        haystack = f"{name}\n{tool.get('description') or ''}".lower()
        if needle not in haystack:
            continue
        matches.append(
            {"connectionId": generation.server, "name": name, "description": tool.get("description") or ""}
        )
        if len(matches) >= limit:
            break
    return matches
prime-agent: prime-agent-runtime/src/rlm/mcp.py:820-834

It is a case-insensitive substring test on name plus description, with no embeddings or ranking, over at most 8 servers per search. Chapter 12 shows how other harnesses do "tool search".

The turn loop

Under all this sits a conventional agent loop: ask the model, run the tool calls it asked for, append the results, ask again. Prime Agent's loop is a port of the TypeScript one, and its core is short:

            let tool_calls = message
                .tool_calls()
                .into_iter()
                .cloned()
                .collect::<Vec<ToolCall>>();

            let mut tool_results: Vec<ToolResultMessage> = Vec::new();

            if !tool_calls.is_empty() {
                let executed_tool_batch =
                    execute_tool_calls(current_context, &message, config, signal, emit).await?;
                tool_results.extend(executed_tool_batch.messages);
                has_more_tool_calls = !executed_tool_batch.terminate;

                for result in &tool_results {
                    current_context
                        .messages
                        .push(AgentMessage::from(result.clone()));
                    new_messages.push(AgentMessage::from(result.clone()));
                }
            }
prime-agent: crates/pa-agent/src/agent_loop/run.rs:91-111

The loop does not know which tools exist; they arrive through a dispatcher. Its hook points (convert_to_llm before every request, should_stop_after_turn, steering polls for /goal and /autonomous) are fixed Rust code that the agent cannot replace. Between turns the engine checks the compaction threshold (95% of the context window by default), queued messages, and any refine the model asked for. Providers are keyed by API dialect (anthropic, openai-completions, google, bedrock, …), not by vendor, which matters for our evals.

How it learns: the Continual Harness

The prompt draws a clean line between the two halves of the design:

Terminology: continual harness names the persisted prompt, memory, skill, and subagent layer; RLM names the runtime, Python REPL kernel, and native call interface exposed to the model.
prime-agent: crates/pa-core/src/prompts/layers/usage.md:26

RLM is the machine. The continual harness is the data the machine learns. Here are the kinds of data:

pub const REFINEMENT_KINDS: [&str; 5] = ["prompt", "memory", "skill", "subagent", "factory"];
prime-agent: crates/pa-core/src/refinement/mod.rs:10
  • prompt: supplemental prompt notes, narrow behavioural rules.
  • memory: facts, decisions, failures, preferences.
  • skill: a description plus a pointer (reference: {"type":"python", import, callable}) to a Python function that is already installed.
  • subagent: a reusable delegation spec: purpose, instructions, when to spawn.
  • factory: a state-machine workflow of subagents (only when factory mode is on).

Where the state lives

All of it is one JSON file, harness_state.json, holding entries by kind plus a list of refinement events. There are two copies with different scopes:

ScopeFileSeen by
local (default)<session_dir>/harness/harness_state.jsonthis session only
global<agent_dir>/harness/harness_state.jsonevery future session using this agent dir

The two are merged when read. Entries are versioned, refinement_history.jsonl records every change, and snapshots support rollback.

How the state reaches the model

The base system prompt is never edited. Instead, the engine renders a short, ranked digest of the harness state and sends it as a separate user message, so the static system prompt can stay cached by the provider:

pub const HARNESS_DIGEST_PREFIX: &str = "[harness-digest]\n\nThe persistent memories produced across this session so far:\n\n<harness_state>\n";
prime-agent: crates/pa-core/src/session_engine/messages.rs:16

The digest is small on purpose. format_harness_state_for_prompt (refinement/ranking.rs:195) takes the top 3 entries of each kind, cuts each to 140 characters, and adds the last 10 refinements (refinement/mod.rs:17-19). Entries are ranked by an IDF-weighted term score against the current goal and recent messages. IDF (inverse document frequency) means rare words count for more than common ones. The digest tells the model these are "compact summaries, not full descriptions", and the model can read full entries through rlm.harness when it needs them.

Three ways the state changes

1. The agent edits it directly. From Python, the model calls functions like this one:

        self,
        title: str,
        content: str,

        id: str | None = None,

        metadata: dict[str, Any] | None = None,

prime-agent: prime-agent-runtime/src/rlm/harness.py:932-943

The call is synchronous, and the kernel writes the file under a lock. Note global_: bool = False: unless the model asks for global, the memory dies with the session.

2. Refine: a second model call reviews the trajectory. The user types /refine, or the agent calls await refine.run(). When the current turn ends, a separate LLM call runs with its own system prompt. It sees the trajectory, the current harness overview and the refinement history, and returns JSON edits. The prompt describes the job well:

This is similar in spirit to context compaction, but instead of summarizing the conversation you emit precise Create, Update, or Delete edits to reusable state. … prompt: supplemental prompt notes only. The base system prompt is immutable and MUST NOT be rewritten. … Prefer small evidence-backed edits. If prior refinements caused issues, rollback or replace the faulty editable entries. Never edit source files directly.
prime-agent: crates/pa-core/src/refinement/planner.rs:10 (excerpts from REFINEMENT_SYSTEM_PROMPT)

The output is {summary, rationale, expectedOutcome, edits:[…]}, with a budget of 32,000 output tokens. Each edit must pass validate_edit, which enforces the immutability rule in code, not only in prose:

    if kind == RefinementKind::Prompt

Skill edits must also include arguments and a Python reference, and harnessRefinements: false in settings switches the whole system off. /refine --global or refine.run(global_=True) writes the global store.

3. Auto-refine after compaction. Compaction means replacing old conversation with a summary when the context window fills up. After a successful compaction, at the next quiet turn boundary, a cheap review call (4,096 output tokens) decides whether a refine is worth running. Its prompt says to "Reject one-off noise, unsupported hypotheses, and transient tool outputs." If the reviewer approves, a normal refine runs, and its scope is hard-coded to local:

Skills as code, after the next bootstrap

New executable behaviour enters another way. The bundled skill-creator skill scaffolds a Python package under .prime/agent/skills/<name>/, and the host installs it into the kernel venv on the next bootstrap: a new session, or /reload in an interactive one. A harness skill entry only points at such a package.

Our eval runner (chapter 11) treats each harness as a command line. Prime Agent's entry:

  • -p is print mode (the in-process engine shown above); the final answer goes to stdout, which the runner saves to logs/<tag>.stdout.txt for the suite's check script to grade.
  • PRIME_AGENT_CODING_AGENT_DIR is Prime Agent's whole state root: settings, sessions, personal skills, and the global harness/harness_state.json. Pointing it at {state} gives each run a clean, private agent dir.
  • ANTHROPIC_API_KEY is a placeholder. The real key never reaches the harness; a local proxy adds it and counts tokens.
  • DO_NOT_TRACK=1 turns off telemetry delivery.

The cmh harnesses get the proxy address through ANTHROPIC_BASE_URL. Prime Agent needs it in a different place: a models.json file in its agent dir that overrides the built-in anthropic provider's endpoint. That is what models_json: true triggers:

Here base is http://127.0.0.1:{proxy_port}/t/{tag}, and the tag names the harness, suite, trial and episode, so the proxy can bill each episode separately.

State carries over between episodes

A suite is a sequence of episodes. The learning suites (l*) and reuse suites (r*) teach something in the first episode and check in later ones whether it stuck. For example, l1-house-style first asks for text_utils.py and states a project rule "for every future task": each file starts with # owner: team-orion and each function has a docstring. Episodes 2 to 4 ask for other files and do not mention the rule. The runner makes this possible by reusing one state dir for a whole suite:

def run_suite(hname, h, suite_dir, spec, trial, model, port, usage, timeout, logs_dir, fresh_state=False,
              isolate=True):
    state = pathlib.Path(tempfile.mkdtemp(prefix=f"cmh-eval-state-{hname}-"))
    rows = []
    try:
        for number, ep in enumerate(spec["episodes"], start=1):
            if fresh_state:  # control: no memory carried between episodes
                shutil.rmtree(state, ignore_errors=True)
                state.mkdir()
evals/run.py:317-325

For Prime Agent, the global harness, personal skills, settings and old sessions all survive between episodes.

My reading of the code, which I have not confirmed from logs: each -p episode is a new session, so local harness entries from episode 1 are invisible in episode 2. Transfer only works if the model writes global entries (global_=True, /refine --global) or leaves files on disk. Auto-refine is local-only and fires only after compaction, which short eval episodes rarely reach. To check, look for harness/harness_state.json in a kept state dir, or refinement_outcome rows in session JSONL.

How it differs from cmh

Both projects say "self-improving", but they mean different things.

cmh (chapter 2) lets the agent rewrite its own userspace while it runs: tools, prompt notes, and the hooks that assemble its own prompt (compose_system, select_lessons). Every change goes through propose_def: it is validated against its tests in a scratch environment, goes live as a trial, and is kept only after a few clean uses. If it fails during that soak, it is reverted automatically and the verdict is written down so the model does not retry the idea blindly.

Prime Agent learns data, not code:

The usage prompt does ask the model to check its own refinements:

they diagnose the issue, update the smallest relevant continual harness component, validate on the next action, then record the outcome.
prime-agent: crates/pa-core/src/prompts/layers/usage.md:27 (excerpt)

But that "validate" is a request to the model, not a gate in the harness. I found no code in refinement/ or session_engine/refine.rs that tests or replays a change before keeping it, though I did not search the whole 617k lines.

Prime Agent can change code informally: REPL helpers survive in the session snapshot, and with bash() it could edit any file, even its own install. None of that is gated or versioned.

Neither approach is simply better. In Prime Agent the model cannot break its own loop, because the loop is compiled Rust it cannot touch. The price is a ceiling: no amount of learning changes how its prompt is built or which tools exist. cmh removes that ceiling and pays for it with the gate machinery of chapter 2. The rest of this book asks whether that trade pays off, and how the choice of language changes it.

Key takeaways

  • Prime Agent is the eval baseline: the "vs prime" column and the 80% pass bar in every results table are measured against it.
  • It gives the model one tool, python_repl, a persistent Python REPL. Shell, edits, subagents, MCP and harness edits are all Python functions called inside it.
  • RLM is the runtime: context lives in variables, and subagents are await rlm.spawn(...) calls that form a tree of persistent sessions.
  • The Continual Harness is versioned JSON state, local by default. The agent edits it directly or through refine, a second LLM call that proposes schema-checked edits. Auto-refine runs only after compaction, and only on local state.
  • Our evals run it in print mode with a private agent dir that is kept for a whole suite, so global state can carry between episodes.
  • Its baseline numbers are strong but noisy: transfer was 94% twice and 67% once on deepseek-v4.1-flash and 50% on glm-5.3-flash, and it is roughly two to four times as fast per episode as the cmh flavors.
  • The core difference: Prime Agent learns data inside a fixed program, with no test gate. cmh lets the agent rewrite live code, including its own prompt assembly, behind a validate → trial → soak → keep/revert gate.
