Harness Engineering · Chapter 7

7. Lean 4: proofs at the gate

A harness whose agent writes code in a proof assistant, so a new tool can carry a claim about itself that the compiler has to check before the tool goes live.

Every flavor of cmh has a gate. Before new userspace code goes live, the kernel checks that it compiles and that it passes the tests the agent wrote for it. Tests are examples: they show the code is right on the inputs someone thought of. The Lean flavor adds a check of a different kind. A proposal may contain theorems, statements about the code such as "counting the words of the empty string gives zero", and each one must be proved to Lean's type checker or the proposal is rejected. A false claim fails the gate just as a failing test does.

A Lean 4 primer

Lean 4 is two things at once. It is a functional programming language that compiles to C and to native executables, with strict evaluation, a Haskell-like type system in which types can mention values, and an IO type for effects. It is also a proof assistant, a tool in which mathematicians write definitions and proofs that a small trusted checker verifies. The two are the same language. A proof is a value, and the statement it proves is that value's type.

The few pieces of syntax this chapter needs:

LeanMeaning
def f (x : Nat) : String := …A function from natural numbers to strings. : means "has type".
IO StringAn action that may do I/O (files, processes, exceptions) and produces a string. Code without IO in its type is pure.
theorem t : countWords "" = 0 := rflA claim (the type, after the colon) and its proof (after :=). rfl means "both sides compute to the same value", which the checker confirms by evaluating them.
example : 1 + 1 = 2 := rflA theorem without a name.
sorryA placeholder that "proves" anything. Lean accepts it with a warning. It exists so people can work on unfinished proofs.
axiomDeclares a fact without proof. One false axiom makes every statement provable.
namespace A … end AA scope for names, so run inside it is really A.run.
unsafe, @[implemented_by g], @[extern "c_fn"]Escape hatches. They let code skip type safety, or swap the logical definition of a function for a different implementation at run time.
#eval eRuns e while the file is being compiled.

Two more words matter. Elaboration is Lean's front end: it parses source, fills in implicit details, type-checks every declaration (including proofs), and adds the results to an environment, the table of all known declarations. The environment is an ordinary immutable value, so you can elaborate the same file against the same starting environment twice and get two independent results. Heartbeats are Lean's deterministic measure of elaboration work (a count of small memory allocations, in thousands). The maxHeartbeats option caps how long the elaborator may grind on one declaration, for example while searching for a proof.

Lean 4 is written in Lean 4. The parser, the elaborator and the environment are library code under import Lean. An executable that links that library, plus Lean's bytecode interpreter, can compile Lean source while it runs and then call what it just compiled. That is the whole trick behind this flavor.

The Lean flavor targets leanprover/lean4:v4.35.0 (pinned in lean/lean-toolchain) and uses no packages beyond Lean's own core libraries: Lean, Lean.Data.Json, Std.Time and Std.Data.HashMap. The Lake manifest lists no dependencies.

Wrap

Each version gets its own namespace, Cmh.Def.<name>.v<N>, so two versions of word_count never fight over the name run. After the agent's source, the kernel appends one line of its own: a declaration called __cmh_entry with a fixed type, defined as the agent's function. The contract table says which type each kind of definition must have:

def contract? (kind name : String) : Option Contract :=
  match kind, name with
  | "tool", _ => some {
      signature := "def run (input : Lean.Json) : IO String"
      entry := "def __cmh_entry : Lean.Json → IO String := run" }
  | "hook", "compose_system" => some {
      signature := "def composeSystem (notes lessons : List String) : String"
      entry := "def __cmh_entry : List String → List String → String := composeSystem" }
  | "hook", "select_lessons" => some {
      signature := "def selectLessons (task : String) (lessons : List (Nat × String × Int)) : List Nat"
      entry := "def __cmh_entry : String → List (Nat × String × Int) → List Nat := selectLessons" }
  | _, _ => none
lean/Cmh/Elab.lean:63-74

This one appended line is the shape check. If the agent writes def run (n : Nat) : String, the entry line fails to type-check and the proposal is rejected with the elaborator's own error message. Test 2 in the suite checks exactly that case. A tool takes JSON and returns a string in IO. The two hooks are pure functions: they cannot do I/O at all, which their types guarantee.

The base environment is built once per process, on first use, and cached in a global reference. Importing modules means reading Lean's precompiled .olean files from the toolchain directory; the kernel finds it through Lean.findSysroot (which honours LEAN_SYSROOT or asks lean --print-prefix) and falls back to the pinned toolchain under $ELAN_HOME.

Lean.Elab.process runs the same parser and elaborator the lean command uses on a file, called here as a function on a string. It returns a new environment env' and a list of messages. Because env is an immutable value, the base environment is untouched: in the module's own words, "The kernel never elaborates into a shared live environment: every version lives in its own environment value." Errors are sorted first, since they are what the model must fix. Line numbers are shifted back by one to hide the namespace line the kernel added, so "line 3" in the message means line 3 of what the agent wrote.

Evaluate

An environment holds declarations, not running code. To get something callable, the kernel asks for the value of __cmh_entry with evalConst, which runs the declaration through Lean's interpreter and returns a real closure at the requested type. The kernel packs it into a small sum type, Compiled, with one case per contract (tool, compose, select, note).

unsafe def evalEntryImpl (kind name : String) (env : Environment) (n : Name) : Except String Compiled :=
  match kind, name with
  | "tool", _ => (env.evalConst (Json → IO String) {} n (checkMeta := false)).map .tool
  | "hook", "compose_system" =>
    (env.evalConst (List String → List String → String) {} n (checkMeta := false)).map .compose
  | "hook", "select_lessons" =>
    (env.evalConst (String → List (Nat × String × Int) → List Nat) {} n (checkMeta := false)).map .select
  | _, _ => .error s!"no entry point for kind {kind}"

/-- `evalConst` at the entry's known type. Only called on declarations we generated with that type. -/
@[implemented_by evalEntryImpl]
opaque evalEntry (kind name : String) (env : Environment) (n : Name) : Except String Compiled
lean/Cmh/Elab.lean:86-97

evalConst is marked unsafe because nothing stops a caller from asking for the wrong type, which would crash. The kernel only ever asks for the type it wrote into the entry line itself, so the pairing is safe by construction. The opaque + @[implemented_by] pattern lets safe code call it: the logical definition is an opaque constant, and at run time the compiler substitutes the unsafe implementation. Note the irony. The two tokens that do this, unsafe and implemented_by, are among those the agent is forbidden to write.

Keep alive

The closures from evalConst point into the environment they came from. If env' were freed, the closure would dangle. So every successful environment is pushed onto a global array called keepAlive and never dropped ("closures produced by the interpreter refer to declarations of env'; keep it alive", Elab.lean:132). The price is that old versions stay in memory until the process exits.

Both executables are built with supportInterpreter := true, which links the interpreter into the binary:

Why theorems make a stronger gate

A test runs a function on one input and compares the output. A theorem is checked for every input its statement covers. "rev (rev s) = s for all strings s" cannot be established by any finite number of tests, but it can be proved, and once Lean accepts the proof it holds for every string. In Lean the checker that enforces the contract type also checks the proofs, so a single elaboration pass validates both the shape of the code and the claims made about it.

The seed tool word_count shows the idea at its smallest:

/-- Number of maximal runs of non-whitespace characters. -/
def countWords (s : String) : Nat :=
  (s.toList.foldl (fun (acc : Nat × Bool) c =>
    if c.isWhitespace then (acc.1, false)
    else if acc.2 then acc else (acc.1 + 1, true)) (0, false)).1

theorem countWords_empty : countWords "" = 0 := rfl

def run (input : Lean.Json) : IO String := do
  let text := (input.getObjValAs? String "text").toOption.getD ""
  pure (toString (countWords text))
lean/userspace/word_count.lean:1-11

The theorem lives in the same file as the code it talks about. If a later version kept the theorem but changed countWords so that the empty string gave 1, the theorem would no longer hold, and that version could not get through the gate at all. (It could also just drop the theorem.) To see this happen, I ran the harness with a scripted mock model that proposed a tool with a deliberately false claim, theorem rev_empty : rev "a" = "b" := rfl. The kernel's trace:

[gate] reverse_bad v1 rejected (60ms): elaboration failed: line 3:37: error: Type mismatch   rfl has type   ?m.3 = ?m.3 but is expected to have type   rev "a" = "b" …
output of .lake/build/bin/cmh --provider mock, measured 2026-11-13

The model gets back an exact location and the reason, the same as for a type error.

Be honest about how strong this is. Nothing requires a proposal to contain any theorem; the gate only insists that the theorems present are true. The seed's rfl proof is about one concrete input, so it is really a test that runs at compile time. Proofs can only talk about pure functions such as countWords, not about what run does in IO. And the proof only means what its statement says: a true but irrelevant theorem passes as easily as a useful one. The mechanism makes strong claims possible and false claims impossible; it does not make the agent write good ones.

Banning the escape hatches

A proof checker is only as honest as the axioms it is allowed to use. If the agent could write sorry or declare an axiom, every theorem would "check". If it could write unsafe, implemented_by or extern, it could make the function that runs differ from the function that was proved. If it could write #eval or initialize, arbitrary code would run during elaboration, before any test. And import would pull in modules outside the allowed two. So, before elaboration, the kernel splits the source into tokens and looks for a fixed list of words:

def bannedWords : List String :=
  ["sorry", "sorryAx", "axiom", "implemented_by", "unsafe", "extern", "#eval", "#exit",
   "import", "initialize", "builtin_initialize", "#print"]

def bannedIn (src : String) : List String :=
  let toks := src.splitToList (fun c => !(c.isAlphanum || c == '_' || c == '#'))
  bannedWords.filter (toks.contains ·)
lean/Cmh/Elab.lean:77-83
Banned tokenWhy
sorry, sorryAxProves anything; sorryAx is the axiom sorry expands to.
axiomAdds an unproved assumption.
unsafe, implemented_by, externRun code other than the code that was type-checked.

There is also a second line of defence: after elaboration, any message that mentions "sorry" fails the proposal, which catches tactics that fall back to sorry internally.

The check is lexical: it does not know about strings or comments. A tool that prints "no import needed", or a comment that says "sorry", is refused. That is crude but hard to fool, and the README states it openly ("This is a token check, so the words are also refused inside strings and comments").

The lists do not quite agree across the repo. The code bans all twelve words above. The README lists ten (it omits #exit and builtin_initialize), the rejection message names eight, and the propose_def tool description given to the model names six.

The agent loop

A task is one call to runTask:

def runTask (k : Kernel) (task : String) : IO Outcome := do
  let tid := (← k.st).tasks.size + 1
  k.emit "task_started" [("id", tid), ("task", task)]
  let active := (← k.st).activeLessons
  let ids ← k.selectLessons task (active.map fun e => (e.id, e.text, e.score))
  let selected := ids.filterMap fun i => active.find? (·.id == i)
  let c ← k.converse task (selected.map (·.text))
  -- an error in the last two tool results means the task is not trusted as a success
  let lastErr := (c.toolErrors.toList.drop (c.toolErrors.size - 2)).any id
  let success := c.kernelErr.isNone && !lastErr
  let outcome : Outcome := { success, answer := c.answer, error := c.kernelErr }
  k.emit "task_finished" [("id", tid), ("success", success), ("summary", strTake c.answer 300),
    ("error", toJson (c.kernelErr.map (strTake · 300)))]
  k.scoreLessons selected success
  k.soakNotes tid success
  k.trace s!"[task] {tid} {if success then "succeeded" else "failed"}{match c.kernelErr with | some e => s!": {strTake e 200}" | none => ""}"
  if k.cfg.reflect then k.reflect task c.msgs outcome
  return outcome
lean/Cmh/Kernel.lean:551-568

The lesson-selection hook picks which lessons go into the prompt. Then converse talks to the model. It starts with the error "turn limit (60) reached" and clears it only when the model stops cleanly. On each turn it rebuilds the system prompt and the tool list, so a tool that went live on turn 3 is offered on turn 4. If the model stops without asking for tools, the loop ends; a stop reason other than end_turn (say, max_tokens) becomes the error "stopped with max_tokens". Otherwise every requested tool runs and the results go back as the next user message.

Success is self-reported but guarded: the model must have finished with end_turn, and neither of the last two tool results may be an error. That rule has a side effect worth knowing. A rejected propose_def counts as a tool error, so a task that ends with a rejection followed by one successful call is still scored as a failure. I saw exactly this in the mock run above: the model's last three calls were an accepted proposal, a rejected one and a successful use, and the kernel printed [task] 1 failed.

The system prompt has two blocks. The first is always the base prompt from base-prompt.md (read from the repo at startup, else the embedded copy). The second is whatever the compose_system hook makes of the live notes and the selected lessons, followed by the last 20 verdicts under "Verdicts on past userspace changes". The second block is left out when it is empty.

The gate: validate, trial, soak, keep or revert

propose first runs cheap static checks: the name matches [A-Za-z][A-Za-z0-9_]* and is at most 64 characters, the kind is tool, note or hook, hooks use one of the two hook names and nothing else does, kernel tool names are off limits, and a name keeps its kind across versions. A failure here returns "rejected: …" and journals nothing. Past that point the kernel allocates a version number and journals def_proposed, so a rejected version still uses up its number.

validate then requires at least one test for tools and hooks, elaborates the source as described above, and runs each test under the timed runner. A test passes if the output contains the expect string. For select_lessons the returned id list is rendered as JSON, so a test can expect [2,1]. A failure journals def_rejected with the error (capped at 4,000 characters) and sends the same text to the model. Success journals def_trial, and the new version is live immediately:

  | .ok c =>
    k.cachePut name version c
    -- `s` is still current for `live`: proposing and validating never change it.
    -- A trial replacing another trial restores what that trial would have restored.
    let prev := match s.liveDef? name with
      | some d => if d.status == "kept" then some d.version else d.prev
      | none => none
    k.emit "def_trial" [("name", name), ("version", version), ("prev", toJson prev)]
lean/Cmh/Kernel.lean:304-311

prev is the version to fall back to. If you replace a trial with another trial, the fallback is the last kept version, never the untested trial in between.

Every use of a trial version is recorded. Kept versions are not journaled per use, since their status can no longer change:

Journal and replay

All state lives in .cmh/journal.jsonl, one JSON event per line. One pure function folds events into state, and it is used both live and at startup. The State module's doc comment puts it this way: "apply is the only function that changes state. The live process appends an event and then applies it, and startup replays the same events through the same function, so a replayed state is identical to the state of the process that wrote the journal."

  | "def_trial" =>
    (s.updDef name ver (fun d => { d with status := "trial", soakUses := 0, prev := jNat? ev "prev" })).setLive
      name (some ver)
  | "def_use" =>
    if jBool ev "ok" then
      s.updDef name ver (fun d => if d.status == "trial" then { d with soakUses := d.soakUses + 1 } else d)
    else s
  | "def_kept" => (s.updDef name ver (fun d => { d with status := "kept" })).setLive name (some ver)
  | "def_reverted" =>
    (s.updDef name ver (fun d => { d with status := "reverted", error := jStr ev "error" })).setLive name
      (jNat? ev "restored")
lean/Cmh/State.lean:116-126

The kernel's emit appends the line, flushes, and then runs apply on the in-memory state. readJournal skips a torn final line left by a crash. The cache of compiled closures is not saved; after a restart each definition is re-elaborated from its journaled source the first time it is called. SPEC would allow caching elaborated environments, but this flavor does not bother.

Verdicts are stored differently from the Rust flavor. Here they are knowledge entries, journaled as lesson_added with "kind": "verdict", and lessons and verdicts share one id counter. Test 5 checks replay by comparing a JSON snapshot of the whole state before and after reopening, and by checking that a trial's soak counter survives (version 2, trial, 1 use).

Lessons, reflection and refine

After each task, every lesson that was in the prompt gains 1 point on success and loses 1 on failure. At a score of −3 the lesson is retired and no longer selected. With reflection on, the kernel sends a compact transcript (task, assistant text, tool calls, tool results with errors marked, outcome) to the model, with only the base prompt as system and no tools, and asks for "a JSON array of 0 to 3 short, reusable lessons". The parser takes the text from the first [ to the last ], so prose around the array does not break it, and keeps at most three non-empty strings. Each goes through remember, so duplicates are dropped.

refine is an ordinary task with a fixed prompt: review the last 10 task outcomes, the verdicts and the current userspace, then "Make at most 3 changes and prefer small ones."

Hooks and seeds

A fresh state dir is seeded with three definitions, each journaled as def_proposed with origin seed followed by def_kept: the two hooks and one example tool. The manifest userspace/seeds.json gives each a description, tests and (for the tool) an input schema. The sources are read from lean/userspace/ if present and from the embedded copies otherwise.

/-- Lower-cased words of 4 or more letters. -/
def longWords (s : String) : List String :=
  (s.toLower.splitToList (fun c => !c.isAlpha)).filter (·.length ≥ 4)

/-- The 8 highest-scored lessons sharing a 4+ letter word with the task, else the top 3. -/
def selectLessons (task : String) (lessons : List (Nat × String × Int)) : List Nat :=
  let tw := longWords task
  let sorted := lessons.mergeSort (fun a b => decide (a.2.2 ≥ b.2.2))
  let matching := sorted.filter (fun l => (longWords l.2.1).any (tw.contains ·))

A hook can break the agent's own prompt, so hook calls have a fallback chain:

partial def callHook (k : Kernel) (name : String) (input : Unit → Json) (builtin : α)
    (pick : Compiled → Option (IO α)) : IO α := do
  let some d := (← k.st).liveDef? name | return builtin
  let r ← k.callLive d input s!"bad return type: not a {name} hook" pick
    (onError := fun e => k.trace s!"[hook] {name} v{d.version} error: {strTake e 200}")
  match r with
  | .ok v => return v
  | .error _ => if d.status == "trial" then k.callHook name input builtin pick else return builtin
lean/Cmh/Kernel.lean:206-213

If a trial hook fails, the failure has already reverted it, so the kernel simply calls the hook again and gets the restored version. If a kept hook fails, or no version is live, the kernel uses a built-in copy written in the kernel itself. Those copies duplicate the seeds on purpose: "seeds are elaborated in their own isolated environment, so the kernel cannot call them" as ordinary functions. selectLessons also counts a hook call as failed if it returns a lesson id that was not offered.

The hooks are pure functions, but the kernel still runs them on the timed thread by wrapping them in IO.lazyPure, so a hook that loops forever hits the same 30-second limit as a tool.

The provider: curl as the HTTP client

The kernel uses no HTTP library. The Anthropic provider shells out to curl, which the README lists as a requirement next to elan. The request body and the response go through temporary files that are removed in a finally block. The headers, including the secret, are written to curl's standard input as a config file (-K -), so the token never appears in the process's argument list, where any user on the machine could read it with ps:

private def runCurl (url bodyPath respPath : String) (config : String) : IO (UInt32 × String × String) := do
  let child ← IO.Process.spawn {
    cmd := "curl"
    args := #["-sS", "-X", "POST", url, "-K", "-", "--data-binary", s!"@{bodyPath}",
              "-o", respPath, "-w", "%{http_code}", "--max-time", "600"]
    stdin := .piped, stdout := .piped, stderr := .piped }
  let (stdin, child) ← child.takeStdin
  stdin.putStr config
  stdin.flush  -- last use: the handle is released (closed) here, so curl sees EOF
lean/Cmh/Provider.lean:53-61

The rest follows SPEC's provider rules:

  • Auth. ANTHROPIC_API_KEY sends x-api-key. Without it, CLAUDE_CODE_OAUTH_TOKEN sends a Bearer header plus the OAuth beta header, and the kernel puts the Claude Code system preamble first. With neither, the provider refuses to start.
  • Endpoint. ANTHROPIC_BASE_URL (default https://api.anthropic.com, trailing slash stripped) plus /v1/messages. Requests use max_tokens 32000 and send tools only when there are some.
  • Retries. A curl error, 429, 529 or any 5xx is retried up to 4 times, waiting 4, 8, 16 and 32 seconds. Other non-200 replies throw with the API's error object.
  • Model. --model, then CMH_MODEL, then claude-sonnet-5-5.
  • Mock. A scripted provider that returns canned content arrays in order, reports tool_use when a block asks for a tool, records every request in an in-memory list for the tests, and throws when the script runs out.

Most of the cost is paid once. The first userspace call in a process (here, the lesson-selection hook at the start of a task) imports the base environment and elaborates the seed hooks, and that brings the process from 90 MB to about 535 MB and takes most of the 0.8 seconds. Limitations

The Lean flavor's wall is partial. The ROADMAP's summary table says "partly (panic! not caught)" for "Agent code can crash the harness" and "no (thread keeps spinning)" for "Runaway loop is actually stopped".

panic! is not turned into a gate error

Lean code can call panic! (for example through an out-of-bounds a[i]!). The kernel catches IO exceptions and converts them to errors that revert a trial, but a panic is not an exception, so the gate does not see it. By default, Lean prints the panic message to stderr and carries on with the type's Inhabited default value; this is documented Lean behaviour, not anything in this repo. A tool can therefore return a wrong answer after a panic and still count as a clean use. Stack overflow and running out of memory are not caught either; they take the whole process down.

Threads cannot be killed

Each userspace call runs on its own thread under runTimed:

def runTimed (ms : Nat) (act : IO α) : IO (Except String α) := do
  let t ← IO.asTask act .dedicated
  let start ← IO.monoMsNow
  let mut delay : UInt32 := 1
  repeat
    if ← IO.hasFinished t then break
    if (← IO.monoMsNow) - start > ms then
      IO.cancel t
      return .error s!"timeout after {ms / 1000}s"
    IO.sleep delay
    delay := min 20 (delay * 2)
lean/Cmh/Elab.lean:141-151

It polls with a backoff from 1 to 20 ms. After 30 seconds it calls IO.cancel and reports a timeout, which reverts a trial. But Lean's cancellation is cooperative: it sets a flag that the task may check, and a tight loop never checks it. The comment says so: "On timeout the thread cannot be killed (Lean tasks are cooperative); it is abandoned." The abandoned thread keeps burning a CPU core until the process exits. partial def, which allows non-terminating functions, is not on the banned list, so writing such a loop is easy. To keep abandoned threads from blocking shutdown, Main exits the hard way:

/-- Exit through `IO.Process.exit` so a userspace call abandoned after a timeout (Lean threads
cannot be killed) does not keep the process alive at shutdown. -/
def main (args : List String) : IO UInt32 := do
  let code ← Cmh.cliMain args
  (← IO.getStdout).flush
  (← IO.getStderr).flush
  IO.Process.exit code.toUInt8
lean/Main.lean:3-9

Elaboration itself does not run under the timer. It is bounded by the 200,000-heartbeat limit instead, which caps proof search and other elaborator work.

Other gaps

  • IO is open. A tool's run is in IO, and Init includes file and process functions such as IO.FS and IO.Process.spawn. Banning unsafe and import limits the language, not what a tool can do to the machine. And bash, as in every flavor, can edit anything, including the kernel source and the journal.
  • No accumulation. Every proposal is elaborated against the same base environment, "so a macro defined in one tool is not visible to the next". A helper function cannot be shared between tools; each must carry its own copy. The ROADMAP proposes chaining environments so kept definitions form a prelude. Its experiment 10 goes further: an "accumulating Lean prelude with proofs", where new versions must "prove equivalence or a stated property against the previous one".
  • No scratchpad. To try out a piece of Lean, the agent has to propose a definition. The ROADMAP suggests a tool that would "elaborate in a scratch environment and #eval".
  • Memory only grows. Every elaborated environment stays in keepAlive for the life of the process.
  • Small differences from SPEC and from Rust: static-check rejections and superseded trials leave no journal event, base-prompt.md is not write-protected, and timestamps have one-second precision.

Key takeaways

  • Lean 4's compiler is a library, so the harness elaborates new source with Lean.Elab.process into a fresh environment value and turns it into a callable closure with evalConst, all inside one process.
  • A kernel-written entry line with a fixed type checks that a proposal has the right shape; one namespace and one environment per version keep versions apart.
  • Every theorem and example in a proposal must check, so a tool can carry machine-checked claims about itself and false claims cannot go live. Nothing forces the agent to write useful claims.
  • Twelve banned tokens (sorry, axiom, unsafe, import and the rest) keep the proofs meaningful, at the cost of a lexical check that also refuses them in strings and comments.
  • The gate is fast (tens of milliseconds per small proposal once warm), but the process needs about half a gigabyte after the first elaboration and a 232 MB binary.
  • The wall is partial: panic! is not turned into a gate error, and a runaway call is abandoned on a thread that cannot be killed.
