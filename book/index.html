Harness Engineering

Building agents that rewrite themselves: one design, seven flavors, and what the evals said

A coding agent is a language model plus a harness: the program around the model that sends it a prompt, gives it tools such as bash and read_file, runs the tools it asks for, and feeds the results back. Most harnesses are fixed. The people who wrote them decide which tools exist and how the prompt is built, and the agent works inside that frame.

This book is about harnesses where the agent can change the frame. The project behind it is called cmh, short for "continual, self-modifying harness". Its roadmap states the goal in one sentence:

"a substrate the agent can program itself on, which never crashes from the agent's code, answers every mistake with precise feedback, enforces clear rules, and keeps only the changes that make the agent better."

ROADMAP.md:8-11

In practice that means the agent can write new tools for itself, add notes to its own prompt, and replace the small functions that assemble that prompt, all while it is working on a task. It cannot simply overwrite itself, though. Every change goes through a gate: it is tested in a scratch copy first, then goes live as a trial, and is kept only if its next few uses succeed. A change that fails is reverted, and the reason is written down so the agent does not try the same bad idea again. Lessons the agent learns are scored by whether the tasks that used them succeeded, and they carry over to the next run.

The design is written down once, in SPEC.md, and then built again and again in different languages. Each build is called a flavor. The repository has seven flavors and one prototype: Clojure, Racket, Rust, Lean 4, a small Forth running inside WebAssembly, a version where the entire harness runs inside WebAssembly and can rewrite its own kernel, and Roc on a Zig host. All of them share the same command line, so one eval runner can drive every one of them, and all of them except Roc have recorded eval results against a published self-improving harness, Prime Agent from Prime Intellect.

Why build the same thing seven times? Because the hard parts of a self-modifying harness are not in the agent loop. They are in questions the language answers for you, or does not: can new code be loaded into a running program? Can a bad definition crash the host? Can an infinite loop be stopped? Can the error that comes back say precisely what went wrong? Each language gives a different answer, and comparing them is the most direct way to see which answers matter.

The short version of the results. Every flavor in the committed results files (Clojure, Racket, Rust, Lean, Forth) met the project's pass bar (80% of Prime Agent's score). In a later isolated, one-trial run on the reuse suites, Prime Agent and Racket scored 32/32, while Lean (24/32), Forth (25/32) and WASM (25/32) fell below the bar. Two of Forth's failures were caused by the orb pausing, and excusing them lifts Forth over the bar; Lean and WASM stay below it, because their paused episodes passed. The ROADMAP's reading is that most of the score came from the shared design (lessons, reflection after each task, the gate), not from the agents rewriting themselves: across about 60 episodes per flavor, agents proposed only 5 to 78 changes, and almost every task could be solved with bash alone. Chapter 11 goes through the numbers, including how noisy they are.

Who this book is for

You are a programmer who knows at least one mainstream language, say Python, JavaScript, Java or Go. You have probably used a coding agent, and you may have wondered how one could be made to improve itself without breaking. You do not need to know Lisp, Lean, Forth, WebAssembly, Roc or Zig. Each idea from those worlds is explained in plain words the first time it comes up: what eval is, what "late binding" means, what a sandbox evaluator does, what a theorem prover checks, what WebAssembly "fuel" is, why a pure language cannot read a file by itself.

You also do not need to have followed the project. The book reconstructs it from the repository: the spec, the code, the eval results and the git history. Every code excerpt is copied from the repository and labelled with its file and line numbers, so you can check it. Every number (test counts, line counts, eval scores) comes from the code or from the committed results.

How to read it

  • Read chapters 1 and 2 first. Chapter 1 explains the goal and why the choice of language matters. Chapter 2 explains the shared design in SPEC.md: the kernel, userspace and knowledge rings, the gate, lessons, the journal. Every later chapter assumes it.
  • Chapter 3 is the yardstick. Prime Agent is the harness every flavor was compared with. It takes a different route (one persistent Python REPL as the model's main tool) and is worth knowing before the flavors.
  • Chapters 4 to 10 can be read in any order. Each covers one flavor: how agent code is loaded, what wall keeps it from hurting the harness, how the gate works in that language, what its tests check, and where it falls short. They are roughly in the order they were built, and the safety wall ranges from no sandbox at all (Clojure) to the whole harness inside WebAssembly (chapter 9).
  • Chapter 11 is the evidence. If you only care whether this works, read it after chapter 2.
  • Chapters 12 and 13 step back. Chapter 12 looks at other self-modifying harnesses and at "code mode" and tool search in other agents. Chapter 13 compares the flavors side by side and lists what is still open.

Code blocks are short excerpts, not complete files. Boxes like the one above are asides; amber boxes are caveats you should not skip.

The documents drift. SPEC.md says "four implementations" and the top-level README says "five", because both were written before the later flavors existed and were never renumbered. The repository has seven flavors plus a prototype. Where a document and the code disagree, this book follows the code.

  10. The whole harness in WebAssembly: the agent rewrites its own kernel The agent loop, gate and journal run as a sandboxed component under a thin host, and propose_kernel lets the agent replace the kernel itself behind the same gate.
  11. Roc on Zig: pure code and requests as data A pure, typed language where tools cannot do I/O; they return requests the host checks. Every call runs in a forked compiler session. Includes the roc-proto prototype.
  12. Measuring it: the eval suite and the results The coding, learning and reuse suites, the logging proxy, per-episode isolation, and what the runs against Prime Agent did and did not show.
  13. Other self-modifying harnesses we studied A survey of other projects that let agents change themselves, and how code mode and tool search work in OpenCode, Codex, Pi, Hermes, MiMo, Deep Agents and Grok Build.

For comparison, the eval suite in evals/ (a Python runner, a logging proxy, suites and checkers) is 2,396 lines in 76 files. Every cmh flavor runs from the same command line, cmh [--state DIR] … run "TASK", and is wired into the evals through one entry in evals/harnesses.json.

Line counts were taken with git ls-files <dir> | xargs wc -l at commit 7c715d6, leaving out Cargo.lock and lake-manifest.json. They measure how much each flavor needed in total, not how much of it is kernel logic: the Forth and WASM numbers include a whole Forth VM, and the Roc number includes the host's glue to an embedded compiler.

Key takeaways

  • cmh is one design, written down in SPEC.md, for a coding agent that rewrites its own tools, prompt notes and prompt-building hooks while it runs, and keeps a change only after it passes validation, a trial and a soak.
  • The design was built as seven flavors plus a prototype, so that the language's answers to loading, isolation and error reporting could be compared directly.
  • The safety wall ranges from none (Clojure) to the whole harness inside WebAssembly, where the agent can even replace its own kernel behind the same gate.
  • The flavors kept up with Prime Agent in the committed runs, but by the ROADMAP's reading most of the gain came from lessons, reflection and the gate rather than from self-modification, and the results are noisy. Chapter 11 shows the numbers and their limits.
