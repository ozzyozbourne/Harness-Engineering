Harness Engineering · Chapter 11

11. Measuring it: the eval suite and the results

How one Python script runs every harness on the same tasks with the same model, what it measured, and what it could not

Passing its own unit tests says nothing about whether an agent running on a harness solves real tasks, or whether its memory and self-modification help. To measure that against Prime Agent, the reference, the project has an eval suite: evals/run.py (504 lines), a list of harnesses in evals/harnesses.json, and 19 task suites under evals/suites/.

The short version: the results are useful but noisy. They come from one model and few trials, and the largest run was distorted by the machine pausing.

What an eval is here

A suite is a directory with a suite.json that names a track and a list of episodes. An episode is one task: a prompt, optionally a fixture directory and a setup script that create the input files, and a check script that decides pass or fail.

A suite is a directory under evals/suites/ with suite.json:
  {"track": "coding" | "learning" | "reuse",
   "episodes": [{"prompt": str, "fixture": dir?, "setup": file?, "check": file,
                 "transfer": bool?}]}
Episodes of one suite run in order, each in a fresh working directory and a fresh
process, sharing one harness state directory. A check script runs afterwards with
cwd = the working directory: `python3 check.py <suite_dir> <answer_file>`; exit 0
means pass. Fixtures, setup and checks are hidden from the agent: each harness run is
isolated (see ISOLATE_SH) with a private /tmp and evals/, .git and the key hidden.
evals/run.py:4-12

The important part is the shared state directory, where every harness keeps its tools, notes, lessons and journal (chapter 2). That state is the agent's memory: anything learned in episode 1 can only reach episode 4 through it, and it lasts exactly one suite run. Episodes marked transfer: true depend on something taught earlier; they are the ones that test learning.

The logging proxy

To give every harness the same model, key and token accounting, the runner starts a small HTTP proxy on localhost. Each harness is told that the Anthropic API lives at http://127.0.0.1:<port>/t/<tag>/v1/messages, where the tag is harness.suite.tTRIAL.eEPISODE. The proxy strips the tag, forwards the request upstream, and adds the response's token usage to that tag.

    def upstream_headers(incoming, tag):
        # Every harness authenticates to the proxy with a placeholder API key; the proxy
        # swaps in the real upstream key, so no harness ever sees it.
        headers = {k: v for k, v in incoming.items() if k.lower() not in DROP_REQUEST_HEADERS}
        headers["x-api-key"] = key
        session = str(uuid.uuid5(uuid.NAMESPACE_URL, "cmh-eval/" + tag))
        for name, template in up["extra_headers"].items():
            headers[name] = template.format(key=key, session=session)
        return headers
evals/run.py:123-131

Harnesses get ANTHROPIC_API_KEY=via-eval-proxy, a placeholder; the real key comes from an environment variable or a file under ~/.config/cmh/, and credential variables are removed from the harness's environment. The proxy drops the client's auth headers and anthropic-beta flags, relays streaming responses (server-sent events, SSE) chunk by chunk, and sums usage from a JSON body or the SSE message_start and message_delta events. Any non-200 response is counted as an error and written to proxy-errors.jsonl.

There are two upstreams that speak the Anthropic Messages API: opencode (OpenCode Go, the default, which rejects requests without a session id, hence the uuid5 line) and openrouter. Every result in this chapter used DeepSeek V4.1 Flash through OpenCode Go, except one run of GLM 5.3 Flash through OpenRouter.

harnesses.json has eight entries: prime, clojure, rust, racket, lean, forth, wasm and roc. Prime Agent runs as prime-agent -p --provider anthropic --model {model} {prompt} with its agent directory set to the state dir, where a generated models.json points it at the proxy. Every cmh flavor runs as <binary> --state {state} --model {model} run {prompt} with ANTHROPIC_BASE_URL set to the proxy.

The watchdog

Each episode runs in its own process session (a Unix group of processes that can be signalled together). The runner polls every 2 seconds and kills the whole session with SIGKILL if the episode runs too long or uses too much memory.

def run_watched(cmd, cwd, env, out_f, err_f, timeout):
    """Run cmd in its own session; return its exit code, "timeout" or "memory-limit"."""
    t0 = time.time()
    p = subprocess.Popen(cmd, cwd=cwd, env=env, stdout=out_f, stderr=err_f,
                         stdin=subprocess.DEVNULL, start_new_session=True)
    rc = None
    while rc is None:
        try:
            # Poll rather than wait out the whole timeout, so memory is checked every 2 s.
            rc = p.wait(timeout=2)
        except subprocess.TimeoutExpired:
            if time.time() - t0 > timeout:
                rc = "timeout"
            elif session_rss_mb(p.pid) > EPISODE_MEM_MB:
                rc = "memory-limit"
            if rc is not None:
                kill_session(p)
evals/run.py:230-246

The default timeout is 900 seconds. The memory limit, EPISODE_MEM_MB = 2500, is the summed resident memory (RSS) of every process in the session, read from /proc. It was added after one episode during the Forth run started a 5.5 GB process and got the whole eval service killed by the kernel's out-of-memory killer (commit 61fd5c3). Two caveats: the clock is time.time(), wall time, so time the machine spends suspended counts against the episode; and a process that calls setsid to start its own session escapes both the memory accounting and the kill.

Episodes, resume and the report

Each episode gets a work dir (cmh-eval-work-*) and a private /tmp (cmh-eval-tmp-*). The setup script runs with EVAL_EPISODE=n, and the harness's stdout, logs/<tag>.stdout.txt, is the "answer file". The row records passed, the tail of the check output, exit, wall-clock seconds, usage and isolated. --fresh-state wipes the state directory before every episode: the control condition, the same tasks with no memory.

A suite run's rows are appended to results.jsonl only once all its episodes finish, so a stopped run keeps nothing from unfinished suites. That detail decides the fate of the fresh-state control later in this chapter.

The runner can resume: it keeps the first recorded row per (harness, suite, trial, episode) and reruns any suite not fully recorded. It refuses an output directory that already contains summary.md, because a supervised service reruns its command when it exits. There is a latent bug: a partly recorded suite reruns from episode 1 while its old rows stay in the in-memory list, so the summary would double-count them. The only run known to have resumed is the committed Forth-with-scratchpad run (below), made with an earlier runner; the later runs did not resume, and none of their results files has duplicate keys.

The report (summarize) gives, per harness: the overall pass rate, the coding-track rate, the rate on learning-track transfer episodes, the median seconds per episode, total tokens, API errors, the ratio to Prime and whether the harness meets the bar of 80% of Prime's overall rate. Total tokens are input + output + cache read + cache write, unweighted, so cheap cache reads dominate. On a reuse-only run the "Coding" and "Learning transfer" columns read 0% (an empty selection rates as 0.0); those zeros are left out below. For the learning and reuse tracks it also gives a learning curve: pass rate, mean tokens, seconds and requests by episode position. A position mixes unrelated tasks, so one bad suite can dominate a point.

Why the reuse track was added

The committed results (next section) showed that the first 15 suites barely separate the harnesses: coding is near 100% everywhere, and a learning suite with one fact to remember can be passed by writing one note. The ROADMAP's first eval gap is that they "do not reward self-modification": a harness that can write itself a tool should win when the same hard work recurs, and nothing in c01-l3 recurs.

The reuse track (commit d6bce9c) was built for that: eight episodes per suite that lean on something expensive to rebuild. The commit says every episode fails on the untouched work dir and passes with the reference solution, reference/solve.py, which the runner never copies.

Per-episode isolation and the leaks it closed

The first reuse pilots ran without isolation, and the agents looked around. The isolation commit (526881e) says: "Agents could read other episodes' scratch files in the shared /tmp, the prompts, fixtures and checkers under evals/ (and in git history), and the upstream key in ~/.config/cmh, which inflated the fresh-state controls." The pilot logs contain every case:

  • Reading the suite source. In the fresh-state pilot, Prime on r1 episode 8 wrote that it "found the layout documented in the local eval suite at .../evals/suites/r1-qlog/setup.py and implemented it", and passed. Forth on r1 episode 3 ran sed inside evals/suites/r1-qlog and passed; on episode 5 it ran the generator itself with EVAL_EPISODE=5 and passed.
  • Reading other episodes' /tmp. In the memory pilot, Forth on r1 episode 7 listed /tmp, read other agents' scratch files (/tmp/qlog_parse.py, /tmp/d.md) and grepped another run's harness journal. It passed.
  • Looking for the key and other answers. Forth on r3 episode 6 (fresh) listed ~/.config/cmh, ran a find /, then looped over other episodes' answer.txt files. It failed anyway.

The effect on the control was visible in the scores. Without memory, "same QLOG format as before" should be close to unsolvable, yet r1 scored 6/8 for both Prime and Forth in fresh-state mode.

How isolation works

Linux lets an unprivileged process create a user namespace, in which it appears to be root, and a mount namespace, a private copy of the filesystem layout that it can rearrange without affecting anyone else. The runner wraps each harness command in both.

HIDDEN_PATHS = [ROOT, REPO / ".git", pathlib.Path.home() / ".config" / "cmh"]
ISOLATE_SH = r"""
set -e
priv=$1 work=$2 state=$3 nhide=$4; shift 4
mount --bind "$work" "$priv/${work##*/}"
mount --bind "$state" "$priv/${state##*/}"
mount --rbind "$priv" /tmp
while [ "$nhide" -gt 0 ]; do mount -t tmpfs -o size=1m,mode=755 tmpfs "$1"; shift; nhide=$((nhide - 1)); done
cd "$work"
exec unshare --map-user="$UID_OUT" --map-group="$GID_OUT" "$@"
"""
evals/run.py:259-269

The episode's work and state dirs are bind-mounted (made visible at a second path) inside a private directory, which is then mounted over /tmp, so /tmp holds only this episode's two directories. An empty 1 MB in-memory filesystem (tmpfs) then covers each hidden path: evals/, the repository's .git (so git show cannot recover the suites) and ~/.config/cmh. A nested user namespace maps back to the real user id, so harnesses that start their own sandboxes still work. The outer call is unshare -r -m; --no-isolate turns it off.

Isolation is partial. The network is shared, so the agent can reach the internet and the proxy port. $HOME and the rest of the repository stay visible, including other harnesses' source, SPEC.md and ROADMAP.md. Setup and check scripts run outside the namespace. In the isolated runs, agents that looked in /tmp saw only their own directories, and no isolated log references evals/suites.

Why episodes failed

r2, the house rules. Episode 4 failed the same way for Rust, Lean, Forth and WASM: rows in input order (P-7012 first where P-1202 was expected). They had forgotten rules 4-6, given one episode earlier: a genuine memory failure. Later, Lean, WASM and Forth got episode 5's changes (integer cents, upper-case header) right but still wrote rows that should have been left out, or misordered them. Rust applied episode 5's change in episodes 5 and 6, then fell back to currency units and lowercase headers in episodes 7 and 8. WASM (episode 3) and Forth (6 and 8) also hit the 40-turn limit.

r3, the corrections. Lean failed episodes 4-6 by not applying the −1.5 h-sensor offset, the same mistake Prime and Forth made in the pilot, and got the resend rule wrong in episode 7. Clojure's episode 6 wrote the template word into the data (h005 MIN -12.6), a formatting slip. WASM's episode 4 produced no answer after the turn limit. Clojure's episode 4 and Rust's episode 3 timed out with no answer; both overlapped the first pause.

r4, the vault. Rust's episode 1 never created the vault's state file, so it never used the CLI. Rust's episode 2 and Clojure's episodes 2 and 4 left cursors open. Forth's episodes 7 and 8 timed out during pauses.

Episodes that ran into the 40-turn limit (41 requests; Lean's limit is 60, so its 42- and 44-request episodes are not hits): WASM 5, Forth 4, Clojure 2, Racket 2, Rust 0. Several still passed.

No isolated fresh-state control

The plan was to follow the memory matrix with the same matrix under --fresh-state. It started at 02:48:37 with Prime, Clojure and Rust on r1. The orb paused at 02:49:56, and all three first episodes were reported after about 1490 s: Clojure PASS (6 requests), Prime PASS (12), Rust FAIL (6). Episode 2 logs were created at 03:13:28, and then the run was stopped. Since rows are written per finished suite, its results.jsonl is empty.

So there is no isolated fresh-state control. The only memory-against-no-memory comparison is the non-isolated pilot, with its leaky control. The ROADMAP's "No control run yet" is half stale: a control ran, but not the one that would count.

A roc-only memory run on r1 (started 01:23:57) logged six finished episodes, 3 passes, with e4-e6 each spanning a pause (chapter 10). It was stopped too, and its results.jsonl is empty, so Roc has no recorded result.

What the results say, honestly

  1. The 15 original suites do not separate the harnesses. Coding is 92-100% everywhere. On transfer, the cmh flavors beat Prime clearly only on GLM (83% against 50%), and Prime's own DeepSeek transfer score moved from 94% to 67% between two identical setups.
  2. Memory matters a great deal on the reuse track. In the unisolated pilot it took Prime from 41% to 91% and Forth from 41% to 78%, against a leaky control. It has not been measured under isolation.
  3. In the isolated matrix, the reference harness won. Prime and Racket passed 32/32, and Prime was cheapest and fastest. Lean, Forth and WASM spent the most tokens and lost the most passes, half or more of them on r2. r1, the parser suite, was 8/8 for everyone.
  4. The evals do not yet show self-modification paying off. Prime, which does not rewrite its own kernel, scored 32/32 with the fewest tokens on the track built to reward self-modification. The ROADMAP's first gap is still open.
  5. The matrix is one trial, and pauses distort it. One model, no confidence intervals, and pauses behind every timeout and 4 of the 32 failures. A one- or two-episode difference between harnesses is within the noise of Prime's own 94%/67% swing, and timing should not be compared across harnesses for this run.

The fixes follow from the failures: rerun the matrix and an isolated --fresh-state control with three or more trials; use a pause-aware timeout or keep the orb awake; make the usage counter keep errors that arrive late; and weight cache-read tokens separately from fresh input.

Key takeaways

  • run.py runs every harness through one logging proxy, so model, key and token accounting are identical; a watchdog kills episodes at 900 s or 2,500 MB.
  • Memory is the state directory shared by one suite's episodes; --fresh-state wipes it to make a control.
  • The reuse track (r1-r4) was added because the original suites could not tell the harnesses apart or reward self-modification.
  • Unisolated agents read the eval's own source and other episodes' /tmp; per-episode user and mount namespaces now hide evals/, .git, the key and other episodes.
  • Isolated with memory, one trial: Prime and Racket 32/32, Clojure 28, Rust 26, Forth 25, WASM 25, Lean 24; Prime cheapest and fastest. Treat these as indications.
  • Orb pauses, inferred from gaps in a memory log, line up with all 9 timeouts and 4 failures, skewed wall times and hid 3 API errors.
  • There is no isolated fresh-state control and no Roc result; every conclusion rests on one trial and one model.
