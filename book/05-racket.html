Harness Engineering · Chapter 5

5. Racket: sandboxed evaluators

The same design as the Clojure flavor, but every piece of agent-written code runs inside a walled-off evaluator with its own time and memory budget.

The Racket flavor of cmh implements the same SPEC.md as the Clojure flavor in the previous chapter. It has the same kernel tools, the same gate, the same journal and the same eight required tests. If you read chapter 4, most of this chapter will feel familiar: both flavors follow one spec, so most of what differs comes from the language.

One thing changes a lot. In Clojure, code the agent writes is loaded into the same JVM as the kernel, with full access to everything. In Racket it is loaded into a sandboxed evaluator, a small separate world that cannot read files, open sockets or start programs, and that is stopped when it runs too long or uses too much memory. Racket ships this in its standard library. This chapter explains how cmh uses it, walks through the kernel file by file, and ends with an honest list of what the wall still misses.

A tiny Racket primer

Racket is a Lisp, like Clojure. Programs are written as nested lists in parentheses, and the first element of a list is the thing being called. (+ 1 2) calls + with 1 and 2. A few forms appear in every excerpt in this chapter:

  • (define x 5) names a value; (define (f a b) body) defines a function f with two parameters. The last expression in the body is the return value; there is no return keyword.
  • (λ (x) ...) (also spelled lambda) is an anonymous function.
  • (cond [test1 result1] [test2 result2] [else ...]) is an if/else-if chain. Square brackets are just parentheses with a different look.
  • #t and #f are true and false. Only #f counts as false, so functions often return #f for "nothing" and a value otherwise.
  • 'foo is a symbol, a bare name used as data. (quote (+ 1 2)), written '(+ 1 2), is the list of three items, not the number 3. This is what "code is data" means: a program is a list, and a list can be built, stored and evaluated later.
  • `(f ,x) is a quasiquote: a template list where ,x plugs in the value of x. cmh uses it to build function calls as data.
  • (hasheq 'a 1 'b 2) builds a hash table with symbol keys. The json library turns JSON objects into exactly these tables; Racket calls parsed JSON values jsexprs. JSON null becomes the symbol 'null.
  • (values a b) returns two results at once, and (define-values (a b) ...) receives them. Many kernel functions return (values ok? message).
  • (with-handlers ([pred handler]) body) is try/catch: if body raises something that pred accepts, handler runs instead.
  • (parameterize ([p v]) body) sets a parameter (a dynamically scoped setting) for the duration of body.
  • Names ending in !, like emit!, mutate something by convention. Names ending in ? return a boolean.

Every kernel file starts with #lang racket/base, which picks the small core language.

How code becomes live: racket/sandbox

Racket's runtime has several features that most languages keep out of user reach. A namespace is a table of names that eval can run code against. A custodian owns resources such as threads, files and memory, and can shut all of them down at once. A security guard is consulted on every file, network and process operation and can refuse it. The racket/sandbox library packages these into one call, make-evaluator, which returns an evaluator: a function you hand code to (as a string or as a list), and which runs that code in a fresh namespace, in its own thread, under its own custodian and security guard, with time and memory limits. The kernel can therefore treat every definition the agent proposes as untrusted code without writing any isolation of its own.

Creating and loading an evaluator

(define (new-evaluator)
  (parameterize ([sandbox-output #f]
                 [sandbox-error-output #f]
                 [sandbox-input #f]
                 [sandbox-eval-limits (list (sandbox-time-limit) (sandbox-memory-mb))]
                 [sandbox-memory-limit (* 2 (sandbox-memory-mb))])
    (make-evaluator 'racket/base)))

(define (destroy-evaluator ev) (kill-evaluator ev))

;; Evaluate all top-level forms of the source. A leading #lang line is dropped.
(define (load-source! ev source)
  (ev (regexp-replace #px"^\\s*#lang[^\n]*" source ""))
  (void))
racket/kernel/sandbox.rkt:12-25

The two parameters at the top of the file set the limits: 10 seconds and 128 MB for each evaluation (sandbox-eval-limits), and 256 MB for everything the evaluator holds (sandbox-memory-limit). Going over a per-evaluation limit only fails that evaluation; going over the 256 MB cap terminates the evaluator. Standard output, error output and input are switched off, so agent code cannot print into the kernel's trace or wait on the terminal. The language inside is racket/base; agent code may require other standard libraries such as racket/string or json.

Loading a definition is one call: pass the whole source string to the evaluator, which runs every top-level form in it. A leading #lang line is stripped, because an evaluator takes forms, not a module file.

Entry points and the boundary

Each kind of definition has one function it must define. A tool must define (run input). The select_lessons hook must define (select-lessons task lessons), and the compose_system hook must define (compose-system notes lessons). The kernel describes each with a small struct:

(struct entry (symbol arity signature args check))

(define tool-entry
  (entry 'run 1 "(define (run input) ...)"
         (λ (input) (list input))
         check-string))
racket/kernel/sandbox.rkt:43-48

Before a definition goes live, check-entry! asks the evaluator for the value of that symbol and checks that it is a procedure accepting the right number of arguments (procedure-arity-includes?). Then, to call it, the kernel never takes the procedure out of the sandbox. It builds the call as a list and evaluates the list inside:

;; Call the entry point inside the evaluator (time and memory limits apply)
;; and check the shape of the result. Arguments cross as quoted data.
(define (invoke-entry ev kind name input)
  (define e (entry-for kind name))
  (define sym (entry-symbol e))
  (define call `(,sym ,@(for/list ([a (in-list ((entry-args e) input))]) `(quote ,a))))
  ((entry-check e) sym (ev call)))
racket/kernel/sandbox.rkt:71-77

For a word_count call with input {"text": "a b"}, the list built is roughly (run (quote #hasheq((text . "a b")))). Two things follow from doing it this way. First, the time and memory limits apply to every single call, not only to loading. Second, only plain data crosses the boundary in either direction. Inputs go in as quoted JSON-shaped values. Results come back through a check: tools and compose_system must return a string (copied into an immutable string), and select_lessons must return a list of exact integers. A wrong type is an error, and errors count against a trial like any other.

kernel (host Racket) sandboxed evaluator ───────────────────── ────────────────────────────── input jsexpr ──► `(run (quote ,input)) ─► eval in fresh namespace security guard: no files, net, exec limits: 10 s, 128 MB per eval check-string ◄── result value ◄────────── (run input) returns "3" (string? else error) 256 MB cap for the evaluator

What the wall blocks

The research for this book configured a throwaway evaluator exactly like new-evaluator and tried to escape. Every one of these was stopped:

Attempt inside the sandboxResult
Read /etc/hostnamedenied: "`read' access denied"
Write a file under /tmpdenied
directory-list "/"denied
tcp-connectdenied: "network access denied"
(system "echo hi")denied: "`execute' access denied for /bin/sh"
An infinite loop (let l () (l))stopped: "with-limit: out of time"
(make-vector 100000000 0)"out of memory"
(exit 3)only the evaluator ends ("evaluator: terminated (exited)"); the host keeps running

This is the main reason the project's ROADMAP.md marks Racket as the only Lisp flavor where agent code cannot crash the harness and where a runaway loop is actually stopped. In the Clojure flavor a timed-out call is abandoned but its thread keeps burning CPU; here the evaluator's custodian kills it.

The environment-variable caveat. The security guard checks file, network and process operations. It does not hide environment variables: by default each evaluator gets a copy of the host's, so (getenv "HOME") returns a string inside the sandbox, and the same call can read ANTHROPIC_API_KEY or CLAUDE_CODE_OAUTH_TOKEN if they are set. Agent code cannot send them over the network, but a userspace tool could return one as its result, putting it in the model's context. In the eval suite the key is a placeholder ("ANTHROPIC_API_KEY": "via-eval-proxy" in evals/harnesses.json; the runner strips real keys and a proxy adds them), so the risk is only in direct runs. The fix, not yet in the code, is one more binding in new-evaluator: [sandbox-make-environment-variables (λ () (make-environment-variables))] gives the evaluator an empty set (tried while writing this chapter: getenv then returns #f).

Unlike Clojure, where state is one immutable map in an atom, Racket's kernel state is a set of mutable structs and hash tables: a kernel struct holding defs, lessons, verdicts, tasks and the evaluator cache, and a def struct per name with its versions, its live version, its kept version and its soak count. Mutation is fine here because one function owns it, as the journal section shows.

Late binding and the evaluator cache

"Late binding" means the kernel looks a definition up by name at the moment it is called, rather than holding on to a reference. That is what makes a new version take effect on the very next call.

;; Late binding: look the name up in the registry on every call.
;; Returns (values ok? result-or-error-text).
(define (use-def! k name input)
  (define d (get-def k name))
  (define rec (live-record d))
  (cond
    [(not rec) (values #f (format "no live definition named ~a" name))]
    [else
     (define v (hash-ref rec 'version))
     (define-values (ok? out)
       (with-handlers ([always? (λ (e) (values #f (error-text e)))])
         (let ([ev (live-evaluator k d rec)])
           (values #t (invoke-entry ev (def-kind d) name input)))))
     (record-use! k name v ok? (if ok? #f out) input)
     (values ok? out)]))
racket/kernel/core.rkt:290-304

Making a new evaluator and loading source into it on every call would be slow, so the kernel keeps one evaluator per name, tagged with the version it was loaded from:

(define (live-evaluator k d rec)
  (define cache (kernel-evcache k))
  (define name (def-name d))
  (define version (hash-ref rec 'version))
  (define cached (hash-ref cache name #f))
  (cond
    [(and cached (eqv? (car cached) version)) (cdr cached)]
    [else
     (when cached
       (destroy-evaluator (cdr cached))
       (hash-remove! cache name))
     (define ev (new-evaluator))
     (with-handlers ([always? (λ (e) (destroy-evaluator ev) (raise e))])
       (load-source! ev (hash-ref rec 'source)))
     (hash-set! cache name (cons version ev))
     ev]))
racket/kernel/core.rkt:273-288

If the live version is the cached one, reuse it. Otherwise kill the stale evaluator and load a fresh one from the live record's source. A new trial or a revert changes which version is live, so the next call sees the change. The cache is only a cache: nothing about it is journaled, and after a restart it fills up again on first use.

The racket/README.md says evaluators are "cached by (name . version)". The code caches by name and stores a (version . evaluator) pair, as the comment at core.rkt:27-28 correctly says. The difference matters: only one evaluator per name stays alive, not one per version.

Every kernel with-handlers uses the predicate always?, defined in util.rkt as "anything that is not a break". It catches every raised value, including odd ones like (raise 'nope) that are not exception structs (test 5 uses exactly that), and still lets Ctrl-C through.

The agent loop

agent.rkt runs one task in four steps: build the prompt, run model and tool turns, score the outcome, reflect.

Prompt. The task gets an integer id (one more than the number of finished tasks) and a task_started event. The kernel then calls the select_lessons hook to pick lessons, collects the notes still on trial, and builds the system prompt with system-blocks: the immutable base prompt first, then the supplemental prompt from compose_system if it is not empty. This happens once per task and the result is reused on every turn. Clojure rebuilds it on every model request, so a compose_system redefined mid-task takes effect on the next request there, and on the next task here.

Turns. run-turns is a loop that calls the provider with the system prompt, the current tool list and the messages so far. The tool list is rebuilt on every request from the kernel tools plus the live userspace tools, so a tool proposed in turn 3 can be called in turn 4. If the reply contains tool_use blocks, each is run, the results are appended as a user message, and the loop continues. If it contains none, the loop ends. A provider error ends the loop as a kernel error, and so does passing 40 turns ("turn limit 40 reached").

Outcome. Success has a precise meaning:

  ;; A task succeeds when the model ended its turn normally, nothing broke in
  ;; the kernel, and its last two tool calls (if any) did not fail.
  (define success?
    (and (equal? stop "end_turn") (not kernel-error)
         (not (ormap values (take-up-to tool-errors 2)))))
  ;; Notes soak over tasks: a failed task counts as an error for trial notes.
  (for ([n trial-notes])
    (record-use! k (car n) (cdr n) success? (if success? #f (or kernel-error "task failed")) #f))
  (score-lessons! k lesson-ids success?)
  (emit! k (hasheq 'type "task_finished" 'task_id task-id 'task task 'success success?
                   'summary (one-line (or kernel-error answer) 300)))
  (trace! "[task] #~a ~a" task-id (if success? "succeeded" "failed"))
  (when (kernel-reflect? k) (reflect! k task success? (reverse transcript)))
  (values success? (if (and kernel-error (string=? answer "")) (string-append "error: " kernel-error) answer)))
racket/kernel/agent.rkt:34-47

Notes are plain text, so they have no "call" that can fail. Instead each note on trial counts one use per task, and the use is clean only if the task succeeded. The lessons that were put in the prompt are scored up or down by the same outcome. Then the kernel reflects (below).

The bash tool is worth a look, because a shell command that hangs is a classic way for an agent to get stuck:

(define (run-bash command timeout-s)
  (define-values (sp out in _err)
    (parameterize ([subprocess-group-enabled #t])
      (subprocess #f #f 'stdout "/bin/sh" "-c" command)))
  (close-output-port in)
  (define buf (open-output-bytes))
  (define reader (thread (λ () (copy-port out buf))))
  (define finished? (sync/timeout timeout-s sp))
  (unless finished? (subprocess-kill sp #t))
  (sync/timeout 5 reader)
  (kill-thread reader)
  (close-input-port out)
  (define text (truncate-text (bytes->string/utf-8 (get-output-bytes buf) #\uFFFD) 20480))
  (if finished?
      (values #f (format "~a\n[exit code ~a]" text (subprocess-status sp)))
      (values #t (format "~a\n[timed out after ~a s]" text timeout-s))))

The propose_def tool description is also where the model learns the Racket contracts. The gate: validate, trial, soak, keep or revert

A proposal goes through four stages.

propose_def ─► static checks ──fail──► "invalid proposal: ..." (not journaled) │ ok ▼ def_proposed vN ─► validate in scratch evaluator ──fail──► def_rejected │ ok ▼ (old trial? revert it: "superseded by vN") │ ▼ def_trial: vN is live now │ each use ─► def_use ────┼──── error ──► def_reverted (kept version live again) │ N clean uses (default 3) ▼ def_kept

Static checks. The name must match ^[A-Za-z0-9_-]{1,64}$ and not be a kernel tool; the kind must be tool, note or hook; a hook must be one of the two hook names; a name cannot change kind; tests must be a list of {"input": {...}, "expect": "..."}. A proposal that fails here is answered with "invalid proposal: ..." and is not written to the journal.

Validation in scratch. The kernel builds a brand-new evaluator, loads the source, checks the entry point, runs every test, and kills the evaluator whatever happens. Live evaluators are never touched.

       (when (null? tests) (error "tools and hooks need at least one test"))
       (define ev (new-evaluator))
       (dynamic-wind
        void
        (λ ()
          (with-handlers ([always? (λ (e) (error (string-append "source failed to evaluate: "
                                                                (error-text e))))])
            (load-source! ev source))
          (check-entry! ev kind name)
          (for ([t (in-list tests)] [i (in-naturals 1)])
            (define expect (hash-ref t 'expect))
            (define out
              (with-handlers ([always? (λ (e) (error (format "test ~a raised: ~a" i (error-text e))))])
                (test-output ev kind name (hash-ref t 'input))))
            (unless (string-contains? out expect)
              (error (format "test ~a failed: expected ~s as a substring of the output ~s"
                             i expect (truncate-text out 500)))))
          #f)
        (λ () (destroy-evaluator ev)))])))
racket/kernel/core.rkt:155-173

dynamic-wind takes three functions: before, body, after. The "after" runs even if the body raises, which is how the scratch evaluator is always destroyed. A test passes when its expect string is a substring of the output; for select_lessons the list of ids is JSON-encoded first, so a test expects something like "[2,1]". Error messages are written for the model to read: "source must define (define (run input) ...)", "test 2 failed: expected ... as a substring of the output ...".

Trial and soak. If validation passes, any version still on trial is reverted first ("superseded by vN before its soak finished"), then the new version goes live as a trial. Every use emits a def_use event; while the version is on trial, an error reverts it and enough clean uses keep it:

(define (gate-decision! d v status err #:live live)
  (set-status! d v status err)
  (set-def-live! d live)
  (set-def-soak-count! d 0))

;; True while version v is live and still on trial (its uses count toward soak).
(define (in-soak? d v)
  (and (eqv? (def-live d) v) (equal? (live-status d) "trial")))

;; Count one use; during soak an error reverts and enough clean uses keep.
(define (record-use! k name version ok? err input)
  (emit! k (hasheq 'type "def_use" 'name name 'version version 'ok ok? 'error (if ok? 'null err)))
  (define d (get-def k name))
  (when (and d (in-soak? d version))
    (cond [(not ok?) (revert! k d err input)]
          [(>= (def-soak-count d) (kernel-soak k)) (keep! k d)])))
racket/kernel/core.rkt:263-269

The soak count itself is incremented in apply-event! when a clean def_use arrives, so the same rule runs live and during replay. Once a version is kept, its errors are still returned to the model, but they no longer revert anything (test 4 checks this).

Verdicts. Every keep and revert produces a one-line verdict, such as def word_count v2 ("test version") reverted: ... on input {...} or "... kept after 3 clean uses". Racket stores the verdict as a field on the def_kept and def_reverted events and keeps a list of strings in memory. The last 30 are always appended to the supplemental prompt under "## Verdicts on earlier userspace changes", bypassing both hooks, so the agent always sees what happened to its earlier changes. Seeds have no verdicts. SPEC.md asks that keeps and reverts write knowledge entries; Racket meets the intent with the event field rather than a lesson_added event as Clojure does.

Rollback. rollback_def NAME V takes the source of an older version and proposes it again as a new version number, so it goes through the gate like anything else. Racket refuses to roll back to a version that was never live ("was never live (rejected)").

The journal and replay

Every state change is an event, appended as one JSON line to <state>/journal.jsonl:

(define (journal-append! path ev)
  (define full (hash-set ev 'ts (now-iso)))
  ;; Closing the port (when call-with-output-file returns) flushes the line.
  (call-with-output-file path #:exists 'append
    (λ (o) (write-json full o) (newline o)))
  full)
racket/kernel/journal.rkt:6-11

The trick that makes persistence reliable is that live changes and replay go through the same function. emit! is a single line:

(define (emit! k ev)
  (apply-event! k (journal-append! (kernel-journal k) ev)))
racket/kernel/core.rkt:42-43

When a process starts, open-kernel reads the journal and feeds every event to the same apply-event!. If the journal is empty, it installs the seeds. A final line torn by a crash mid-write is skipped with a [journal] skipping unreadable line trace. apply-event! handles the def_* events, lesson_added, lesson_scored, lesson_retired and task_finished; task_started and unknown types are ignored. Evaluators are not state, so replay creates none; they are rebuilt lazily on first call. Test 5 opens a second kernel on the same directory and checks that definitions, knowledge and an unfinished soak all carry over.

Lessons, reflection and refine

Lessons are short strings with integer ids, a score and a retired flag. remember adds one with source "model"; reflection adds them with source "reflection". Text is whitespace-normalised, and a lesson that matches an existing one ignoring case is rejected as a duplicate.

(define (score-lessons! k ids success?)
  (for ([id (in-list ids)])
    (define l (hash-ref (kernel-lessons k) id #f))
    (when (and l (not (lesson-retired? l)))
      (define delta (if success? 1 -1))
      (define new (+ (lesson-score l) delta))
      (emit! k (hasheq 'type "lesson_scored" 'id id 'delta delta 'score new))
      (when (<= new -3)
        (emit! k (hasheq 'type "lesson_retired" 'id id))
        (trace! "[lesson] #~a retired at score ~a" id new)))))
racket/kernel/core.rkt:400-409

A lesson that was in the prompt gains a point when the task succeeds and loses one when it fails; at −3 it is retired and never shown again. Test 7 walks a lesson from 1 down to −3.

Reflection runs after every task (unless --no-reflect). The kernel sends the model a fixed prompt asking for "only a JSON array of 0 to 3 short, reusable lessons", the outcome, and the transcript truncated to 12,000 characters, with the base prompt as the only system block and no tools. It pulls the first [...] out of the reply, parses it, takes up to three strings and adds them. Racket puts no length cap on each lesson (Clojure caps at 400 characters).

Refine (cmh refine or /refine) runs a normal task whose text is built by refine-task-text: an instruction to make at most three small improvements, then the last 10 tasks, all verdicts, and the list of userspace definitions. Unlike Clojure, the refine prompt does not include the lessons.

Hooks

Two parts of prompt assembly are userspace hooks the agent can rewrite: select_lessons picks which lessons go into the prompt, and compose_system turns notes and lessons into the supplemental prompt. The kernel always puts the base prompt first, so no hook can remove it (test 6). Both go through one helper:

;; Call a hook by name; on failure (which reverts a trial) try the now-live
;; version once more, then fall back to the kernel's built-in behavior.
(define (hook-call k name input fallback)
  (let loop ([tries 0])
    (cond
      [(and (< tries 2) (live-record (get-def k name)))
       (define-values (ok? out) (use-def! k name input))
       (cond [ok? out]
             [else (trace! "[hook] ~a failed: ~a" name (one-line out 160))
                   (loop (add1 tries))])]
      [else (fallback)])))
racket/kernel/core.rkt:328-338

If a hook on trial fails, that failure reverts it, so the second try runs the restored kept version. If that also fails, or nothing is live, the kernel uses its built-in behavior: the first three active lessons, or a default-compose that deliberately copies the seed (the seed runs sandboxed, so the two cannot share code). A hook failure is traced but is not a kernel error, so it does not fail the task; in Clojure it does. The select_lessons hook is called even when there are no lessons. Whatever ids it returns are filtered to active lessons and de-duplicated.

Seeds

A new state dir starts with three version-1 definitions described in seed/seeds.json. Their sources are .rktl files: bare forms with no #lang line, exactly what an evaluator expects. The smallest is the tool:

;; Userspace tool. Contract: (define (run input) ...) where input is a
;; jsexpr hasheq with symbol keys; returns a string.
(define (run input)
  (define text (hash-ref input 'text ""))
  (number->string (length (regexp-match* #px"\\S+" text))))
racket/seed/word_count.rktl:1-5

The select_lessons seed (21 lines) returns the 8 highest-scored lessons that share a word of four or more letters with the task, or else the top 3 by score. The compose_system seed (17 lines) puts notes under "## Notes", separated by blank lines, and lessons as bullets under "## Lessons". Both are written with only racket/base primitives, including a hand-rolled first-n and a join-notes loop.

Unlike Clojure, the Racket kernel runs each seed through validate before installing it, and refuses to start if one fails. The events are marked "seed": true and the seeds go straight to kept.

The provider

A provider is a struct holding one function, (system tools messages) → response. There are two.

The mock provider plays a JSON script: an array of assistant content arrays, one per request. It records every request it receives, so tests can check exactly what the model would have seen, and fails with "script exhausted at request N" if the kernel asks for more than the script holds. All 12 tests run offline against it.

The Anthropic provider uses net/http-client from the standard library over https:// (with certificate checks) or plain http://, so a local logging proxy works through ANTHROPIC_BASE_URL. It authenticates with ANTHROPIC_API_KEY or else CLAUDE_CODE_OAUTH_TOKEN (a bearer token, the OAuth beta header, and the Claude Code identity as the first system block). Each request sends max_tokens 32,000 and omits tools when the list is empty. A request runs in its own thread with a 600-second timeout. Retries look like this:

     (let loop ([attempt 1])
       (define (retry!) (sleep (expt 2 attempt)) (loop (add1 attempt)))
       (define retries-left? (< attempt max-attempts))
       (define (retryable-network-error? e)
         (and retries-left? (exn:fail? e) (not (exn:fail:user? e))))
       ;; code is #f when the request failed with a retryable network error.
       (define-values (code resp)
         (with-handlers ([retryable-network-error?
                          (λ (e) (trace! "[provider] network error (attempt ~a): ~a" attempt (exn-message e))
                            (values #f #f))])
           (http-post url headers data 600)))
       (cond
         [(not code) (retry!)]
         [(= code 200) (bytes->jsexpr resp)]
         [(and (memv code retryable) retries-left?)
          (trace! "[provider] HTTP ~a, retrying" code)
          (retry!)]
         [else (error 'anthropic "HTTP ~a: ~a" code (one-line (bytes->string/utf-8 resp #\?) 600))])))

Statuses 408, 429, 500, 502, 503, 504 and 529, and network errors, are retried up to three times, waiting 2, 4 and 8 seconds. The model comes from --model, then CMH_MODEL, then the default claude-sonnet-5-5.

The command line

    (cond

The flags are --state DIR (default .cmh), --provider anthropic|mock, --script FILE, --model M, --soak N (clean uses before keep, default 3) and --no-reflect, parsed by the standard racket/cmdline. run prints only the final answer to stdout and exits 0 on success, 1 on failure; usage errors exit 2. The trace goes to stderr, one line per event, at most 400 characters. A mock run from the research looked like this:

[assistant] I'll make a tool.
[tool] propose_def reverse -> trial v1
[tool] reverse {"text":"hello"} -> olleh
[task] #1 succeeded
[reflect] lesson #1 Write a small tool for repeated string transforms.

The REPL (cmh repl) prints a cmh> prompt on stdout and accepts tasks plus /defs, /knowledge, /show NAME [V], /rollback NAME V, /refine and /quit. bin/cmh is a four-line shell script that runs racket main.rkt.

Building and testing

The flavor needs Racket 9 CS (checked with v9.3) and nothing outside the standard distribution.

raco make racket/main.rkt            # compile once for fast startup
racket/bin/cmh run "TASK"            # or: racket racket/main.rkt run "TASK"
raco test racket/

raco test racket/ reports 12 tests passed. Run uncompiled in a fresh copy, it took between about 16 and 23 seconds across runs during the research and while writing this chapter. The 12 cases are:

  1. Late binding: a new word_count version is used on the next call.
  2. Gate rejection: an evaluation failure and a test failure leave the live version unchanged.
  3. Soak revert: an error during soak reverts to the kept version, with a verdict.
  4. Soak keep: after enough clean uses the version is kept.
  5. Persistence: a fresh kernel replays the same state.
  6. Hook redefinition changes the system prompt; the base prompt stays first.
  7. Lesson scoring: +1 on success, −1 on failure, retired at −3.
  8. End-to-end mock run: propose a tool and call it within one task.
  9. Anthropic wire format: OAuth headers and system blocks, API key, base URL.
  10. Anthropic over a plain http:// base URL, against a real TCP listener on 127.0.0.1.
  11. write_file refuses the state dir and kernel source.
  12. The kernel tool names in core.rkt match the specs in tools.rkt.

rackunit counts test cases, not individual checks, so "12" here is not comparable with Clojure's "10 tests, 66 assertions". A macro, with-state, gives each test a temporary directory and silences the trace.

Eval results

Chapter 11 covers the eval suite. In short, from ROADMAP.md: Racket scored 102% of the reference Prime Agent on DeepSeek V4.1 Flash, the same as Clojure and Rust, and 118% on GLM 5.3 Flash, the highest of the four flavors run there (Clojure 116%; Forth was not run). Treat these as noisy. The roadmap itself says most of the score comes from the shared design (lessons, reflection, the gate), not from self-modification: across about 60 episodes per flavor, the agents proposed only 5 to 78 changes. On the later reuse matrix (four eight-episode suites, one trial each, DeepSeek V4.1 Flash), Racket and Prime both passed 32/32, the best of the seven harnesses in that run, though Racket used 1.8 times Prime's tokens (8.2 M against 4.5 M) and its median episode took 98.1 s against 33.1 s (evals/results/matrix-memory/summary.md). The sandbox makes Racket safer; the evals do not show it making Racket smarter.

Limitations

  • Environment variables leak into the sandbox, as described above. Userspace can read API keys and return them to the model.
  • bash is unrestricted. The sandbox walls off userspace code, but the agent can still run any shell command, including one that edits kernel/ or the journal. write_file's refusals do not apply to bash. This is true of every flavor.
  • A dead evaluator stays cached. If a kept version calls exit or hits the 256 MB cap, its evaluator is terminated, but the cache still holds it. A small script run while writing this chapter showed every later call failing with "evaluator: terminated (exited)" while the version stays kept, until the live version changes or the process restarts. A trial would simply be reverted.
  • No scratchpad. To try a snippet, the agent must propose a whole definition with tests. The roadmap proposes an eval tool backed by a throwaway evaluator, and says Forth's scratchpad (forth_eval) cut that flavor's rejected proposals from 69 to 0.
  • Thin feedback, narrow scope. Errors are raw exception text, the gate only runs the agent's own tests, and a trial is kept for three error-free uses, not for helping. Only tools, notes and two hooks can change.
  • Small deviations from SPEC: verdicts are event fields, not knowledge entries, and statically invalid proposals are not journaled. Other differences (prompt built once per task, no lessons in the refine prompt) are allowed by SPEC but differ from Clojure, and the README describes the evaluator cache key incorrectly.

Racket costs about 150 more kernel lines and a slower test suite, and buys a real wall with almost no code of its own: the whole sandbox layer is 82 lines because the language runtime does the hard part. Clojure is quicker and its state handling is purer, but any code the agent writes can take the process down. The lesson for harness designers is that "can the language run untrusted code safely, out of the box?" is one of the first questions to ask. Of the first four flavors, Racket was the only one that could answer yes. Chapters 8 and 9 get the same guarantee another way, by moving userspace, and later the whole harness, into WebAssembly.

Key takeaways

  • Racket's racket/sandbox gives each definition its own evaluator with a security guard, a custodian and time and memory limits, all from the standard library.
  • The kernel calls userspace by building the call as a quoted list and evaluating it inside the sandbox, so limits apply to every call and only checked plain data crosses the boundary.
  • Late binding is one cached evaluator per name, replaced when the live version changes and rebuilt lazily after a restart.
  • File reads and writes, network, subprocesses, runaway loops, memory bombs and exit are all contained. Environment variables are not, and bash is not sandboxed at all.
  • All 12 tests pass offline. Eval scores match or slightly beat Clojure, but the evals are noisy and do not yet reward self-modification.
