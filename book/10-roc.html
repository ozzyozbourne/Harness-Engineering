Harness Engineering · Chapter 10

10. Roc on Zig: pure code and requests as data

A language with no eval and no I/O becomes a live userspace: a Zig host compiles every call on its own, runs it in a child process it can kill, and does the I/O the code asks for.

Every flavor so far picked a language that already likes being changed while it runs. This chapter goes the other way on purpose. Roc is a pure, statically typed, ahead-of-time compiled language. It has no eval, and Roc code cannot read a file. The question was whether the shared design from Chapter 2 still works when the language does nothing to help.

It does, by embedding the compiler in the host, rebuilding a small program for every call, and turning every side effect into a value the host inspects before acting. The work came in two commits 74 minutes apart: a 471-line prototype in roc-proto/ late on 2026-11-12, then the full flavor in roc/ just after midnight (UTC) on 2026-11-13. The flavor has 19 files and 4,185 lines, 3,146 of them in ten Zig files.

Two primers

Roc in a few paragraphs

Roc is a functional language in the ML family. Values are immutable (a local can be declared mutable with var), most functions are pure, and the compiler infers and checks types before anything runs. A Roc program has two halves. The app is the Roc code you write. The platform is a host program, usually written in Zig, Rust or C, plus a Roc API that says what the app may ask it to do. Only the platform touches the outside world. In a normal Roc program, functions that have effects end in !, and they are provided by the platform (they are "hosted"). This split is general Roc background, not from this repository.

The Roc used here is the new compiler, a rewrite in Zig. The project pins one commit, roc-lang/roc a5c6d8b, because the language is still moving. Its syntax differs from older Roc that a model may remember from training, and the cheat sheet the host sends to the model opens by saying so:

# Roc reference (this compiler: roc-lang/roc a5c6d8b)

Your userspace is written in current Roc. It differs from older Roc you may
remember: there is no `when`/`is` (use `match`) and no `\x ->` (use `|x|`).
Calls use parentheses and commas, `f(a, b)`, and `Num.to_str` is gone (use
`x.to_str()`). Every example below is checked against the compiler. Try any
snippet with `roc_eval` before you propose it.
roc/host/roc_reference.md:1-7

Here is what a complete userspace tool looks like. It is the seed tool that every fresh state starts with:

# Seed tool: counts whitespace-separated words in `text`.
# Tools are called as NAME(input_json, results) and return a Str or a request.
WordCountInput : { text : Str }

word_count : Str, List(Str) -> Str
word_count = |input, _results| {
    parsed : Try(WordCountInput, _)
    parsed = Json.parse(input)
    match parsed {
        Ok(args) => {
            spaced = args.text.replace_each("\n", " ").replace_each("\t", " ").replace_each("\r", " ")
            Str.split_on(spaced, " ").keep_if(|w| !Str.is_empty(w)).len().to_str()
        }
        Err(_) => "error: expected {\"text\": string}"
    }
}
roc/seed/word_count.roc:1-16

WordCountInput is a record type, and the line under it is a type annotation: two arguments, a string result. |input, _results| { ... } is a lambda whose block ends with its value. Try is Roc's result type (Ok or Err), and match picks a branch by pattern.

Zig in a few paragraphs

Zig is a systems language in the same space as C: explicit allocators, error unions (!T is "a T or an error", and try passes the error up), and comptime code that runs at compile time. It calls C directly, so the host can use std.c.fork() and std.c.kill() with no wrapper. Its build script is itself Zig, build.zig.

The Roc compiler is written in Zig, so a Zig host can import its modules as source and link them into one binary, with no C API to wrap. The flavor needs Zig 0.17.1.

The framing: nvim and Lua, but Roc has no eval

The prototype's README states the goal in one line: a host that "lets Roc definitions be replaced while it runs, the way nvim reloads Lua" (roc-proto/README.md:3-5). Neovim is a small C core with a Lua scripting layer that users reload while the editor runs, the same shape as the kernel/userspace split from Chapter 2. Zig plays the C core and Roc plays Lua.

The analogy breaks in one place. Lua has load, which turns a string into a function. Roc has nothing like it: all Roc code is parsed, type-checked and lowered before it runs, so the language cannot change itself.

A host can, though. The one part of the Roc compiler that takes source text while it runs and returns a value is the REPL core, src/cli/ReplSession.zig in the Roc checkout. The host links it in as a library: Roc never gets an eval, but the host has a compiler it can call.

nvim + Lua cmh (Roc flavor) ---------- ---------------- C core (editor) Zig host (kernel: loop, gate, journal) | | | load(string) -> function | embedded Roc compiler (ReplSession) v v Lua plugins (userspace) Roc tools and hooks (userspace) can call vim.api.* directly cannot call anything: they return requests, and the host performs them

A REPL session keeps its definitions as source text. To evaluate an expression it pastes them together with a main wrapping the expression, compiles the module, and computes the value at compile time. A redefinition replaces the old snippet, after a snapshot; if the re-check fails, the snapshot is restored. That gives hot reload with rollback. Because everything is recompiled from source, an older caller sees the newest version of what it calls: late binding.

The prototype: hot reload in 296 lines

roc-proto/host.zig (296 lines) reads a scenario file of steps separated by ---. Each step is a Roc statement: a definition or an expression. The host passes it to the session and prints what happened. Here is the middle of the main scenario:

# hot reload: greet v2
greet = |name| Str.concat("Howdy, ", name)
---
# the old caller now uses the new greet (late binding)
shout("Roc")
---
# bad reload: breaks the contract (returns a number)
greet = |name| 42
---
# bad reload: syntax error
greet = |name| Str.concat("Hi", name
---
# both rejected, so v2 is still live
shout("Roc")
roc-proto/scenario.txt:11-24

Earlier steps defined greet v1 (with the type Str -> Str) and a caller, shout = |name| Str.concat(greet(name), "!"), which is never defined again. After the reload, shout uses v2. The bad reloads are a type error (greet must return a Str, not 42) and a parse error. The session rejects both, restores its snapshot, and v2 stays live. The host counts versions on its own and prints a line like [host] `greet` v2 is live when a definition is accepted (roc-proto/host.zig:138-142).

The scenario also shows where the prototype stops. A reload of greet = |name| crash "greet is broken" type-checks, so it is accepted, and the crash shows up only on the next call: checking types alone cannot catch code that is well typed and wrong. The scenario ends by reloading the v2 source by hand as a rollback (scenario.txt:26-34).

The two unknowns

Hot reload was the easy part. Two harder questions decided whether a full harness was possible, and a second scenario, work/unknowns.txt, tests them.

Unknown 2: can the host survive a hang? Roc code is pure, but pure code can still loop forever. The REPL evaluates at compile time, so a definition whose value never finishes hangs the compiler, inside the host:

# unknown 2: a definition whose evaluation never ends
spin : U64 -> U64
spin = |n| spin(n + 1)
stuck = spin(0)
roc-proto/work/unknowns.txt:5-8

The fix is a process boundary. With --timeout-ms N, the prototype runs each statement in a fork()ed child, a copy of the host process that shares its memory copy-on-write. The parent waits on a pipe, and kills the child when the deadline passes:

        if (timed_out) {
            _ = std.c.kill(pid, .KILL);
            _ = std.c.waitpid(pid, null, 0);
            return .{ .killed = try std.fmt.allocPrint(self.arena, "no result after {d} ms; child killed", .{limit}) };
        }
roc-proto/host.zig:115-119

The scenario then calls greet("Roc") and greet("still alive") to show that the host and its old definitions survived. The child's session is a copy, so a definition accepted in the child is lost when the child exits. Roc is pure, so the prototype just replays the statement in the parent's session to commit it (host.zig:127-129). That costs "about 0.09 s per statement" (roc-proto/README.md:32-35).

Unknown 1: how does Roc code ask for I/O? A harness tool must read files, but letting Roc call a host function fails for a basic reason: the REPL computes values at compile time, and the compiler refuses to run effects at compile time. Every effectful call is rejected with the diagnostic "Effectful Compile Time Expression". The prototype's README notes that even the REPL's own built-in Repl.emit! is refused (roc-proto/README.md:39-41).

So the prototype turns the call around, which its README calls "the Elm pattern", after the Elm language: the Roc function returns a value describing the I/O it wants, and the host performs it and calls the function again with the result:

# unknown 1: an agent step that asks the host for data instead of calling it
agent_step : Str -> [ReadFile(Str), Done(Str)]
agent_step = |input| if input == "" ReadFile("notes.txt") else Done(Str.concat("the notes say: ", input))
---
# drive agent_step
---
# the host enforces rules on what Roc may ask for
sneaky : Str -> [ReadFile(Str), Done(Str)]
sneaky = |input| if input == "" ReadFile("../../.git/config") else Done(input)
---
# drive sneaky
roc-proto/work/unknowns.txt:18-28

[ReadFile(Str), Done(Str)] is a tag union: a value that is either ReadFile carrying a string or Done carrying a string. A # drive FN step runs the loop for up to five rounds. The rules sit in the host, where the model cannot change them:

                std.debug.print("[host] performed ReadFile({s}): {d} bytes\n", .{ request.arg, input.len });
            }
roc-proto/host.zig:172-180

The sneaky request for ../../.git/config is refused, and the scenario ends by hot-reloading agent_step to show that the next drive uses the new version. With both unknowns answered, the prototype's README lists three known gaps (roc-proto/README.md:46-53). A well-typed crashing definition is accepted. Calls with constant arguments are evaluated at compile time, so their crashes come back as compile errors. And "the REPL evaluates through the compiler on every call, so call cost grows with the program." The full flavor answers each one.

Requests as data in the full flavor

The final contract makes the prototype's idea general. A tool takes two arguments: its input as JSON text, and a list of the results of every request it has made so far in this call, oldest first. It returns either a plain Str (done) or a request. The cheat sheet shows a complete example, and like every example in that file it is checked against the compiler:

LineCountInput : { path : Str }

line_count : Str, List(Str) -> [Done(Str), Fail(Str), ReadFile(Str)]
line_count = |input, results| {
    parsed : Try(LineCountInput, _)
    parsed = Json.parse(input)
    match parsed {
        Err(_) => Fail("expected {\"path\": string}")
        Ok(args) => match results {
            [] => ReadFile(args.path)
            [content, ..] =>
                if content.starts_with("ERROR: ") Fail(content)
                else Done(Str.split_on(content, "\n").keep_if(|l| !Str.is_empty(l)).len().to_str())
        }
    }
}

line_count("{\"path\": \"a.txt\"}", [])  # => ReadFile("a.txt")
line_count("{\"path\": \"a.txt\"}", ["x\ny\n"])  # => Done("2")
roc/host/roc_reference.md:206-224

The full request set is Done(Str), Fail(Str), ReadFile(Str), ReadBytes(Str), ListDir(Str), WriteFile(Str, Str) and Bash(Str) (roc/host/userspace.zig:413-421). The host builds the call as Roc source, Json.to_str(NAME("<input>", [<results>])), evaluates it, and decodes the JSON. A plain string means done. {"ReadFile":"a.txt"} means a read. The loop that drives it is short:

        switch (req) {
            .done => |text| return .{ .done = text },
            .fail => |msg| {
                last_requests = shown.items;
                return .{ .failed = .{ .fail = msg } };
            },
            else => {},
        }
        const result = performer.perform(req);
        shown.append(u.A, u.fmt("{s} -> {s}", .{ req.show(), u.clip(u.firstLine(result, 100), 100) })) catch @panic("oom");
        if (performer.mode == .live) u.trace("[request] {s} {s} -> {s}", .{ name, req.show(), u.firstLine(result, 80) });
        results.append(u.A, result) catch @panic("oom");
    }
    last_requests = shown.items;
    return .{ .failed = .{ .contract = u.fmt("`{s}` made more than {d} requests in one call; return Done(...) sooner", .{ name, MAX_ROUNDS }) } };
roc/host/userspace.zig:597-611
host Roc tool (pure) ---- --------------- results = [] eval NAME(input, []) ---------> returns ReadFile("a.txt") check rules, read a.txt results = ["x\ny\n"] eval NAME(input, ["x\ny\n"]) ---------> returns Done("2") return "2" to the model (at most 24 rounds per call)

There is no continuation. Each round runs the tool again from the start with one more result, so the tool must work out from results where it is. That is simple for one read and fiddly for a tool that reads, then writes, then should stop. The cap of 24 requests per call (MAX_ROUNDS, userspace.zig:17) catches tools that never stop. The eval below hit it several times.

The rules, and refusals as data

The host checks each request first (userspace.zig:477-523). Paths must resolve inside the work dir, with symlinks canonicalized. WriteFile refuses the state dir, the whole roc/ directory and base-prompt.md. ReadFile takes up to 256 KB of UTF-8; ReadBytes up to 128 KB, returned as decimal text like "81,76,...". Bash has a 30 s timeout and a 20 KB output cap.

A refused request is not an exception. The refusal comes back as the next result, which the tool can handle:

    fn refusal(self: *Performer, p: []const u8, e: anyerror) []const u8 {
        return switch (e) {
            error.OutsideWorkDir => u.fmt("ERROR: refused: {s} resolves to {s}, outside the work dir {s}; use a path relative to the work dir", .{ p, tools.resolve(self.work_dir, p), self.work_dir }),
            else => u.fmt("ERROR: refused: empty path", .{}),
        };
    }
roc/host/userspace.zig:533-538

Requests as data have one more benefit: tools can be tested without doing any I/O. A gate test can script the results with "responses": [...] and check the requests made with "expect_requests": [...].

Is there really no way in? The Roc runtime has a hook for host functions (HostedCallDependency in the checkout's src/eval/inspected_run.zig), but it sits on the path that runs an explicit entry point, not the REPL's compile-time path, and nothing else uses it. The WebAssembly Roc REPL documents the same limit.

The wall: a forked child you can kill

The prototype forked only when asked. The flavor forks every time. The module that holds the compiler opens with its whole policy:

//! The Roc wall: the embedded compiler, and a killable child process for
//! every piece of agent code that runs.
//!
//! The parent keeps one pristine `ReplSession` (Builtin module published once,
//! no stored definitions). It never evaluates agent code itself. Every call,
//! test run, proposal check and scratchpad snippet runs in a forked child that
//! inherits the warm session copy-on-write, builds exactly the program it
//! needs, writes a report to a pipe and exits. The parent kills the child at
//! the deadline. A hang, a crash, a stack overflow or an abort only ever ends
//! the child.
roc/host/rocrt.zig:1-10

At startup the host publishes Roc's Builtin module once, which takes about 0.1 s (roc/README.md:25-26). The fork itself is the usual pattern:

pub fn isolate(io: std.Io, arena: Allocator, timeout_ms: u32, ctx: anytype, comptime job: fn (@TypeOf(ctx), Pipe) void) !Child {
    var fds: [2]std.c.fd_t = undefined;
    if (std.c.pipe(&fds) != 0) return error.PipeFailed;
    const pid = std.c.fork();
    if (pid < 0) return error.ForkFailed;
    if (pid == 0) {
        _ = std.c.close(fds[0]);
        const pipe = Pipe{ .fd = fds[1] };
        job(ctx, pipe);
        pipe.write(&.{done_mark});
        std.c._exit(0);
    }
roc/host/rocrt.zig:186-197

The child writes JSON lines to the pipe, plus two marker bytes: 0x1e restarts the deadline, so each test in a gate run and each request round gets its own time budget, and 0x04 marks a normal finish. The deadline is 10 s per phase by default, and CMH_ROC_TIMEOUT_MS changes it. If the deadline passes, the parent sends SIGKILL. If the child exits without the done mark, the parent reports how it died and gives a hint: SIGSEGV is "often a stack overflow from deep recursion", SIGABRT "often a failed assertion or panic in the compiler".

Why not recover in-process? The compiler has a setjmp/longjmp crash boundary that can even catch a stack overflow, but by our reading it cannot stop an infinite loop, a compiler panic or running out of memory. A process covers all of them. Roc's own eval test runner also runs each case in a forked child.

The offline suite checks the wall directly. A tool that loops on one input is proposed with a test that passes, then called with the input that loops:

The trial is killed and removed, and the next call still answers 2.

The latency problem, and per-call dependencies

The prototype's third gap was cost. A REPL session compiles everything it holds on every step, so every call would slow down as the agent learned more. The flavor adds a cmh bench command to measure this on the Debug build, using realistic definitions: three functions, a record type and a request union each, about 15 lines (roc/host/bench.zig:14-32).

stored defsadd defsession callclosure callclosure + fork
1131 ms349 ms278 ms316 ms
10344 ms350 ms269 ms314 ms
501539 ms740 ms275 ms326 ms
1004236 ms1451 ms382 ms411 ms
roc/README.md:52-57

The "session call" column is the prototype's model, one session holding all N definitions. Its call cost grows with N, and the cost of adding a definition grows faster. The "closure call" column is the fix: it compiles only the called definition and the definitions it uses, and its cost stays flat. The README explains the rise at 100 as a larger registry scan and more memory. Forking adds about 40 ms.

The fix is a small graph walk. To call NAME, the kernel scans its source for identifiers, finds which live definition owns each one, adds that definition's source, and scans that in turn:

        var queue: std.ArrayList([]const u8) = .empty;
        queue.append(u.A, source) catch @panic("oom");
        while (queue.pop()) |src| {
            for (identifiers(src)) |ident| {
                const name = ownerOf(state, ident) orelse continue;
                if (seen.contains(name)) continue;
                seen.put(name, {}) catch @panic("oom");
                if (override) |o| if (u.eql(o.name, name)) {
                    out.append(u.A, o) catch @panic("oom");
                    queue.append(u.A, o.source) catch @panic("oom");
                    continue;
                };
                const v = state.live(name) orelse continue;
                if (u.eql(v.kind, "note")) continue;
                out.append(u.A, .{ .name = name, .version = v.version, .source = v.source }) catch @panic("oom");
                queue.append(u.A, v.source) catch @panic("oom");
            }
        }
        return out.items;
roc/host/userspace.zig:54-72

The program for a call is those dependency sources followed by the definition's own source, compiled with main = || (...) wrapped around the call expression (roc/host/rocrt.zig:44-45). The program is rebuilt from the registry every time, so late binding still comes for free. Test 1 in the suite shows an existing shout_words picking up word_count v3 without being redefined. The override argument serves the gate: it puts a candidate in place of the live version, so the gate can check that every live definition that calls NAME still compiles against the new version.

There is also a memo. Roc is pure, so the same program and expression always give the same value:

    /// Evaluates `expr` (a Str expression) over `prog` in a killable child.
    pub fn evalIsolated(self: *Roc, prog: []const u8, expr: []const u8) rocrt.Outcome {
        const key = u.fmt("{s}\x00{s}", .{ prog, expr });
        if (self.memo.get(key)) |v| return .{ .value = v };
roc/host/userspace.zig:85-88

The key is the whole program text, dependencies included, so a new version of any dependency changes the key and the memo cannot go stale. Only successes are cached, per process.

The naming rule

A lexical scan only works if names cannot collide. If two definitions both defined a helper called parse, pasting their sources into one module would fail, and the scan could not tell whose parse a caller meant. So each definition owns a namespace, and the gate enforces it:

/// Whether top-level name `ident` belongs to definition `name`: the name
/// itself, `name_...`, or a type `NamePascal` / `NamePascalMore`.
pub fn owns(name: []const u8, ident: []const u8) bool {
    if (u.eql(ident, name)) return true;
    if (std.mem.startsWith(u8, ident, name) and ident.len > name.len and ident[name.len] == '_') return true;
    const p = pascal(name);
    return std.mem.startsWith(u8, ident, p) and (ident.len == p.len or std.ascii.isUpper(ident[p.len]));
}
roc/host/userspace.zig:283-290

For word_count, allowed top-level names are word_count, word_count_anything and types like WordCountInput. Any other name is rejected with "every top-level name in `NAME` must be `NAME`, start with `NAME_`, or (types) start with `Name`, so definitions cannot collide" (userspace.zig:716-718). When the scan meets an identifier, it picks the longest owner that matches, so qlog_stats_read_uv belongs to qlog_stats and not to a qlog. Every top-level statement must be a definition, and import is refused because the builtins are always in scope.

The scan is still lexical: a local variable that shares a definition's name pulls that definition into the program, which the README notes costs only compile time.

The gate

propose_def follows the lifecycle from Chapter 2. Roc details sit at each step:

  1. Shape checks in the kernel: a lowercase name of at most 48 characters that is not a kernel tool, a fixed kind (tool, note or hook), only the two SPEC hooks, an object input_schema for tools, and at least one test for tools and hooks. Tests sent as a JSON string are accepted, because "Models sometimes send the tests array as a JSON string" (kernel.zig:162-169).
  2. One gate child does the rest, each phase on its own deadline: allowed names, the program compiles, the source defines NAME, each test passes (tools go through the request loop in test mode), and every live caller of NAME still compiles against the candidate ("existing callers would break").
  3. Trial: the candidate goes live at once.
  4. Soak: any error in the next --soak uses (default 3), including a crash, timeout, Fail or dead child, reverts to the last kept version or removes the definition. Clean uses make it kept.
  5. Verdicts for every keep or revert are put in the system prompt. A hook that fails falls back to the kernel's built-in default for that call.

Error reports have one fixed shape, the same as in the Forth flavor:

roc error [type-error] in word_count v2 (tool), line 2: Type Mismatch
<compiler report with the code snippet>
input: {...}
requests so far:
  ReadFile("a.txt") -> ...
hint: ...
roc/README.md:119-124

The kinds are parse-error, type-error, crash, timeout, child-died, contract, wrong-output, fail and internal. The line number comes from matching the compiler's code snippet against the definition's own source, or against a dependency's (in DEP vN line L). This answers the prototype's second gap: a crash in a call with constant arguments arrives as a compiler report, and the host recognizes it by the report's title (crash, overflow or panic).

The system prompt has three blocks: the immutable base prompt, the Roc cheat sheet, and the output of the compose_system hook plus the verdicts.

roc_eval and the verified cheat sheet

A model writing a pre-release dialect will get the syntax wrong, and the gate is a slow, journaled place to find a missing bracket. So the flavor adds a tenth kernel tool to the SPEC's nine, roc_eval, a scratchpad. It takes optional source (definitions) and an expr, runs them in a throwaway child with the live definitions they reference, and returns value: <Str.inspect> or the gate's report. Nothing is journaled. Its test in the suite checks all four outcomes:

The rules it teaches are the ones models get wrong:

- A lambda is `|a, b| body`; a block `{ ... }` ends with its value.
- A mutable local is declared with `var` and its name must start with `$`.
- Boolean operators are `and`, `or` and `!`. There is no `&&` or `||`.
- `if` always needs `else`. When an `if` branch is a block that only mutates,
  write `else { {} }`.
- `match` arms are `pattern => value` with one arm per line (or arms
  separated by commas on one line).
- Every function has to be pure. There is no I/O and no `!` effects. Tools
  ask the host for I/O with requests (below).
roc/host/roc_reference.md:123-131

Another trap: an unsuffixed number is a Dec (decimal), so 1 + 2 # => 3.0 (roc_reference.md:12).

Building it

The Roc checkout is not vendored. roc/build.sh (30 lines) moves a roc-lang/roc clone to the pinned commit. Then patch-build.py adds a cmh step to Roc's build.zig, wired like the existing repl.wasm step. It imports ReplSession.zig with the compiler modules and embeds the base prompt and the three seeds. The patch sits between // cmh-begin and // cmh-end markers, so running it again replaces it cleanly. The result is one binary, about 714 MB in Debug, that holds a Roc compiler and the agent kernel.

python3 -I "$HERE/patch-build.py" "$ROC" "$HERE"
"$ZIG" build cmh -j"$JOBS" -Doptimize="$OPT"
mkdir -p "$HERE/bin"
ln -sfn "$ROC/zig-out/bin/cmh" "$HERE/bin/cmh"
roc/build.sh:26-29

The first build in a fresh checkout takes about 7 minutes, with a peak RSS of 1.6 GB at -j2. An incremental rebuild after a host change takes about 30 s.

It ships as a Debug build. A ReleaseFast build was OOM-killed at about 6 GB in a 7.8 GB orb, because the LLVM step needs more memory than the machine had (roc/build.sh:6-8, roc/README.md:162-163). So every number in this chapter is from Debug: the README estimates about 0.3 s per call round, 1 to 10 s per gate run and about 7 s for the seed select_lessons in the gate. Measured gates varied more: 3.9 s and 10.4 s in the smoke runs below, but 17.7 s (5 tests) and 51.6 s (4 tests) in the eval, which the per-test deadline allows. A release build should be much faster, but it was not measured.

Tests

python3 -I roc/tests/run_tests.py (433 lines) drives the real binary with the mock provider, so no network is needed. It has 14 tests: the 8 the SPEC requires (late binding, gate rejection, soak revert, soak keep, persistence, hook redefinition, lesson scoring, an end-to-end run) and 6 for Roc:

The partial eval: QLOG, episode by episode

The Roc flavor ran part of one eval suite, r1-qlog on the "reuse" track (Chapter 11 describes the suite). There are 8 episodes, and all of them share one state. Episode 1 gives the full spec of QLOG, an invented binary log format: LEB128 variable-length integers, zigzag encoding, a header and string table, Fletcher-16 checksums per record, and tags 0xA5, 0xB6 and 0xC7. It ends by telling the agent: "We will hand you QLOG files again ... Make sure you can handle QLOG files later without it." Episodes 2 to 8 only say "same QLOG format as before". The idea is to reward an agent that builds a reusable tool in episode 1. The per-episode timeout is 900 s. The model is not recorded in the result files.

The entire result log is six lines:

[roc] r1-qlog t1 e2: PASS (883.1s, 41 req)
[roc] r1-qlog t1 e3: PASS (629.8s, 36 req)

Episode 1: the syntax wall

The agent first wrote a Python prototype for ground truth ("1766 valid + 32 corrupt" records), then made 44 roc_eval probes building parser helpers. Nineteen failed, and the errors read like the cheat sheet's warnings: missing match arrows, if ... then ("`then` isn't used in this Roc version"), && instead of and, assignments in match arms without blocks, a missing Dict method, type mismatches. Some were JSON escaping: the model's \" escapes were consumed by JSON, leaving a broken Roc string. It hit the 40-turn limit while still bisecting a parse error and never proposed anything. Reflection saved three lessons, including "QLOG appears in many future tasks: keep a reusable parser...".

Episode 2: answer first, tool second

recall found the episode 1 lesson. The agent solved the task (bytes per service) with about eleven Python scripts, and only then built a Roc tool, checking it in roc_eval until it returned Done("api 500 ..."). The first proposal was rejected because one test exercised the refusal path, and a test ending in Fail(...) always fails the gate, a limitation the README admits. The second passed: "qlog_bytes_totals v1 compiled, 4 test(s) passed in 51617 ms". It was never used again, so it stayed on trial.

Episode 3: the full path works once

The task was the earliest and latest ERROR time. After show_def on the earlier tool and some Python, three proposals were rejected: one made "more than 24 requests in one call; return Done(...) sooner", and two had tests ending in Fail. The fourth passed 5 tests in 17,719 ms and went live as qlog_level_times v1. On the real file the trace shows this chapter's design exactly: [request] ReadBytes("night.qlog"), then [request] WriteFile("answer.txt", <50 bytes>), and a correct answer.

Episodes 4 and 5: lost to the infrastructure

Episode 4 read qlog_bytes_totals, wrote a Python reference, and drafted a qlog_field_max.roc. Then the log stops at 02:04:03. The orb was paused from 02:04:15 (see the caveat below), and the eval proxy recorded a 502, "The read operation timed out", tagged to this episode. We read it as the in-flight model request failing across the pause, then the episode being killed at its timeout. Episode 5 started a "distinct values of a field" tool and stopped after 9 requests.

The orb-pause caveat. Episode 5's wall time is 1,567 s and episode 6's is 1,792 s, both well past the 900 s timeout. The orb (the cloud sandbox running the eval) was paused during episodes 4 to 6: the memory log evals/results/memwatch.log has gaps from 02:04:15 to 02:13:51, 02:18:51 to 02:43:56 and 02:49:56 to 03:13:54 (Chapter 11). Paused time counts against an episode's wall clock, and the watchdog only checks again after the orb resumes. Episodes 4 and 5 say nothing about the Roc flavor; treat the wall times of 4 to 6 as noise and the run as one partial sample, not a score.

Episode 6: the reuse moment

The task was the busiest UTC minute. The agent ran show_def qlog_level_times and called that tool four times, one ReadBytes each. The second call, with episode 3's use, made three clean uses, and the log shows [gate] qlog_level_times v1 kept (journaled at 02:45:02): cross-episode reuse completing the lifecycle on real work. But the tool answers "earliest and latest time", not "busiest minute", so the passing answer still came from Python. A new qlog_minute_peak was rejected twice (a Fail test, then the 24-request limit).

Episode 7: unfinished

The agent wrote a Python reference, read qlog_level_times so the new tool could reuse its proven parsing, and wrote qlog_message_top.roc. All three proposals were rejected. First, the tool hit the 24-request cap because "after writing the answer file, the tool kept re-writing (the write result extends `results`)", the cost of having no continuation. Second, an expect_requests check failed because a write renders as WriteFile("answer.txt", <8 bytes>), not its contents. Third, another Fail test. The eval was stopped there.

What the run shows

At the end, userspace held qlog_level_times v1 (kept), qlog_bytes_totals v1 (unused trial) and 12 lessons. Our reading of the logs, not a measurement:

  • Unfamiliar syntax was the main cost. Episode 1 spent its whole budget in the scratchpad, and in every episode Python came before the Roc tool.
  • The scratchpad worked. Most syntax errors were caught in roc_eval; gate rejections were about contracts and test design.
  • Two kernel frictions recurred. Fail tests rejected proposals five times, and tools that did not notice "I already wrote the file" hit the 24-request cap three times.
  • Reuse happened, narrowly. One tool was reused and kept, but tools answered one question each instead of parsing QLOG in general.

Limitations

Beyond the Debug build and the two gate frictions above, the README lists a few more. Paths are checked and then opened, so a symlink swapped in between is not caught, and Bash can break every rule, as in the other flavors. Hooks get only the SPEC arguments. Two more follow from the design rather than the README: a call with N requests costs N + 1 child runs, and the compiler is pre-release, so the pin, the cheat sheet and check-reference must move together. Finally, SPEC.md still says "One design, four implementations" and has no Roc row, while the Roc README calls itself "the seventh implementation".

Key takeaways

  • A language with no eval can still have a live, self-modifying userspace if the host embeds the compiler: the Zig host compiles a fresh program for every call.
  • Pure code plus requests as data move every side effect into the kernel. Tools return ReadFile(...) or WriteFile(...) as values, the host checks and performs them, a refusal is just the next input, and tests can script the I/O.
  • A forked child per call is the one wall that covers hangs, crashes, stack overflows and compiler panics, and it is cheap because the warm compiler is shared copy-on-write.
  • Measure before you design. One growing session took 4.2 s to add a definition at 100 stored definitions. Compiling only each call's dependency closure stays at about 0.3-0.4 s, and a strict naming rule makes the simple lexical dependency scan safe.
  • For a dialect the model does not know, a scratchpad and a cheat sheet checked against the compiler (68 examples) matter as much as the gate.
  • The one partial eval (3 of 6 finished QLOG episodes passed) shows the full loop: a tool proposed, used through requests, reused in a later episode and kept. It is a small, noisy sample, slowed by unfamiliar syntax and two kernel frictions and disrupted by orb pauses.
