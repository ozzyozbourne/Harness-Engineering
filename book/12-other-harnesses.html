Harness Engineering · Chapter 12

12. Other self-modifying harnesses we studied

Twelve open-source projects, what each lets an agent change about itself, and how mainstream coding agents keep a growing tool list manageable

cmh did not start from a blank page. Before we wrote SPEC.md we cloned a dozen public repositories that let an agent change the program it runs in. We also cloned seven mainstream coding agents to see how they cope when a model has more tools than fit comfortably in its context. This chapter tours the first group, lists what cmh took from them and could still take, then explains code mode and tool search, two ideas that matter once an agent keeps writing its own tools.

How this survey was done. The repositories were cloned on 2026-10-29 and read as untrusted data; nothing was built or run. The small ones were read closely, the large ones (golem, deepseek-harness, fx, fold, exo) surveyed from READMEs, docs and targeted searches. Where a claim below is our reading of a design rather than something the code or docs state, we say so.

A map of the twelve

Most of these projects are written in a Lisp, for the reasons chapter 1 gave: programs are ordinary data, and a running system can be extended without restarting. The Lisp projects also know each other. autolith's README lists samizdat, sm-harness, fractal-engine, oh-my-lisp, jiti and lisptc among its "Friends of Autolith", and samizdat's mutation.clj adopts "autolith's journaled mutation state machine".

A useful way to sort them is by what is mutable:

what the agent may change projects ─────────────────────────────────────────────── ─────────────────────────────── 1. the harness's own code, live, in-process cl-sm-harness, autolith, oml 2. the agent loop and its policies, as data samizdat 3. an application or userspace next to a jiti, lisptc, fractal-engine, fixed kernel deepseek-harness 4. its own source, then rebuild and restart exo (self-improving example) 5. nothing (useful as contrasts) golem, fold, fx

cmh sits in group 3: a fixed kernel calls, by name, a userspace of tools, notes and hooks that the agent grows. Only the WASM flavor (chapter 9) reaches into group 1, by letting the agent propose a new kernel image.

The projects one by one

autolith: the most complete self-modifier

autolith is "a live, self-modifying Common Lisp terminal agent". It runs inside a live SBCL image. An image is the whole running heap of functions and data, which can be saved and restarted later. The agent can redefine its own functions while it runs.

Its self-modification works in two tiers: explore, then commit. self.eval and self.redefine install a change live and journal it with an undo action, and self.exercise records evidence that it works. self.commit then replays the changes in a clean process to check that key functions survived, commits them to a private git history, and makes that the startup state.

(defun self-install-definition
    (configuration source &key (package (find-package '#:autolith)))
  "Compile and install one exploratory SOURCE definition in PACKAGE."
  (with-live-mutation
    (let ((definition   (self-read-form source
                                        :read-eval nil
                                        :package   package))
          (package-name (package-name package)))
      (unless (definition-form-p definition)
        (error 'source-mutation-error
               :message   "self.redefine accepts one complete supported definition."
               :tool-name "self.redefine"
               :pathname  nil))
autolith/src/self/tools.lisp:720-732

Notice :read-eval nil. The Lisp reader can normally run code while it is parsing text, and this option turns that off, so the source stays plain data until autolith decides to install it.

autolith has more safety nets. At startup, a replayed change whose original source has since moved is skipped and reported, so an old patch never hides newer code. Generations are full image checkpoints, made by forking the process and saving it. And if the active image is broken, the launcher boots a separately built recovery image, a pristine copy of the agent that can repair the broken one from outside.

samizdat: the agent loop as data

samizdat is "a self-hosting agentic harness for Clojure development". It runs on Jolt, a Clojure implementation hosted on Chez Scheme. It is cmh's most direct ancestor (see "What cmh borrowed" below).

samizdat has three rings. The kernel (journal, event bus, store, secrets) cannot be changed by the agent. The executor is the agent loop, written as an EDN manifest. EDN is Clojure's data notation, much like JSON with more types. The loop is a graph of cells (steps) and edges (what runs next). The outer ring holds capabilities such as the REPL, the language server and the shell.

Because the loop is data, the agent can edit it, so the manifest also carries invariants that the kernel checks:

 :edges {:route  {:continue  :start
                  :done      :distil
                  :abandoned :distil
                  :exhausted :distil}
         :distil :revisit
         :revisit :finish
         :finish :end}

 :invariants
 [{:type :must-precede :cell :distil :before :finish :enforced true
   :protects "A task that ended wrote down what it learned about the project
              before the branch closed. Asking the model to remember things
              produced nothing across 46 turns of live runs; a step in the
              graph runs whether or not it feels like it, and putting it before
              :finish is what stops a future edit routing an ending around it."}]}
samizdat/resources/manifests/loop.edn:25-39

Every ending, including giving up, routes through :distil, the reflection step, and the invariant stops any loop edit from skipping it.

samizdat's gate, in mutation.clj, is the longest in the set: checkpoint, reload, validate, soak (a dry run with a 10-second timeout), live probes of each changed definition, a test battery, then commit or rollback. A rollback restores the registry and the file, and journals the bad edit as a negative constraint. A separate held-out gate (heldout.clj) replays a frozen battery against the current and the candidate userspace, each in its own child process. It is non-compensatory: a candidate fails if any target that passed before now fails, however much it improves elsewhere. It deliberately accepts ties, so neutral edits get through.

jiti: caller-owned acceptance

jiti ("grow a running Lisp application by talking to it") is a Common Lisp kernel of about 2.1k lines. Rather than editing files, chat develops a live application, a catalogue of functions plus managed state, while the kernel stays fixed. Tools like develop_form (add, redefine or remove a function) and execute_form share one evaluator and one transaction engine.

Its key idea is that the agent does not decide whether its own work is acceptable. The caller supplies goals (has the capability been achieved?) and safety invariants (is this state acceptable?). Every attempt starts from a checkpoint:

               (let ((results (check-predicates (session-invariants s))))
                 (emit s :invariants :results results)
                 (unless (all-pass-p results) (throw 'abort-attempt :unsafe)))
               (handler-case (setf changed (not (equalp before (capture-managed-state w))))
                 (error () (throw 'abort-attempt :state-capture-failed)))
               (setf (getf (session-outcome s) :changed) changed)
               (when preview (throw 'abort-attempt :preview))
               (when (and changed (session-store s))
                 (handler-case (publish-revision s)
                   (publication-error (c)
                     (if (publication-uncertain-p c) (error c)
                         (throw 'abort-attempt :publication-failed)))))
               :accepted))))
jiti/src/kernel.lisp:305-317

A failed invariant aborts the attempt, and the world is restored from the checkpoint (line 323). Otherwise a changed world is published as a durable revision. As the README puts it, "Model-generated implementation or a completion message cannot replace the acceptance contract."

jiti also uses Common Lisp restarts: a failing call pauses instead of unwinding and survives across prompts in a persistent worker thread, so the model can fix the function and resume inside the original failing call.

cl-sm-harness: reload yourself, then prove it

cl-sm-harness is "a self-improving agent harness for Claude Code, written in Common Lisp". It drives the claude CLI as a subprocess and gives it the harness's own tools through an in-process MCP server. The agent edits the harness's .lisp files with write_file, then calls reload_harness, which reloads the whole system into the running process:

          (asdf/session:call-with-asdf-session
           (lambda () (asdf:load-system *reload-harness-system* :force force))
           :override t :override-cache t))
cl-sm-harness/harness/sm-harness/src/tool-catalog.lisp:872-874

This works because tool handlers are stored as symbols (names), not function objects, so the next call finds the new definition: the same late binding cmh uses (chapter 2). After a successful reload the harness sends an automatic follow-up turn telling the model to "call it now to verify it works", at most 3 in a row.

cl-sm-harness has no automatic rollback. Its own reload error message warns that an incompatible struct or class redefinition can leave the image "permanently unable to reload that type again ... until the container is restarted". Recovery is git plus a container restart (our inference).

oh-my-lisp: every step is a var

oh-my-lisp (oml) is "a minimal coding agent in Clojure (babashka) that you change while it runs", a teaching project of about 1.5k lines. Every loop step (system-prompt, call-model, execute-tool and so on) is a public function called through its var, Clojure's named, mutable slot, so replacing what the var holds changes the next call. The catch is that the user does the modifying, with defn or Emacs-style advise! (which wraps a function in place) from an init file, /eval or a REPL. The model has only read, write, edit and bash, and there is no safety layer.

fractal-engine: a sandboxed REPL with immutable history

fractal-engine is "a recursive language-model compute engine": a model drives a persistent Clojure REPL and can spawn child sessions. The engine is fixed, but two ideas matter. First, model code runs in SCI (the Small Clojure Interpreter) under a capability profile that denies everything by default. The strictest, locked-down, denies file reads and writes, shell and network, and grants five core namespaces (src/fractal/engine/capability.clj). The gated I/O functions are injected into clojure.core itself, so switching namespace with in-ns cannot escape them. Second, every turn publishes an immutable head (a saved state); an aborted turn leaves a "wreckage" head that can be inspected or forked but is never resumed from.

The rest, briefly

lisptc hosts its own Lisp dialect in TypeScript. The model has no tools: its whole reply goes to a persistent Lisp REPL, so functions it defines stay live and its vocabulary grows. The image can be snapshotted as JSON, and memories can carry a replayable form and an event trigger. There is no gate on a definition (our inference).

deepseek-harness is built on Cordis, where "everything is a plugin" and plugins hot-reload. In Creator mode the agent writes and installs a plugin bundle, and its tools appear in the running session. A failed install restores package.json and the lockfile. Its SAFETY.md says it has not had a security audit and must not be treated as secure.

exo is an agent runtime in Rust and TypeScript. Its examples/self-improving-agent mounts exo's own source in the agent's sandbox and gives it rebuild_and_restart_exo, which builds and restarts the host. The sandbox can be rewound, but we found no rollback of code.

Three projects do not self-modify at all. golem runs WebAssembly components as durable workers, and it can update a running worker to a new version by replaying its operation log and failing on divergence. fold records model and prompt changes as "epochs" in an event log. fx is a Zig binary whose tool registry is fixed at compile time, which shows what a truly minimal kernel looks like.

Three ideas recur: late binding through names, so a redefinition reaches the running loop; journaling every attempt but keeping only what survived; and recovering a broken self from a pristine image, a snapshot or a rewound sandbox. By our rough ranking, samizdat and autolith have the strongest safety, and oml and lisptc the weakest.

What cmh borrowed, and what it could still borrow

Already borrowed

SPEC.md names samizdat, Prime Agent (chapter 3), autolith and oh-my-lisp as sources. Links marked "inferred" are our reading, not stated in the spec.

Could still borrow

Most items below fill a gap that ROADMAP.md already names.

  1. The agent loop as data, with invariants (ROADMAP §4, experiment 6). Today the agent cannot change its own loop. samizdat's manifest shows how: loop steps as hooks, with kernel-checked ordering rules such as "reflect before finish".
  2. A non-compensatory held-out battery (ROADMAP "fitness-based keeping"). cmh's --provider mock --script could replay recorded tasks against the current and candidate userspace, as samizdat's heldout.clj does.
  3. Caller-owned acceptance checks (ROADMAP: "Task success is self-reported"). jiti-style goals would let a task carry an external verifier.
  4. A pristine recovery mode (ROADMAP §1): boot the seed kernel with an empty userspace to diagnose a journal that replays into a broken state, as autolith's recovery image does.
  5. Reflection on every ending. ROADMAP suggests reflecting only on failure or novelty. samizdat argues for reflecting on every ending, abandoned runs most of all. That disagreement is worth an A/B test.
  6. Capability profiles (ROADMAP §1, sandboxed bash). fractal-engine's deny-by-default profile, and its point that gating must survive in-ns, apply directly to the Clojure flavor, where SCI could replace raw load-string.
  7. A verification nudge after a change, like cl-sm-harness's follow-up turn. cmh's soak counts uses but never asks for them, and a nudge could shorten trials.

Smaller ideas would also fit: autolith's stale-override detection, lisptc's triggered memories as input to cmh's scored lessons (ROADMAP §6), and golem's update modes for cmh-wasm kernel images whose state format changes.

Code mode and tool search

A harness normally sends the model every tool's name, description and input schema on every request. cmh does exactly this: SPEC.md says "Userspace tools are added to the tool list on every model request, rebuilt from the live registry each time."

That is fine with nine kernel tools and a few userspace ones. Now imagine an agent that has kept two hundred small tools. All their schemas sit in the context on every turn, though a task needs three. Chaining is slow too: with ten tool calls, every result flows back through the model before the next call. Mainstream coding agents have converged on two answers.

Tool search: deferred tools

Tool search keeps most definitions out of the context. A deferred tool is not described up front. The model gets one always-present search tool instead, and when it searches, the harness loads the matching tools' schemas so it can call them.

Anthropic shipped this as the Tool Search Tool in November 2025, with tools marked defer_loading: true and regex and BM25 search variants. BM25 is a classic keyword-ranking formula from search engines. Anthropic reported that tool search raised Opus 4 from 49% to 74% and Opus 4.5 from 79.5% to 88.1% on its MCP evaluations, and recommends it from about 10 tools ("Introducing advanced tool use"). Deferred tools also stay out of the cached prompt prefix, so the provider's prompt cache survives.

Hermes Agent's docs show the shape most clearly. When tool search is on, the deferred tools are replaced by three bridge tools:

tool_search(queries, limit?)   search the deferred-tool catalog (one or more queries)
tool_describe(names)           load the full schemas for one or more tools
tool_call(calls)               invoke deferred tools; `calls` is an array of {name, arguments}
hermes-agent/website/docs/user-guide/features/tool-search.md:36-38

Code mode: one tool that runs a program

Code mode attacks chaining. The model gets one tool that runs code, the other tools appear as functions in an API, and the model's short program runs in a sandbox. Intermediate results stay inside the program, and only what it prints or returns reaches the model. Cloudflare introduced the idea in 2025. Anthropic's "Code execution with MCP" (November 2025) cites Cloudflare's similar findings, with an example that cut 150,000 tokens to 2,000 (98.7%). Combined, the two give the arrangement below: tools are deferred, found by search, and called from inside a code-execution tool.

model context harness ┌──────────────────────────┐ ┌──────────────────────────────────┐ │ always loaded: │ │ catalog (hundreds of tools, │ │ tool_search │──query──▶│ BM25 over names + descriptions) │ │ code_exec │◀─schemas─│ │ │ a few core tools │ └──────────────────────────────────┘ │ │ ┌──────────────────────────────────┐ │ model writes: │ │ sandbox (V8, QuickJS-in-WASM, │ │ const a = await t1(x) │──code───▶│ interpreter, or subprocess) │ │ const b = await t2(a) │ │ t1 ─▶ host ─▶ result │ │ text(summary(b)) │◀─output──│ t2 ─▶ host ─▶ result │ └──────────────────────────┘ └──────────────────────────────────┘ only the search hits and the final output enter the context

The sandbox has no powers of its own beyond the functions the host injects. Pi's package says it in one sentence:

Runs model-written JavaScript in a QuickJS VM (compiled to WebAssembly) where the only capability is calling injected tools. Nested tool calls never enter the LLM context; only the script's output and return value do.
pi/packages/codemode/README.md:3

Prime Agent (chapter 3), not one of the seven, does both its own way: its only tool is a persistent Python REPL, and inside it mcp.search_tools finds MCP tools by an unranked, case-insensitive substring test on name and description.

Some patterns stand out. BM25 is the usual search backend (Codex, Pi, Hermes, MiMo, Grok Build, Anthropic's server tool). Code-mode sandboxes vary: V8 in Codex, QuickJS compiled to WebAssembly in Pi and MiMo, natively embedded QuickJS in Deep Agents' partner package, a custom interpreter in OpenCode, a Python subprocess in Hermes. Hermes and MiMo keep core tools loaded and defer mainly MCP and plugin tools. MiMo's spec shows the care the details need: its auto mode defers only once MCP definitions exceed 10% of the context window, and the catalog arrives in <system-reminder> deltas so the tool definitions stay byte-stable for the prefix cache.

Why this matters for an agent that writes its own tools

The cmh flavors grow their tool lists, and ROADMAP notes that the agent "cannot change ... how tools are chosen". Today the answer is "all of them, every time". That is the long tail tool search was built for, with three twists.

  • The tools are numerous and narrow. A self-made tool often serves one chore, such as one file format or one project's tests, so most are irrelevant to any given task.
  • The list changes during a run. Each accepted propose_def can add or change a tool mid-conversation. If that rewrites the tool list at the top of the request, it also breaks the prompt cache. MiMo's stable search tool plus catalog deltas fits a self-editing agent well.
  • The agent writes the descriptions. With tool search, the description is how a tool gets found, so a gate could check it: a trial could fail if the tool does not come up when searched for its own task.

Code mode matters for another reason: it changes what a good tool looks like. If the model can write a short program that calls parse_log, filters the result and passes it to summarize_failures, then small tools that compose are worth more than big all-in-one ones. The userspace becomes a library rather than a menu. That is Voyager's idea of skills as code that compose (chapter 1), applied to tools.

Code mode is also a sandboxing decision, the one this book keeps making. Pi's guest code can only call injected functions, just as in the Forth and WASM flavors (chapters 8 and 9) and Roc's platform (chapter 10): the guest computes, and the host decides which effects exist. A cmh flavor with deferred tools and code execution would need few new parts: the registry is already a catalog with names, descriptions and scores, and several flavors have a sandboxed evaluator.

No cmh flavor implements tool search or code mode today. This is a direction suggested by the survey, not a measured result; ROADMAP's tool-reuse suite (experiment 1) would be the place to measure it.

Key takeaways

  • autolith and samizdat are the most complete self-modifiers: both journal every attempt, gate changes and can recover. cmh's gate and three rings come mostly from samizdat.
  • Late binding through names is the shared trick. Holding a function object instead of a name freezes the old code.
  • The strongest designs take judgment away from the model: samizdat's non-compensatory held-out battery and mandatory reflection step, jiti's caller-owned invariants.
  • cmh's clearest next borrowings, such as loop as data and a held-out replay battery, mostly fill gaps ROADMAP already lists.
  • Tool search (deferred tools found by search, usually BM25) and code mode (one tool that runs a sandboxed program calling the others) are now common: Codex, Pi, Hermes, MiMo and (opt-in) Deep Agents have both, and OpenCode has a search function inside its code mode.
  • An agent that keeps writing tools will hit the long tail these mechanisms solve. Code mode also rewards small composable tools and uses the same "only injected capabilities" wall as the WASM-based flavors.
