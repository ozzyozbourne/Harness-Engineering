Harness Engineering · Chapter 8

8. Forth in WebAssembly: a language built for the agent

A tiny late-bound Forth, written for the agent and locked inside Wasmtime, so nothing the agent writes can crash or hang the harness

The four flavors before this one each picked an existing language and asked how far its own machinery could be bent toward self-modification. Clojure brought eval and namespaces. Racket brought sandboxed evaluators. Rust brought compiled libraries loaded at runtime. Lean brought proofs. Each also showed the same weak spot: when the agent's code loops forever, corrupts memory or panics, the harness struggles to stop it, and sometimes cannot.

The fifth flavor, in forth/, comes from the other side. It asks what the agent's language would look like if we built it ourselves, around the harness's needs, inside a wall the host fully controls. The result is a small Forth dialect, about 1,800 lines of Rust, compiled to WebAssembly and run inside the Wasmtime runtime. The kernel stays ordinary Rust on the outside.

A primer on Forth

Forth is a language from around 1970. It is very small, and almost all of it follows from two ideas: a stack and a dictionary of words.

The stack

Most languages pass values to functions through named parameters: add(2, 3). Forth has no parameter lists. Instead there is one shared data stack, a pile of numbers. Writing a number pushes it onto the pile. Writing an operation takes its inputs off the top of the pile and pushes its result. So 2 3 + means: push 2, push 3, then + pops both and pushes 5. This style is called postfix or "reverse Polish" notation.

source: 2 3 + dup * stack: [2] [2 3] [5] [5 5] [25] (top of stack on the right)

Because there are no names for arguments, Forth programmers document each word with a stack effect comment in parentheses: ( a b -- a+b ) means "takes two items, leaves one". Everything before -- is what the word expects on top of the stack, and everything after it is what it leaves. These are just comments, but the VM keeps the stack effect of every built-in word and quotes it back in its error messages.

A handful of words exist only to rearrange the stack: dup copies the top item, drop discards it, swap exchanges the top two, over copies the second item to the top, and nip drops the second item. Strings are not a separate type here. A string is two numbers on the stack, an address in memory and a length, written ( addr len ) or ( a u ).

Words and the dictionary

A Forth "function" is called a word. You define a new one with a colon: : square ( n -- n*n ) dup * ;. The colon starts the definition, square is its name, and the semicolon ends it. After that, square is a word like any built-in one, and 7 square leaves 49.

Every defined word goes into the dictionary, the table that maps names to code. A Forth system is mostly a dictionary plus a loop that reads the next word, looks it up and either runs it or compiles a call to it. That loop has two modes. Outside a definition the system is interpreting: each word runs as soon as it is read. Between : and ; it is compiling: each word is appended to the new definition instead of being run.

Here is the seed tool every fresh harness starts with. It counts words in a text. It is the whole file:

\ Seed tool `word_count`: {"text": string} -> number of whitespace-separated words.
: skip-space ( a u -- a' u' )  begin dup 0> if over c@ bl <= else false then while 1 /string repeat ;
: skip-word  ( a u -- a' u' )  begin dup 0> if over c@ bl >  else false then while 1 /string repeat ;
: count-words ( a u -- n )
  0 >r
  begin skip-space dup 0> while  r> 1+ >r  skip-word  repeat
  2drop r> ;
: run ( json-addr json-len -- out-addr out-len )
  s" text" json-get count-words n>s ;
forth/seed/word_count.fs:1-9

Read it from the bottom. run receives the tool's JSON input as a string ( json-addr json-len ). s" text" pushes the string text, and json-get looks up that key and leaves the value as a string. count-words turns the string into a number, and n>s turns the number back into a string, which is what run must return. count-words keeps its counter on the return stack (>r pushes there, r> pops back), a second stack Forth programmers use as scratch storage. c@ fetches the byte at an address, bl is the code of a space, and 1 /string moves a string one character forward.

Why Forth at all? It is about the smallest language that still lets a program define new words at runtime, so the whole interpreter fits in one readable file. It has almost no syntax to get wrong, and its single stack gives the error reporter one obvious thing to show. The cost is that Forth is unfamiliar to most models, which is why the kernel ships a 71-line dialect reference in the system prompt (forth/host/src/kernel/forth_reference.md).

A primer on WebAssembly and Wasmtime

WebAssembly, usually shortened to WASM, is a portable, low-level bytecode format. Think of it as the instruction set of a virtual CPU. Compilers such as rustc can target it (the target used here is wasm32-unknown-unknown, which means "32-bit WebAssembly, no operating system"). A runtime then runs the bytecode. This project uses Wasmtime 50.0.1, which translates WASM into native machine code with the Cranelift compiler.

The property that matters for us is isolation. A WASM module can read and write only its own linear memory, one flat array of bytes whose maximum size the host can cap. It has no system calls of its own. Anything else it needs (files, clocks, network, or here, "look up a key in this JSON") must be handed in by the host as an import, a function the host implements and the module is allowed to call. In the other direction, the module offers exports that the host calls.

When something goes wrong inside the module (an out-of-bounds memory access, a call stack that grows too deep, running out of an instruction budget), the runtime stops it with a trap. For the host a trap is just an error value returned from the call. The host process does not crash.

Wasmtime adds two ways to stop code that runs too long:

  • Fuel is a counter that goes down as WASM instructions execute. When it reaches zero, the guest traps. It counts work, not time.
  • Epoch interruption is a cheap deadline. A host thread periodically bumps a global "epoch" number, and generated code checks it at loop heads and function entries. When the epoch passes the store's deadline, the guest traps. It measures wall-clock time.
+------------------------------ host process (Rust, cmh) ------------------------------+ | kernel: agent loop, gate, journal, kernel tools, provider | | | | imports it provides: host_word host_take host_pending_len host_known host_panic| | | ^ | | v | | | +----------------- Wasmtime store (fuel, epoch deadline, 64 MB cap) --------------+ | | | Forth VM module (wasm32-unknown-unknown) | | | | linear memory: dictionary, slots, compiled code, data space, strings, stacks | | | | exports: cmh_define cmh_call cmh_resume cmh_where cmh_bind ... | | | +---------------------------------------------------------------------------------+ | +---------------------------------------------------------------------------------------+

Why we built our own small Forth

The commit that added this flavor states the goal in one sentence: "A Rust host runs our own small, late-bound Forth inside Wasmtime with fuel, a memory cap and memory snapshots, so agent code cannot crash or hang the harness and every failure comes back as a structured error." Each part of that sentence is a reason not to embed an existing language.

  • Late binding had to be built in. SPEC.md requires that redefining a tool changes what every existing caller runs on its next call. Here that is the VM's core design, not a hoped-for property of the language.
  • The whole image had to live in linear memory. Then a byte copy of that memory is a complete snapshot, and rolling back is writing the copy back.
  • Errors had to be designed for a model to read. Every failure path can name the word, definition, version, line, token, stack and call chain. A borrowed interpreter would give us whatever messages it already had.

The VM's opening comment states all three:

//! Everything the Forth image consists of lives in this module's linear
//! memory: the dictionary (words, slots, namespaces), compiled code, the data
//! space (`HERE`, `VARIABLE`, string literals), the per-call string scratch
//! space, and the stacks. A copy of linear memory is therefore a complete
//! snapshot of the image; the host uses that for rollback.
//!
//! Late binding: every compiled call goes through a slot (an indirection cell
//! with a name). Redefining a word rebinds its slot, so every existing caller
//! uses the new code on its next call. Public slots are named after userspace
//! definitions; an unbound public slot makes the VM suspend with NEED_LOAD so
//! the host can compile that definition lazily and resume.
//!
//! Errors never panic: they come back to the host as JSON (kind, word, def,
//! version, line, token, data stack, call trace, console output).
forth/vm/src/lib.rs:3-16

The dialect is deliberately ordinary: 64-bit integer cells, case-insensitive words, ( addr len ) strings, the usual stack, arithmetic, memory and control words, plus a string builder (<b b+ bc+ bn+ b>) and six host words for JSON, files and lessons. There is no floating point. The contract for every tool and hook is the one line the reference puts first: : run ( json-addr json-len -- out-addr out-len ) ... ;.

The VM

What lives where

All VM state is held in Rust static mut variables, which the compiler places in linear memory. There is a 1 MB permanent data space (for HERE, variable, create and string literals) and a 2 MB string scratch space that is reset for every call. Stack limits are fixed constants:

Compiled code is a vector of small instructions, not native code. The VM walks it with an explicit instruction pointer:

Prim runs one of 83 built-in primitives. Each primitive is listed in a table together with how many stack items it needs and its stack-effect string, and the error messages reuse that table. Lit pushes a number. Branch and ZBranch (branch if zero) implement if and the loops. Call is where the interesting part starts.

Slots: late binding in one indirection

A compiled call never points straight at a word's code. It points at a slot, a small named cell that holds "which word does this name mean right now":

    name: String,
    target: Option<u32>,

Rebinding the slot changes every caller at once, because they all go through it. This is the SPEC's "late binding" requirement, done with one pointer. When the agent proposes word_count v2, the VM compiles the new code and points the word_count slot at it. A tool written earlier as : run word_count s" !" concat ; uses v2 on its next call without being recompiled. When the gate reverts v2, the slot is pointed back at v1, or left empty.

caller tool slot "word_count" definitions : run word_count ... ; +-----------------+ Op::Call(slot) --------> | target ---------+-------> word_count v1 `run` | version: 1 | (x) word_count v2 `run` (after a revert) +-----------------+ propose v2: target -> v2 revert v2: target -> v1 no live version: target = None

The None branch is what an empty slot does: instead of failing, it suspends the VM with a request for the host, "I need this definition". That is lazy loading, covered below.

Namespaces: two tools can both have a helper called skip

Each version of each definition gets its own private namespace, named "def/version" (for example word_count/2). Helper words defined in a source, like skip-space and count-words above, live in private slots in that namespace. Only the definition's run word is bound to the public slot named after the definition. When the compiler meets a name, one function decides what it means:

    /// What `tok` (lowercased) means in namespace `ns`: a private word first,
    /// then a primitive, then a public (userspace) slot that already exists.
    fn resolve(&self, ns: &str, tok: &str) -> Option<Op> {
        if let Some(slot) = self.privs[ns].get(tok) {
            return Some(Op::Call(*slot));
        }
        if let Some((p, _, _)) = prim(tok) {
            return Some(Op::Prim(p));
        }
        self.public.get(tok).map(|slot| Op::Call(*slot))
    }
forth/vm/src/lib.rs:540-550

Private words come first, so a definition's own helper may even shadow a primitive of the same name. Two tools can each define skip without clashing. A name that matches neither a helper nor a primitive is looked up as another tool, so tools can call each other by name.

Compile versus interpret

The compiler walks the source token by token, in the two modes from the primer. Outside : ... ;, tokens are interpreted: numbers go onto a load-time stack, :, variable, constant and create define names, and any other word runs right away through a temporary two-instruction stub that is removed afterwards. Inside a definition, tokens are compiled. Control words such as if, begin and do emit branches and patch their targets later, using a small control stack. Everything else becomes a literal or a call:

    fn compile_word(&mut self, u: &mut Unit, tk: &Token) {
        let op = if let Ok(v) = tk.t.parse::<i64>() {
            Op::Lit(v)
        } else if let Some(op) = self.resolve(&u.ns, &tk.t) {
            op
        } else if unsafe { host_known(tk.t.as_ptr() as usize as i32, tk.t.len() as i32) } == 1 {
            Op::Call(self.public_slot(&tk.t))
        } else {
            let slot = self.private_slot(&u.ns, &tk.t);
            u.forwards.push(Forward { slot, line: tk.line, token: tk.raw.clone() });
            Op::Call(slot)
        };
        self.emit(op, tk.line, &tk.raw);
    }
forth/vm/src/lib.rs:1530-1543

The four cases are, in order: a number; a known helper, primitive or already-loaded tool; a live userspace definition the VM has not compiled yet (the VM asks the host with the host_known import, and binds the call to an empty public slot that will be filled on first use); and otherwise a forward reference, a helper that must be defined later in the same source. When the source ends, the VM checks that no : was left open, that every forward reference got defined (otherwise undefined word, with a "did you mean" suggestion based on edit distance), that top-level code left nothing on the stack, and that a run word exists. Only then is the version recorded and the public slot bound.

Lazy loading

When a process starts, it compiles only the seed definitions. Everything else the agent has built stays in the journal as source text until something calls it. A call into an empty public slot suspends the VM with status ST_NEED and the slot's name. The host looks the name up among live definitions, compiles that source into the same VM, and resumes:

Resuming with 0 means "no such definition", and the VM turns that into an undefined-word report. Each lazy load is printed on stderr as, for example, [forth] lazy-load reverse v1. The test forth_lazy_load_in_fresh_process checks this path.

The ABI: one file both sides compile

An ABI (application binary interface) is the set of low-level conventions two pieces of compiled code agree on: which numbers mean what, and how arguments are laid out. Because the host and the VM are compiled separately, for different targets, these numbers could easily drift apart. The fix is to compile one file into both. The VM says mod abi; and the host says #[path = "../../../vm/src/abi.rs"] mod abi;.

/// Status of `cmh_define`, `cmh_call` and `cmh_resume`: done, output is the result.
pub const ST_OK: i32 = 0;
/// Failed; the output is a JSON error report.
pub const ST_ERR: i32 = 1;
/// Suspended on an unbound public slot; the output is its name. The host
/// compiles it (or not) and calls `cmh_resume`.
pub const ST_NEED: i32 = 2;

/// Returned by `host_word` when the host word failed; the error message is pending.
pub const HOST_ERR: i64 = i64::MIN;

/// Host word op codes passed to `host_word`.
pub const OP_JSON_GET: i32 = 1;
pub const OP_JSON_LEN: i32 = 2;
pub const OP_JSON_STR: i32 = 3;
pub const OP_FILE_READ: i32 = 4;
pub const OP_FILE_WRITE: i32 = 5;
pub const OP_REMEMBER: i32 = 6;
forth/vm/src/abi.rs:7-24

WASM functions can pass only numbers, so strings travel through memory. To call the VM, the host first asks it for a "mailbox" of N bytes (cmh_mailbox), writes the arguments into it back to back, and then calls the export with only their lengths. Results come back through cmh_out_ptr and cmh_out_len. In the other direction, a host word that returns a string first returns only its length. The VM allocates that much scratch space and calls host_take(addr) to have the host copy the bytes in. This two-phase dance means the host never writes into memory the VM did not allocate itself.

The VM's exports are cmh_init, cmh_mailbox, cmh_out_ptr, cmh_out_len, cmh_define, cmh_call, cmh_resume, cmh_bind, cmh_unbind, cmh_bound, cmh_where and cmh_stats. Its imports, all in a module named "cmh", are host_word, host_take, host_pending_len, host_known and host_panic. Through host_word the VM gets six host words, its entire view of the outside world. json-get, json-len and json-str work on JSON strings. file-read (capped at 1 MB) and file-write are limited to the working directory: they refuse .., the state directory, the host crate and base-prompt.md. remember records a lesson, at most 10 per entry. There is no network.

The Wasmtime wall

Most of the other flavors share one hard problem: once agent code is running inside the host process, stopping it is up to the language. In ROADMAP.md's comparison table, Clojure, Rust and Lean all answer "no" to "runaway loop is actually stopped", because the thread running the loop keeps going after the harness gives up on it. Forth answers "yes (fuel)" and, to "agent code can crash the harness", "no (WASM wall)". Racket is the only other flavor in that table with the same two answers, thanks to its sandbox.

Fuel is the main guard and the wall clock is a backstop. Time spent in host words burns no WASM fuel but does count toward the deadline. Wasmtime's docs note that epochs only affect running WASM code, though, so a single slow host call is not cut short: the trap comes once control is back in WASM. Memory is capped with Wasmtime's ResourceLimiter hook, which the runtime asks before growing memory. Refusing growth also sets a flag, so the report can say memory-limit instead of a vaguer failure:

            return Ok(false);
        }
        Ok(true)
    }
    fn table_growing(&mut self, _current: usize, desired: usize, _maximum: Option<usize>) -> wasmtime::Result<bool> {

Snapshots and restore

Since the entire image lives in linear memory, a snapshot is a byte copy, and restore means starting a fresh instance and writing the copy back:

    pub fn snapshot(&self) -> Snapshot {
        Snapshot(self.mem.data(&self.store).to_vec())
    }

    /// Replaces this instance with a fresh one whose linear memory is the
    /// snapshot. Globals (the shadow stack pointer) start at their initial
    /// values, which are the values between top-level calls.
    pub fn restore(&mut self, snap: &Snapshot) -> Result<(), String> {
        let h = self.store.data();
        let mut fresh = Self::instantiate(self.limits.clone(), h.work_dir.clone(), h.protected.clone())?;
        let cur = fresh.mem.data_size(&fresh.store);
        if snap.0.len() > cur {
            let pages = (snap.0.len() - cur).div_ceil(65536) as u64;
            fresh.mem.grow(&mut fresh.store, pages).map_err(|e| format!("restore: grow memory: {e:?}"))?;
        }
        fresh.mem.data_mut(&mut fresh.store)[..snap.0.len()].copy_from_slice(&snap.0);
        *self = fresh;
        Ok(())
    }

If the restore itself fails, the kernel builds a fresh VM with the seeds compiled. The test forth_out_of_bounds_trap_restores_snapshot writes over data space and then stores to address 4000000000, far past the end of memory, and asserts that the VM's statistics afterwards are identical to before.

The restore relies on one quiet assumption, spelled out in the doc comment above: WASM globals, notably the shadow stack pointer that rustc's generated code uses, are back at their initial values between top-level calls. A fresh instance starts them there, so writing the memory back is enough. That holds for the code rustc emits today, but no document guarantees it.

The remaining cases are timeout, wasm-out-of-bounds, wasm-stack-overflow, vm-panic (with the panic message, captured by a hook the VM installs at startup), wasm-trap and wasm-error. Then comes the useful trick. The host gives the trapped instance a small fresh budget (20 million fuel, 1 second) and calls its cmh_where export to ask where it was. This works because the VM writes its instruction pointer, current token and current word with volatile writes, which the compiler may not delay or optimize away:

So a trap is reported exactly like an ordinary Forth error, with word, line and stack. If even cmh_where fails, the report falls back to the kind and message. Errors the VM detects itself (stack-underflow, stack-overflow, return-stack-overflow, undefined-word, division-by-zero, bad-address, compile-error, contract, host-error, string-space, data-space, builder, vm-error) come back as JSON with status ST_ERR. The host formats both kinds of failure the same way and adds a hint written for each kind.

The shape is: forth error [kind] in word W of DEF vN, line L, at TOKEN:, then the message, the data stack, the call chain, the top two stack items read as a string, any console output printed before the error, the input and the hint.

Real reports

A typo.

There is no "did you mean" here, because nothing within edit distance 2 of revrese existed in that VM. The kind is compile-error, because the name was caught at compile time. The runtime kind undefined-word appears only when a lazy load finds no live definition.

Reports like these show up in real eval runs too. One local eval log shows the model hitting [bad-address] in word `fq` of scratchpad v1, line 8, at `c@` and later [fuel-exhausted] in word `fmt-csv` of scratchpad v1, line 20, at `@`, both while experimenting in the scratchpad, not in live tools.

The forth_eval scratchpad

In the four earlier flavors, the only way for the agent to try new userspace code inside the harness is to propose it as a definition. That makes each experiment a journaled proposal, and a rejected proposal is a visible failure in the record. The Forth flavor adds one kernel tool that runs code without proposing it:

    /// Scratchpad: compiles and runs a snippet in a throwaway VM. Nothing is
    /// journaled, so experiments do not count as proposals.
    fn forth_eval(&self, input: &Value) -> Result<String, String> {
        let source = str_field(input, "source");
        if source.trim().is_empty() {
            return Err("source is empty".into());
        }
        let arg = input.get("input").filter(|v| v.is_object()).cloned().unwrap_or_else(|| json!({}));
        let code = live_code(&self.state);
        let mut vm = self.new_vm()?;
        vm.define("scratchpad", 1, &source, &code).map_err(|e| format!("compile failed:\n{e}"))?;
        let out = vm.call("scratchpad", arg.to_string().as_bytes(), &code);
        out.result.map(|o| format!("output: {}", tools::truncate(&o, 20 * 1024)))
    }
forth/host/src/kernel/mod.rs:301-314

The snippet is compiled as scratchpad v1 in a fresh VM, and the result is either output: ... or the same structured report the gate would give. The source has to follow the same run contract as propose_def, "so working code can be proposed unchanged", as the tool description puts it. Live userspace words can be called from the snippet. The test forth_eval_scratchpad_runs_code_without_proposing checks that the journal gets no def_proposed or def_rejected events.

"Throwaway" covers the VM, not the world. The tool description says it plainly: "Host words with side effects (file-write) still act on the working directory." A scratchpad snippet that writes a file really writes it. Lessons recorded with remember inside a scratchpad are dropped, because forth_eval ignores them (an inference from the code, not a tested behavior).

The measured effect

The eval suite (chapter 11) was run twice on this flavor with DeepSeek V4.1 Flash, 15 suites with 2 trials each, both on 2026-10-29: one of the flavor "before the forth_eval scratchpad tool", as its results file puts it, and one with the tool. Each run also ran Prime Agent, the reference harness, as the baseline.

The clearest effect is on tokens: they fell from about 7.8 million to about 3.7 million, less than half, with the same pass rate. ROADMAP.md adds that the scratchpad "cut that flavor's rejected proposals from 69 to 0 and its tokens from 7.8M to 3.7M". In the newer local eval logs, models called forth_eval 692 times and propose_def only 32 times across 128 Forth episodes, and only 3 of those proposals were rejected. Given the choice, models try code roughly 20 times for every time they commit it.

Read these numbers with care.
  • The headline "114% vs Prime" is mostly Prime getting worse, not Forth getting better. Forth scored 100% in both runs. Prime dropped from 98% to 88% between them. Two trials per suite is a small sample, and the same model gave the baseline a 10-point swing.
  • The scratchpad made episodes slower, not faster: the median rose from 22.1 s to 29.5 s.
  • The "69 to 0 rejected proposals" figure appears only in ROADMAP.md. The results files have no rejection column, and both say "Raw logs are not kept in git", so it cannot be checked from the repository.
  • The scratchpad run "was interrupted once by an out-of-memory kill of the whole service (traced to a 5.5 GB process started inside an episode)" and resumed, with interrupted episodes rerun. The file does not say whether a Forth or a Prime episode started it.
  • The 692-vs-32 counts come from gitignored local logs that no results file describes. They show how the tool gets used, not a published result.

With those caveats, the lesson holds: a cheap place to try code changes how the agent works. It debugs in private and proposes only what already runs. When ROADMAP.md was written, no other flavor had such a tool, and it lists adding one elsewhere as a gap. The later WASM and Roc flavors both have one (forth_eval and roc_eval).

The host depends on wasmtime 50.0.1 (only the cranelift, runtime and std features, no component model), serde, serde_json and ureq for HTTP. The VM has no dependencies at all.

The kernel follows SPEC.md like the other flavors. It has 10 kernel tools: bash, read_file, write_file, list_defs, show_def, forth_eval, propose_def, rollback_def, remember and recall. The system prompt has three blocks: the immutable base-prompt.md, the Forth reference, and the supplemental prompt that the agent's own compose_system hook builds. The system prompt is recomposed on every turn, up to 40 turns per task. Both hooks are themselves Forth: the seed select_lessons.fs implements the SPEC's default lesson selection in 69 lines of Forth.

The gate

The gate is SPEC.md's path for every change: validate, trial, soak, then keep or revert. This flavor adds one twist at each step: a fresh WASM instance.

propose_def | v validate: name [a-z][a-z0-9_]* (max 48), not a kernel tool, kind tool/note/hook, kind unchanged across versions, schema + tests present | v brand-new wasm instance: compile source, run every test (expect = substring of output) | fail -> def_rejected (structured report back to the model) v compile into the LIVE vm as trial (an older soaking trial is reverted as "superseded") | v soak: every call journals def_use; snapshot before each call | | | 3 clean uses (default soak) | any error while in trial v v def_kept restore snapshot, def_reverted, slot -> last kept version (or unbound)

Validation compiles and tests the source in a brand-new instance with its own store and fuel, so a broken proposal never touches the live image. The trace line looks like [gate] scratch vm: house_fmt v1 compiled, 10 test(s) passed in 0 ms. A select_lessons hook's output must also parse as a JSON array of integers.

The test forth_infinite_loop_stopped_by_fuel shows the whole loop working against the hardest failure. It proposes a word_count v2 that spins forever when the text is spin:

The trial passes its own test, then hangs on a real input. Fuel stops it within the test's ten-second bound, the report names spin in word_count v2, the slot goes back to v1, a verdict mentioning fuel-exhausted is recorded, and the very next call works. This is the test the Clojure, Rust and Lean flavors cannot pass in this form.

Verdicts (the text def NAME vN ("desc") reverted: <first error line> on input {...} or its "kept" counterpart) are shown to the model: the last 20 are appended to the supplemental prompt, bypassing select_lessons. rollback_def re-proposes an old version's source as a new trial version through the same gate.

The journal

The journal is SPEC.md's append-only journal.jsonl (chapter 2). When it is empty, the three seeds are installed as def_trial plus def_kept v1 events marked "seed": true, which produce no verdict.

The journal holds source text, not compiled code. No Forth image is ever written to disk. Each process rebuilds its image from the journal: seeds eagerly, everything else lazily through the ST_NEED path. This keeps the journal the single source of truth, at the cost of recompiling on first use.

Limitations

  • bash is outside the wall. The WASM sandbox holds the agent's Forth, but the bash kernel tool runs commands directly in the working directory with no filesystem sandbox. write_file refuses the kernel and the journal, but bash can edit anything. In ROADMAP.md's chess terms, "the agent can flip the board". The next chapter's flavor closes this gap with a namespaced sandbox.
  • Old versions leak. Every compiled version stays in the live VM's code and data space until the process exits. cmh_stats exposes how much data space is used and how many words exist, but nothing reclaims it.
  • A small language. No floating point, and lower and trim handle only ASCII. json-get re-parses the whole JSON string on every access, which likely makes repeated lookups slow on large inputs.
  • Limits are fixed. The per-entry fuel and time budgets are not configurable from the CLI, and they also bound the gate's test runs, so a tool that needs more cannot pass.
  • Snapshots copy everything. The whole linear memory (at least the 3 MB of static buffers plus the heap) is copied before every call, including the hook calls on every turn. That is probably cheap at today's sizes (not measured), but the cost grows with memory.
  • The gate's limits are shared with every flavor. It checks only the agent's own tests, it keeps a change after it survives 3 uses without crashing, which is not proof that it works, and task success is self-reported.

Key takeaways

  • Building our own language let us design three properties into the VM: late binding through slots, an image entirely in linear memory, and errors written for a model to read.
  • WebAssembly makes the wall real: fuel stops infinite loops, an epoch deadline caps wall time, a resource limiter caps memory, and every trap comes back as an ordinary error. In ROADMAP.md's table only this flavor and Racket both stop runaway loops and keep agent code from crashing the harness.
  • Because the image is just bytes, rollback is a memory copy: snapshot before every call, restore after a trap or a failing trial.
  • Asking the trapped VM "where were you?" turns a bare trap into a report with word, version, line, token, stack, caller, input and a hint.
  • The forth_eval scratchpad halved token use (7.8M to 3.7M) at the same pass rate and is used far more than propose_def. The "114% vs Prime" headline mostly reflects the baseline's drop, and episodes got slower.
  • The wall covers Forth, not bash. Closing that hole, and letting the agent change the kernel itself, is the subject of the next chapter.
