Harness Engineering · Chapter 2

2. The shared design: SPEC.md

One 192-line contract that every flavor implements: three rings, a gate, a journal, and eight tests

Every harness in this repository is called cmh, short for "continual, self-modifying harness". They are written in very different languages: Clojure, Racket, Rust, Lean, a home-made Forth inside WebAssembly, a whole harness compiled to WebAssembly, and Roc. But they all do the same job in the same way, because they all implement one document: SPEC.md at the repository root. This chapter walks through that document section by section. The later chapters can then concentrate on what is different about each language, because you will already know what is the same.

The spec opens with the whole idea in two clauses:

Each is a coding agent that (1) rewrites parts of itself while it runs and
(2) learns across runs, keeping only the changes and lessons that hold up.
SPEC.md:4-5

"Rewrites parts of itself while it runs" is the self-modification half. "Learns across runs" is the continual-learning half. "Keeping only the changes and lessons that hold up" is the selection mechanism that ties them together, and it is where most of the design effort goes.

The documents drift on one number. SPEC.md:3 says "One design, four implementations: clojure/, rust/, racket/, lean/." That was true when the spec was written on 29 October 2026. The repository now has seven flavors plus a Roc prototype; the Forth, WASM and Roc flavors were added later and follow the same spec, but the spec was never renumbered. Where this chapter says "every flavor", it means all seven.

The spec credits its ideas to earlier harnesses (SPEC.md:7-11): samizdat for the immutable kernel and the validate/soak/rollback gate, Prime Agent for versioned prompt notes and lessons on top of an immutable base prompt, and autolith and oh-my-lisp for live redefinition. Chapter 3 covers Prime Agent; chapter 12 covers the rest.

Three rings

The first design decision is to split the harness into three parts with different rules about who may change them. The spec calls them rings, borrowing the operating-system idea of privilege rings (the kernel runs with more rights than user programs).

1. **Kernel** (host code, immutable to the agent): model client, agent loop,
   journal, gate, evaluator, kernel tools. The agent can read it but no kernel
   tool writes it.
2. **Userspace** (mutable, versioned): named definitions written in the
   flavor's eval language. The kernel resolves every userspace definition **by
   name at call time** (late binding), so a newly installed version takes effect
   on the very next call without a restart.
3. **Knowledge** (durable): lessons and verdicts that carry across runs and are
   scored by outcome.
SPEC.md:15-23
+------------------------------------------------------------+ | KERNEL (host code; the agent may read it, never write it) | | model client · agent loop · gate · evaluator · journal | | kernel tools: bash read_file write_file list_defs ... | | | | +----------------------------------------------------+ | | | USERSPACE (versioned definitions, agent-written) | | | | tools e.g. word_count | | | | notes plain text for the prompt | | | | hooks compose_system, select_lessons | | | +----------------------------------------------------+ | | | | +----------------------------------------------------+ | | | KNOWLEDGE (survives across runs) | | | | lessons scored +1 / -1 by task outcome | | | | verdicts what the gate decided, and why | | | +----------------------------------------------------+ | +------------------------------------------------------------+ everything above is rebuilt from journal.jsonl

Late binding, in plain words

"Late binding" means the program decides which function to run at the moment it calls it, not earlier. A cmh kernel never keeps a direct pointer to, say, the word_count tool. Each time the model calls word_count, the kernel asks its registry "which version of word_count is live right now?" and runs that one. So installing version 2 needs no restart and no reload step: the next lookup simply finds version 2. This one property is what makes "rewrite yourself while running" cheap. The Clojure kernel's call-live (clojure/src/cmh/kernel/gate.clj:111-123) does exactly this: look up the live record, call it, record the use.

The spec's table of how code becomes live lists only the first four flavors, but it shows how far apart "late binding" can be in practice:

FlavorHow code becomes live at runtime (SPEC.md:25-30)
Clojureload-string/eval into a dedicated namespace; vars resolved by name per call
Racketeval in a sandboxed namespace (racket/sandbox, time and memory limits)
Rusteach version is compiled by cargo into a cdylib and hot-loaded with libloading; the Rust compiler is part of the gate
Leansource is elaborated in-process (Lean.Elab frontend) and evaluated with evalConst; any theorems in the source must type-check, so proofs are part of the gate

(A cdylib is a Rust shared library that a running program can load; elaborating Lean source means type-checking it into definitions. Each flavor chapter explains its own mechanism.)

Userspace definitions

Userspace is a set of named, versioned records, each with a name, kind, version, source, description, tests and a status of trial, kept, reverted or rejected (SPEC.md:34-35).

Versions are never overwritten; the registry just remembers which one is live. There are three kinds.

Tools

A tool is exposed to the model under its name, with an input_schema. "Contract: takes one JSON object (the tool input), returns a string" (SPEC.md:38-42); each flavor fixes the exact function signature. To the model it looks exactly like a built-in tool. (Roc bends the contract: a tool gets its input as JSON text and may return requests, such as reading a file, that the host performs before the tool returns its string; chapter 10.)

Notes

- **`note`**: prompt note. `source` is plain text, appended to the supplemental
  system prompt. No evaluation, but still versioned and soaked.
SPEC.md:43-44

A note is a standing instruction the agent writes to itself. It is not code, but it still goes through the gate.

Hooks

- **`hook`**: kernel extension points the kernel calls by these fixed names:
  - `compose_system(notes: [string], lessons: [string]) -> string`: builds the
    *supplemental* system prompt. The kernel always prepends the immutable base
    prompt itself, so a hook cannot remove it.
  - `select_lessons(task: string, lessons: [{id, text, score}]) -> [id]`:
    picks which lessons go into the prompt for this task.
SPEC.md:45-50

Hooks let the agent change kernel behavior in two narrow places: how the prompt is assembled and which lessons are shown.

The seed userspace

A brand-new harness is not empty. On first start each flavor installs a small seed:

Seed userspace, shipped as source files in each flavor and installed as
`kept` version 1 when the journal is empty: both hooks with their default
behavior (`compose_system` joins notes under a "Notes" heading and lessons
under "Lessons"; `select_lessons` returns the 8 highest-scored lessons that
share at least one word of 4+ letters with the task, else the top 3 by score),
and one example tool, `word_count` (`{"text": string}` -> count as a string).
SPEC.md:52-57

The seed word_count tool is a good way to see the flavors side by side, since it does the same trivial thing in every language. In Clojure the tool is a function named run that takes the input map:

;; Tool: (run input) -> string, input is a keyword-keyed map.
(defn run [input]
  (str (count (re-seq #"\S+" (str (:text input))))))
clojure/seed/word_count.clj:1-3

In Lean the seed also carries a theorem, a small machine-checked proof that the counter returns 0 for the empty string. If the agent proposes a version whose theorem does not check, the gate rejects it:

/-- Number of maximal runs of non-whitespace characters. -/
def countWords (s : String) : Nat :=
  (s.toList.foldl (fun (acc : Nat × Bool) c =>
    if c.isWhitespace then (acc.1, false)
    else if acc.2 then acc else (acc.1 + 1, true)) (0, false)).1

theorem countWords_empty : countWords "" = 0 := rfl

def run (input : Lean.Json) : IO String := do
  let text := (input.getObjValAs? String "text").toOption.getD ""
  pure (toString (countWords text))
lean/userspace/word_count.lean:1-11

The seeds carry their own tests in the same JSON format the agent must use, for example {"input": {"text": ""}, "expect": "0"} (lean/userspace/seeds.json:18).

The gate: validate, trial, soak, keep or revert

This is the heart of the design. The spec states the rule in one line:

`propose_def` is the only way userspace changes.
SPEC.md:61

The agent submits source and tests; the kernel decides. Here is the lifecycle of one proposal:

propose_def(name, kind, source, description, tests) | v +-------------------------------------------+ | 1. VALIDATE in a scratch environment | | compiles / evaluates? | | entry point has the right shape? | | every test's "expect" is a substring | | of the output? | +-------------------------------------------+ | no | yes v v +--------------+ +----------------------------------+ | REJECTED | | 2. TRIAL new version is live | | live version| | now; previous version kept | | unchanged; | | in reserve | | model gets | +----------------------------------+ | the error | | +--------------+ v +----------------------------------+ | 3. SOAK count the next N uses | | (default N = 3) | +----------------------------------+ | | any error (exception, panic, N clean uses timeout, bad return type) | v v +-------------------+ +-------------------+ | REVERTED | | KEPT | | previous kept | | becomes the new | | version is live | | stable version | | again (or the def | | | | is removed) | | | +-------------------+ +-------------------+ \ / v v +---------------------------------------------+ | 4. VERDICT written to knowledge, always | | shown to the model in later prompts | +---------------------------------------------+

1. Validate

1. **Validate** in a scratch environment, never the live one: the source
   compiles/evaluates, defines the required entry point with the right shape,
   and every test passes. Tests are JSON: `[{"input": {...}, "expect": "..."}]`
   where `expect` must be a substring of the output (hooks get their arguments
   as `input`; for `select_lessons` compare the JSON-encoded result). Tools
   and hooks need at least one test. On failure the proposal is `rejected`, the
   live version is unchanged, and the model gets the error text.
SPEC.md:63-69

The scratch environment is throwaway (a temporary Clojure namespace, a fresh Racket sandbox, a new WebAssembly instance), so code that does not compile never touches the live harness. The loose substring test format works in every language.

2. Trial

2. **Trial**: the new version goes live immediately with status `trial`. The
   previous live version is retained.
SPEC.md:70-71

Passing its own tests earns a version a trial, not trust. Going live at once is what lets the agent write a tool and use it in the same task.

3. Soak

3. **Soak**: the next `soak` uses (default 3; a hook use is one invocation by
   the kernel) are counted. Any error (exception, panic, timeout, bad return
   type) during soak reverts immediately to the previous kept version (or
   removes the definition if there was none) with status `reverted`. After
   `soak` clean uses the version becomes `kept`. Notes soak over tasks: a task
   that ends in an error counts as an error.
SPEC.md:72-77

"Soak" is a hardware term: leave a new machine running and see whether it fails. The Clojure kernel counts after each call:

(defn record-use!
  "Journal one use and run soak accounting for trial versions."
  [k {:keys [name version status] :as rec} ok error input-desc]
  (st/emit! k {:type "def_use" :name name :version version :ok ok :error error})
  (when (= "trial" status)
    (if-not ok
      (revert! k rec error input-desc)
      (let [uses (get-in @(:state k) [:defs name :uses] 0)]
        (when (>= uses (:soak k)) (keep! k rec uses))))))
clojure/src/cmh/kernel/gate.clj:101-109

Every use is journaled first, which is what lets a restarted harness resume a half-finished soak.

4. Inherit the verdict

4. **Inherit the verdict**: every keep or revert writes a knowledge entry,
   e.g. `def word_count v2 ("counts unicode words") reverted: ArithmeticException
   on input {...}`. Verdicts are always shown to the model (they bypass
   `select_lessons`), so it does not retry a failed idea blindly.
SPEC.md:78-81

A verdict is the gate's decision as one line of text: the agent's memory of its own self-edits. Because verdicts skip the selection hook, a broken select_lessons cannot hide its own failure.

After the gate

Runtime errors from a `kept` definition are returned to the model as tool
errors but do not trigger revert. `rollback_def(name, version)` reinstalls an
older version as a new `trial` version (new version number, same source).
SPEC.md:83-85

So a kept version stays kept, and rollback never rewrites history: rolling word_count v4 back to v2 creates v5 with v2's source, which soaks again.

What "keeps only the changes that help" really means today. The gate keeps a change when it did not error during its next three uses. It does not check that the change made the agent better: faster, cheaper or more often correct. ROADMAP.md lists this as an open gap ("changes are kept for not crashing, not for helping") and also notes that the gate only runs the agent's own tests, and an agent can write a test that agrees with a wrong implementation. Chapter 13 comes back to this.

Continual learning: lessons, reflection, scoring

Code is one way the agent improves; text is the other. The knowledge ring holds lessons, short free-text insights with a score.

- **Lessons**: free-text entries in knowledge with an integer `score`
  (starts 0). Created by the model through `remember`, and by reflection.
- **Reflection**: after each task finishes, the kernel makes one extra model
  call (no tools) with a compact transcript and asks for a JSON array of 0 to 3
  short, reusable lessons. Lessons are added unless they duplicate an existing
  lesson's text. Reflection can be disabled with `--no-reflect`.
- **Scoring**: each lesson that was in the prompt for a task gets +1 if the task
  succeeded and -1 if it failed. A task succeeds when the model ends with
  `end_turn` and the task had no kernel errors and no tool errors in its final
  2 tool results. Lessons at score <= -3 are retired (excluded from
  selection, still in the journal).
SPEC.md:89-99

Reflection is the kernel asking the model, after the task, "what did you learn?". end_turn is the API's signal that the model stopped on its own. The credit is crude: every lesson in the prompt gets the same +1 or -1 whether or not it mattered, which the ROADMAP lists as a gap.

There is also a deliberate "improve yourself" mode, /refine or cmh refine: a normal task with a fixed prompt to review recent outcomes, verdicts and userspace, "making at most 3 changes and preferring small ones" (SPEC.md:100-103).

How the prompt is assembled, and where the hooks sit

Put the pieces together and you get the path from the stored state to the system prompt the model sees on each request:

task text live lessons (not retired) | | +----------+----------+ v select_lessons(task, lessons) <-- hook: one "use" for soak | ids v live notes + selected lesson texts | v compose_system(notes, lessons) <-- hook: one "use" for soak | supplemental text v +---------------------------------------------------------+ | system block 1: base-prompt.md (added by the kernel)| | system block 2: supplemental text | | + "Verdicts on past userspace changes" | | (added by the kernel, skips the hooks)| +---------------------------------------------------------+ tools: kernel tools + live userspace tools (rebuilt per request)

The Clojure kernel builds the two blocks like this. Notice that the base prompt is put in place by the kernel, outside any hook, and the verdicts are appended after the hook's output:

(defn supplemental [k errors lesson-ids]
  (let [s @(:state k)
        notes (mapv :source (st/live-defs s "note"))
        lessons (vec (keep #(some-> (get-in s [:knowledge %]) :text) lesson-ids))
        composed (call-hook k errors "compose_system" {:notes notes :lessons lessons}
                            (str "(" (count notes) " notes, " (count lessons) " lessons)")
                            #(str/join "\n\n" (concat notes lessons)))
        verdicts (take-last 20 (st/verdicts s))]
    (str/trim
     (str composed
          (when (seq verdicts)
            (str "\n\n## Verdicts on past userspace changes\n"
                 (bullets :text verdicts)))))))

(defn system-blocks [k errors lesson-ids]
  (let [sup (supplemental k errors lesson-ids)]
    (cond-> [{:type "text" :text (:base-prompt k)}]
      (not (str/blank? sup)) (conj {:type "text" :text sup}))))
clojure/src/cmh/kernel/agent.clj:92-109

This is why it is safe to let the agent rewrite its prompt builder: a bad compose_system can only produce a bad supplement, never delete the base prompt, and a hook that throws is reverted during soak. (Clojure also passes a fallback, the last argument to call-hook, so a failing hook degrades to a plain join.)

Kernel tools

The kernel tools are always present and cannot be redefined. They are the fixed instruction set the agent builds everything else from:

ToolInputEffect (SPEC.md:107-117)
bashcommand, optional timeout_s (default 60)runs in the working directory, returns combined stdout/stderr and exit code, truncated to 20 KB
read_filepathfile contents, truncated to 50 KB
write_filepath, contentwrites the file. Refuses paths inside the state dir or the harness's own kernel source directory
list_defsnonename, kind, live version, status, description for every definition
show_defname, optional versionthat version's full record including source and tests
propose_defname, kind, source, description, tests, input_schema (tools only)runs the gate, returns the verdict
rollback_defname, versionreinstalls an old version as a new trial
remembertextadds a lesson
recallquerylessons and verdicts whose text shares words with the query, highest score first
Userspace tools are added to the tool list on every model request, rebuilt
from the live registry each time.
SPEC.md:119-120

That is late binding for the tool list.

bash is a hole in the wall. write_file refuses the state directory and the kernel source, but bash can run any command, including one that edits those same files. The ROADMAP puts it bluntly: "In chess terms, the agent can flip the board." The spec does not close this gap. Only the WASM flavor does, by running bash in a mount namespace where the state dir, wasm/ and base-prompt.md are read-only (when user namespaces are available). Roc checks its tools' file requests on the host side, but its README admits that Bash "can break every rule, as in the other flavors". The eval suite hit the same problem: until per-episode isolation was added, agents could read other episodes' files and the checkers under evals/.

Later flavors add kernel tools that the spec does not mention: forth_eval (forth, wasm) and roc_eval (roc) are scratchpads that run code without proposing it, and the wasm flavor adds propose_kernel and list_images for replacing the kernel itself.

The journal and replay

Where does all this state live? In exactly one file:

State dir, default `.cmh/` in the working directory, overridable with
`--state DIR`. The single source of truth is `journal.jsonl`, an append-only
log of one JSON object per line, each with `type` and `ts` (ISO-8601). Event
types: `def_proposed`, `def_rejected`, `def_trial`, `def_use` (name, version,
ok, error), `def_kept`, `def_reverted`, `lesson_added`, `lesson_scored`,
`lesson_retired`, `task_started`, `task_finished` (success flag). On startup
the kernel replays the journal to rebuild the registry (including soak
counters of trial versions), and the knowledge. Replay must reproduce the
same state that the process had; never rewrite earlier lines. The Rust
flavor may also cache build artifacts in the state dir; the Lean flavor may
cache elaborated environments. Caches must be rebuildable from the journal.
SPEC.md:124-134

This pattern is event sourcing: store what happened, not the current state, and compute the state by replaying the events. Compiled Rust libraries, Racket sandboxes, Lean closures and Forth snapshots are all caches that can be rebuilt.

journal.jsonl (append-only, one event per line) ------------------------------------------------------------ def_proposed word_count v1 \ def_kept word_count v1 | seed install ... / task_started "count the words..." def_proposed word_count v2 def_trial word_count v2 live = v2, uses = 0 def_use word_count v2 ok uses = 1 def_use word_count v2 ok uses = 2 task_finished success <-- process stops here ------------------------------------------------------------ | fresh process: read every line, fold in order v empty state --apply--> s1 --apply--> s2 ... --apply--> sN | v registry: word_count live v2, status trial, uses = 2 knowledge: lessons with scores, verdicts | v next use of word_count ok -> uses = 3 -> def_kept v2

(A schematic sequence, not a real journal.) A soak survives a restart: two clean uses before the stop, one more after.

In Clojure replay is one line, and the live process uses the same function, so the two cannot disagree:

(defn replay [events] (reduce apply-event empty-state events))

(defn emit!
  "Append one event to the journal and apply it. The event is round-tripped
  through JSON first so live state equals replayed state exactly."
  [k ev]
  (locking (:state k)
    (let [line (json/write-str (assoc ev :ts (str (Instant/now))))
          ev' (json/read-str line :key-fn keyword)]
      (with-open [w (io/writer (:journal k) :append true)]
        (.write w (str line "\n")))
      (swap! (:state k) apply-event ev')
      ev')))
clojure/src/cmh/kernel/state.clj:92-104

reduce (a "fold") applies the pure apply-event to each event in order, starting from empty-state. A half-written last line after a crash is skipped (clojure/src/cmh/kernel/state.clj:88-89).

The base prompt

Every flavor sends the model the same immutable system prompt, read from base-prompt.md at the repository root, "falling back to a copy embedded at build time" (SPEC.md:153-155). It is 18 lines long, so here it is in full:

You are cmh, a coding agent that can improve itself while it runs.

You work in the user's current directory with the kernel tools `bash`,
`read_file`, and `write_file`, plus any userspace tools listed in this request.

Your userspace (tools, prompt notes, and the hooks `compose_system` and
`select_lessons`) is code you can rewrite with `propose_def`. Every proposal is
validated against its tests in a scratch environment, goes live as a trial, and
is kept only if its next uses succeed; otherwise it is reverted and the verdict
is remembered. Use `list_defs` and `show_def` before changing a definition.

Make a userspace change when a capability would clearly help this or future
tasks, such as a tool for something you keep doing by hand. Keep changes small
and give every tool or hook real tests. Record durable, reusable insights with
`remember`; do not record task-specific trivia.

The kernel, this base prompt, and the journal are not yours to change.
Finish each task with a concise answer for the user.
base-prompt.md:1-18

It explains the gate (lines 6-10), says when self-modification is worth it (12-15) and states the one hard rule (17). It permits self-modification without pushing it. In the evals of the first five flavors, agents proposed only 5 to 78 changes per flavor across about 60 episodes; the ROADMAP adds that the evals do not yet reward self-modification (ROADMAP.md:23-26). Language references never go in this file: the Forth, WASM and Roc kernels send theirs as extra system blocks between the base prompt and the supplement.

Model provider and the mock

The default provider is the Anthropic Messages API (SPEC.md:138-146); in the evals every cmh harness points at a logging proxy via ANTHROPIC_BASE_URL, so all use the same model. The second provider is what makes the tests possible:

The mock provider "replays a JSON array of assistant content arrays in order, one per model request", "and records every request it received so tests can assert on the system prompt and tool list" (SPEC.md:147-151). In other words, a fake model that plays back pre-written replies.

One CLI for every flavor

cmh [--state DIR] [--provider anthropic|mock] [--script FILE] [--model M]
    [--soak N] [--no-reflect] <command>

  repl            interactive; each line is a task. Slash commands:
                  /defs  /show NAME [VERSION]  /knowledge  /refine
                  /rollback NAME VERSION  /quit
  run "TASK"      one task, prints the final answer, exits 0 on success
  refine          one refine task
  defs            print the registry
  knowledge       print lessons and verdicts
SPEC.md:160-169

Answers go to stdout; a one-line-per-event trace such as [tool] propose_def word_count -> trial v2 goes to stderr (SPEC.md:172-174).

An identical CLI lets one eval runner drive every flavor (evals/harnesses.json; chapter 11).

The eight required tests

The spec ends with an executable definition of "this is a cmh". Each flavor must pass these, in its own language's test framework, with the mock provider and no network:

1. Late binding: propose a new `word_count` version; the next call in the
   same process uses it.
2. Gate rejection: source that fails to compile/eval, and source that fails a
   test, are both rejected; the live version is unchanged.
3. Soak revert: a version that throws on some input reverts on that use; the
   previous version is live again; a verdict entry exists.
4. Soak keep: after `soak` clean uses the version is `kept`.
5. Persistence: a fresh kernel on the same state dir has the same live
   versions, statuses, soak counters, and knowledge.
6. Hook redefinition: a new `compose_system` changes the system prompt seen by
   the mock provider, and the base prompt is still present.
7. Lesson scoring: lessons gain and lose score with task outcomes and retire
   at -3.
8. One end-to-end mock run through `run` where the model proposes a tool and
   then calls it within the same task.
SPEC.md:178-192

For example, Clojure's test 6 (clojure/test/cmh/kernel_test.clj:146-159) scripts the mock to propose a new compose_system and finish, then checks that the second request in the same task already carries the custom supplement while its first system block is still the base prompt. The eight are a floor: the wasm flavor has 27 tests and Roc 14.

What the spec leaves open

The spec fixes behavior but not safety mechanisms: it says a timeout is an error, not how to stop a runaway loop or keep agent code from crashing the host. That is where the flavors differ most: a real wall in Racket (sandbox), Forth and WASM (fuel and memory limits) and Roc (a fork per call), and almost none in Clojure, Rust and Lean, where agent code runs in the harness process.

Key takeaways

  • Every flavor implements the same 192-line SPEC.md: an immutable kernel, a versioned userspace of tools, notes and two hooks, and a knowledge store of lessons and verdicts.
  • Late binding (look up the live version by name on every call, and rebuild the tool list on every request) is what lets a change take effect on the very next call without a restart.
  • propose_def is the only way userspace changes. Each proposal is validated in scratch, goes live as a trial, soaks for 3 uses, and is kept or reverted; either way a verdict is written and always shown to the model.
  • "Kept" currently means "did not error for 3 uses", not "measurably helped", and the gate only runs the agent's own tests.
  • Lessons come from remember and from one reflection call after each task; they score +1/-1 by task outcome and retire at -3.
  • The kernel, not a hook, prepends the 18-line base prompt, so the agent can rewrite its prompt builder without being able to delete its rules.
  • All state is an append-only journal.jsonl; replaying it rebuilds the registry, soak counters and knowledge exactly, and everything else is a cache.
  • A shared CLI and a mock provider make the harnesses interchangeable in the evals and testable offline; eight required tests define what counts as a cmh.
