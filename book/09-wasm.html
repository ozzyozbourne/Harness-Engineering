Harness Engineering · Chapter 9

9. The whole harness in WebAssembly: the agent rewrites its own kernel

The agent loop, the gate and the tools become one replaceable image, and a small hypervisor keeps it honest.

Every harness so far drew the same line. Below it was the kernel: the agent loop, the prompt assembly, the gate that tests new definitions, the journal. Above it was userspace: the tools, notes and hooks the agent writes for itself. The agent could reshape userspace as much as it liked, but the kernel was fixed. Whoever built the harness wrote it, and it changed only when a human changed it.

The sixth implementation, in wasm/, removes that limit. The whole harness, agent loop included, is compiled into one WebAssembly component called the kernel image. The agent can read the image's Rust source, propose changes to it, and, if the new image passes a series of checks, run on it from the next task on. Beneath the image sits a small native program, the hypervisor. It holds every real capability and contains no agent logic. It does not trust the image.

This chapter explains the idea, the contract between the two halves, how the hypervisor survives a broken image, how a kernel change is built and judged, and what the design does not yet deliver.

The unikernel idea, and why WebAssembly stands in for it

A unikernel is a program compiled together with just enough operating system to run on its own inside a virtual machine. There is no general-purpose OS underneath, just one image that boots and does one job. A hypervisor runs such images, gives each one virtual hardware, and can stop, discard or restart them. If an image misbehaves, the hypervisor throws it away and boots another.

That maps neatly onto a self-modifying agent. Treat each version of the harness as an image. A new version is a new image. If it is bad, you boot the previous one. The agent changes the image, and the hypervisor owns the outside world and decides which image runs.

Real unikernels need hardware virtualisation (on Linux, KVM). The orbs this project ran in do not provide KVM. The roadmap lists "Unikernel or microVM per generation" (Unikraft or Firecracker images) as experiment 11 and notes it "Needs a runner with KVM; orbs do not have it." So the WASM flavor uses WebAssembly as the stand-in:

tools. This is the "harness as a unikernel" idea. Real unikernels need KVM,
which orbs do not have, so a WebAssembly component plays the role of the
unikernel image and a small Rust program plays the role of the hypervisor.
wasm/README.md:6-8

WebAssembly (WASM) is a portable bytecode, a bit like the instruction set of a virtual CPU. A compiler such as rustc can target it, and a runtime runs it. Here the runtime is Wasmtime 50.0.1, which compiles the bytecode to native code. The property that matters is isolation. A WASM program can only read and write its own linear memory, one flat byte array whose size the host can cap. It has no system calls of its own. Files, the clock, the network and "ask the model" must all be handed to it by the host as imports: functions the host implements and the guest may call. The guest offers exports, functions the host calls. When something goes wrong inside the guest, such as an out-of-bounds access, a panic, or running past a deadline, the runtime stops it with a trap. A trap reaches the host as an ordinary error value, never as a crash of the host process.

That gives the same three properties that make a hypervisor useful: the image can be thrown away, everything it can do is listed, and its failures are contained. Chapter 8 used the same runtime for a much smaller job. Only the Forth interpreter ran inside WASM, and the harness around it was native Rust. The table compares the two.

The two halves

The flavor is two Rust crates. guest/ is the kernel image, compiled into one .wasm component. host/ is the hypervisor, the cmh binary. The README draws the split like this:

Everything in the lower box can be replaced by the agent. Everything in the upper box cannot. The guest is about 3,800 lines of Rust: forth/vm.rs 1,866, kernel.rs 951, state.rs 236, tools.rs 156, sys.rs 154, selftest.rs 136, plus smaller files. The hypervisor's src/hv/ is 2,256 lines, the largest parts being images.rs (684) and guest.rs (529).

Userspace still exists. Tools, notes and the two hooks (compose_system, select_lessons) are Forth definitions, exactly as in chapter 8, and the seed files are identical to the Forth flavor's. The Forth VM is now just one more part of the kernel image. That has a cost the chapter returns to at the end: wasm/guest/src/forth/vm.rs is a copy of forth/vm/src/lib.rs, and the two differ by an 824-line diff.

The component model and the WIT world

A plain WASM module only understands numbers: its imports and exports take and return integers and floats. Passing a string means agreeing on where in memory it lives and how long it is. The Forth flavor did that by hand. The component model is a layer on top of WASM that adds real types (strings, lists, records, optional values, results that are either a value or an error) and generates the glue code on both sides. A component is a WASM program plus a description of the typed functions it imports and exports. That description is written in a small interface language called WIT (WebAssembly Interface Types). A WIT world names one complete contract: these imports, these exports.

If you have used an IDL such as Protocol Buffers or an OpenAPI schema, WIT plays the same role: one file, read by tools on both sides, from which each side gets functions in its own language. Here is the world the whole flavor revolves around:

world harness {
    import host;
    use types.{task-outcome};

    /// Replays the journal (and installs the seeds if it is empty).
    export init: func() -> result<_, string>;
    /// One agent task.
    export run-task: func(task: string) -> task-outcome;
    /// Continues a task from a checkpoint after the previous instance
    /// trapped; `report` explains the trap and goes to the model.
    export resume-task: func(checkpoint: string, report: string) -> task-outcome;
    /// One refine task.
    export refine: func() -> task-outcome;
    /// A non-task command: defs, knowledge, /show NAME [V], /rollback NAME V,
    /// /state (JSON), /call NAME JSON, /propose JSON, /remember TEXT.
    export command: func(line: string) -> result<string, string>;
    /// The image's own mock scenarios; run by the host before a new image
    /// may go live. Uses no host side effects.
    export self-test: func() -> result<string, string>;
}
wasm/guest/wit/cmh.wit:76-95

Read it as a job description for any kernel image. An image must be able to rebuild its state (init), run a task, pick a task back up after a crash (resume-task), run a refine pass, answer commands such as defs, and test itself. result<_, string> means "nothing on success, an error message on failure". task-outcome is a record defined at the top of the file with three fields: success: bool, answer: string and error: option<string>.

Each side generates its bindings from the same file. In the guest, one macro call, wit_bindgen::generate!({ world: "harness", path: "wit" }); (lib.rs:6), produces a Guest trait. The image implements it with thin wrappers around the kernel:

with_kernel first calls k.sync(), which applies any journal events the hypervisor appended since the last call (image verdicts, for example). In the host, the matching macro wasmtime::component::bindgen! generates a Harness type with methods such as call_init and call_run_task, and a trait the host implements for the imports.

The kernel talks to the world through a Rust trait, Sys, with two implementations. HostSys calls the real WIT imports. MemSys is "an in-memory world with a scripted model, used by the image's own self-test (no side effects)" (sys.rs:2-3). The same kernel code can therefore run against the hypervisor or against a fake world held entirely in memory, which the self-test step below depends on.

The contract belongs to the host. The header of cmh.wit says it plainly: "Owned by the host: kernel proposals cannot change this file, and an image that does not match it fails to boot." The agent may rewrite everything behind the exports, but not the exports themselves.

The host as hypervisor

The README sums up the hypervisor's stance in one line: "The host never trusts the image." It does four things: it hands out capabilities, it enforces limits, it turns traps into reports, and it restores state after a trap.

Capabilities

An image starts with nothing. Each thing it can do is one import, and the host decides what that import really does. post-messages sends only to $ANTHROPIC_BASE_URL (or the mock), and the host adds credentials, so the image never sees a key. write-file refuses the state dir, wasm/ and base-prompt.md. bash runs inside a sandbox where those same paths are read-only (more on that below). Even the base prompt is enforced at this level:

        // The base prompt is immutable: whatever the image sends, it comes first.
        if system.first() != Some(&self.env.base_prompt) {
            system.retain(|s| s != &self.env.base_prompt);
            system.insert(0, self.env.base_prompt.clone());
            self.base_prompt_inserted = true;
        }
wasm/host/src/hv/guest.rs:267-272

A kernel image could rewrite its prompt assembly to drop the base prompt. It would not matter: the hypervisor puts it back before the request leaves the machine, and sets a flag that makes the conformance check (below) fail.

Limits measured in guest time

An image could loop forever or allocate until the machine runs out of memory. Memory is the simple case: a Wasmtime resource limiter refuses to let linear memory grow past 512 MB. Time is harder, because much of a task's wall-clock time is spent outside the guest, waiting for the model, running bash, or building a new image. A plain wall-clock limit would kill healthy tasks that are only waiting on a slow model. So the hypervisor counts only guest time. Every import runs through one helper that books its duration as host time:

    /// Runs one import: its time is host time, and the guest's slice
    /// starts again when it returns.
    fn host<R>(&mut self, f: impl FnOnce(&mut Self) -> R) -> R {
        let t = Instant::now();
        let r = f(self);
        self.host_time += t.elapsed();
        self.slice_start = Instant::now();
        r
    }
wasm/host/src/hv/guest.rs:211-219

Wasmtime's epoch interruption does the checking. A background thread advances a global counter (the "epoch") at a fixed interval, every 10 ms (TICK, guest.rs:33), and the compiled guest code checks it at loop heads and function entries. When the deadline passes, Wasmtime calls a callback the host registered:

        store.epoch_deadline_callback(|mut s| {
            let d = s.data_mut();
            let slice = d.slice_start.elapsed();
            let total = d.call_start.elapsed().saturating_sub(d.host_time);
            if slice > d.limits.slice {
                let msg = format!(
                    "the kernel ran {:.1} s without returning to the hypervisor (limit {:.0} s)",
                    slice.as_secs_f64(),
                    d.limits.slice.as_secs_f64()
                );
                d.limit_hit = Some(("guest-timeout".into(), msg));
                return Err(wasmtime::format_err!("guest time limit"));
            }
wasm/host/src/hv/guest.rs:437-449

Two limits are checked. A slice is a stretch of guest code without a single host call; the default is 20 s, and exceeding it is a guest-timeout. The total is guest time across one export call, 300 s by default, and exceeding it is a guest-time-limit. Returning Err from the callback makes Wasmtime trap the guest at that point. Unlike the Forth flavor, there is no fuel (a per-instruction counter) at the Wasmtime level. Runaway Forth code is caught earlier, inside the image, by the VM's own step counter of 20,000,000 Forth steps (MAX_STEPS, forth/mod.rs:13-14). The guest-time limit is the backstop for runaway Rust in the kernel itself.

Trap → report

When a call traps, the hypervisor works out what kind of trap it was and writes a report for the model, not for a developer. fault_of checks, in order: a time limit the callback recorded, the memory limiter, a panic (detected because the guest's captured stderr contains "panicked"), an allocation failure, a stack overflow, an out-of-bounds access, and any other trap. Then it formats one message:

    let mut report = format!("kernel trap [{kind}] in image v{} during {export}: {msg}", image);
    if !stderr.is_empty() {
        report.push_str(&format!("\n  guest stderr:\n    {stderr}"));
    }
    report.push_str(&format!("\n  hint: {}", hint(&kind)));
    GuestFault { kind, report }
wasm/host/src/hv/guest.rs:413-418

A report reads like kernel trap [guest-timeout] in image v2 during run-task: the kernel ran 20.0 s without returning to the hypervisor (limit 20 s), followed by the last lines of guest stderr (where a Rust panic message ends up) and a one-line hint about what usually causes that kind of trap. The instance that trapped is marked dead and never called again (guest.rs:485-499).

Fresh instance → journal replay → resume

Recovering from a trap does not mean repairing the broken instance. The hypervisor discards it and boots a new one, and the new one gets its state back from the journal. That works because every lasting fact in this design, from definitions and verdicts to lessons and tasks, is an event in journal.jsonl, and init rebuilds the kernel's state by replaying those events. The fresh instance has "exactly the state of the last journaled event" (README:92-93).

The task that was running when the trap happened is not lost either. Before each turn's tool calls, the kernel saves a checkpoint:

                break;

            // If a tool call traps the image, the hypervisor resumes from here.

The checkpoint holds the task id, the task, the selected lessons, the messages so far, the transcript, the tool-error history and the turn number. The hypervisor keeps it outside the image. After a trap, its recovery loop does the rest:

In order: log the trap, revert the image that trapped (so a bad new kernel is dropped right away), boot the live image afresh (its init replays the journal), and call resume-task with the checkpoint and the report. In the resumed instance, every tool call of the interrupted turn gets an error result that begins "error: the kernel image trapped during this turn's tool calls; the hypervisor restored it and replayed the journal. Work from tool calls in this turn may be lost." with the report appended (kernel.rs:659-661). The model reads that and carries on. A task may be resumed at most three times (MAX_RESUMES = 3, mod.rs:31). If there is no checkpoint, or the limit is reached, the hypervisor itself journals the task as failed, with "by": "hypervisor".

A test injects exactly this. host_survives_guest_infinite_loop_and_memory_blowup builds an image whose kernel has a /spin command (an infinite Rust loop), a /blowup command (pushing 1 MB vectors forever) and a chaos_spin tool. It asserts that /spin fails with kernel trap [guest-timeout] in image v2 during command in under 30 seconds, that "a fresh instance serves the next call", that /blowup gives kernel trap [memory-limit] in image v2, and that a task calling the spinning tool still finishes: the model's next tool result contains the trap report and the word "restored", v2 is reverted, v1 runs the rest, and the journal still records exactly one task (host/tests/images.rs:152-192).

The image lifecycle: propose_kernel

The state directory holds kernel-src/, a copy of the live image's Rust crate. The agent reads it with read_file or bash, like any other source code. A system block the image adds to every prompt explains the arrangement:

Besides userspace (`propose_def`), you can change the kernel itself: the
agent loop, the prompts, the kernel tools and the gate. Its Rust source is in
the state dir under `kernel-src/` (`src/kernel.rs` holds the agent loop and
prompt assembly, `src/tools.rs` the tool schemas). Read it first, then call
`propose_kernel` with exact `edits` or whole `files` under `src/` or `seed/`.
wasm/guest/src/kernel_reference.md:10-14

The same block ends with advice that turns out to matter for the results: "Builds take a while: keep changes small and only change the kernel when userspace cannot do the job."

A proposal is JSON with a description and either exact string replacements or whole files:

{"description": "print a per-turn token summary",
 "edits": [{"path": "src/kernel.rs", "old_str": "...", "new_str": "..."}],
 "files": {"src/extra.rs": "..."}}
wasm/README.md:111-113

propose_kernel is a kernel tool, but it does almost nothing itself. It passes the request to the propose-image import, and the hypervisor does the work. Version 1 is the image built into the cmh binary; host/build.rs embeds both the compiled .wasm and every guest source file, so v1's source can be written out at startup. Each proposal becomes image vN and passes through six stages. Failing any of them rejects it, and the live kernel stays as it was.

propose_kernel(request) │ 1 edit copy parent's source to images/vN/src, apply edits │ (only src/ and seed/; each old_str exactly once) 2 compile cargo build --release --locked --offline --target wasm32-wasip2 │ in a sandbox: no network, repo + state dir read-only 3 boot scratch instance: temp dirs, mock model, no bash, run init 4 self-test the image's own self-test export (4 scenarios) 5 conformance the hypervisor's own mock task + journal replay check │ 6 trial live from the next task on ├── soak (3) clean tasks ──► kept └── trap / boot failure / failed task ──► reverted

1. Edit

The hypervisor journals image_proposed, copies the parent image's source into images/vN/src, and applies the edits. Each old_str must occur exactly once, and "The edits change nothing" is itself a rejection. The paths are checked first:

fn check_path(p: &str) -> Result<PathBuf, String> {
    let path = Path::new(p);
    let ok_components = path.components().all(|c| matches!(c, std::path::Component::Normal(_)));
    if p.is_empty() || !ok_components {
        return Err(format!("`{p}`: paths are relative to kernel-src/, without `..`"));
    }
    if !(p.starts_with("src/") || p.starts_with("seed/")) {
        return Err(format!(
            "`{p}` cannot be changed: only files under src/ and seed/ (Cargo.toml, Cargo.lock and wit/ belong to the hypervisor)"
        ));
    }
    Ok(path.to_path_buf())
}
wasm/host/src/hv/images.rs:110-122

Fixing Cargo.toml and Cargo.lock means a proposal cannot add dependencies, build scripts or procedural macros, all of which run code at build time. Fixing wit/ keeps the contract stable.

2. Compile

The hypervisor runs a real cargo build --release --locked --offline --target wasm32-wasip2 with two jobs. The build runs in the same kind of sandbox as agent bash, but stricter: no network, the whole repository and the state dir read-only, and ~/.config covered by an empty tmpfs so that no credentials stored there are visible. One shared target directory (target/ under $CMH_IMAGE_CACHE, else $XDG_CACHE_HOME/cmh-wasm, else ~/.cache/cmh-wasm) serves every state dir, behind a file lock. If crates are missing it retries once online, and it gives up after 900 s. Compiler output is trimmed to start at the first error line, so the model sees what rustc said rather than pages of build log.

3. Boot, 4. self-test, 5. conformance

A new image is not trusted just because it compiles. The hypervisor boots it in a scratch instance: temporary state and work dirs, an empty mock model, bash disabled, and the propose-image and images imports disabled. A panic in init is caught here. One test plants panic!("boom at boot") in lib.rs and checks for a rejection containing kernel trap [guest-panic] and the panic text.

Next it calls the image's own self-test export, which runs four scenarios against MemSys, the in-memory world:

The self-test lives in the image, so an image could weaken its own test. That is why a fifth stage exists that the image cannot touch. Conformance is the hypervisor's own scripted mock task, four model responses long: call the seed tool word_count, propose a Forth tool reverse, call reverse in the same task, then answer "conformance done". The hypervisor then checks the base prompt came first, that the nine SPEC kernel tools plus word_count were offered, that reverse appeared in the next request (late binding, chapter 2's core promise), that the journal holds the expected events (task_started, a successful task_finished, def_trial, a clean def_use), and that a second instance replaying the same journal reports an identical /state (images.rs:596-683).

6. Trial, then kept or reverted

An image that passes everything becomes a trial. It is journaled as image_trial, kernel-src/ is rewritten to match it, and it becomes the live kernel "from the next task on". The task that proposed it finishes on the old image. Each later task of the trial adds an image_use event. After --soak clean tasks (default 3) the image is kept. It is reverted if it traps, fails to boot, or a task fails during its trial. Reverting falls back to "the newest kept image other than v, else the built-in one" (images.rs:360-364). This is the same gate → trial → soak → keep/revert cycle that userspace definitions go through (chapter 2), applied to the whole kernel.

The verdicts become knowledge. They enter the guest's state under the name image and are shown to the model under "## Verdicts on past userspace and kernel changes", so an agent that broke its kernel last week sees that it did.

The journal: a schema the host owns

The journal is the one thing that must outlive every image. Image v5 has to be able to read events written by v2, and v1 (the fallback of last resort) has to read events written by v5. If the image owned the journal format, a single bad proposal could make history unreadable to every other image. So the hypervisor owns the schema. Images may write only the SPEC event types, with their required fields, or free-form ext_* events. A separate list of image lifecycle events belongs to the hypervisor alone:

/// Event types only the hypervisor writes (kernel image lifecycle).
const HOST_EVENTS: &[(&str, &[(&str, Ty)])] = &[
    ("image_proposed", &[("version", Ty::Int), ("parent", Ty::Int), ("description", Ty::Str)]),
    ("image_rejected", &[("version", Ty::Int), ("stage", Ty::Str), ("error", Ty::Str), ("verdict", Ty::Str)]),
    ("image_trial", &[("version", Ty::Int), ("parent", Ty::Int), ("description", Ty::Str)]),
    ("image_use", &[("version", Ty::Int), ("ok", Ty::Bool)]),
    ("image_kept", &[("version", Ty::Int), ("verdict", Ty::Str)]),
    ("image_reverted", &[("version", Ty::Int), ("restored", Ty::Int), ("reason", Ty::Str), ("verdict", Ty::Str)]),
];

The guest list (journal.rs:20-33) has eleven types, from def_proposed to task_finished, each with its required fields: def_use needs name (a string), version (an integer) and ok (a boolean), and so on. Every journal-append from the image passes through this check:

/// Checks an event from a kernel image against the stable schema.
pub fn check_guest_event(ev: &Value) -> Result<(), String> {
    let obj = ev.as_object().ok_or("journal schema: an event must be a JSON object")?;
    let kind = obj.get("type").and_then(Value::as_str).ok_or("journal schema: an event needs a string `type`")?;
    if kind.starts_with("ext_") {
        return Ok(());
    }
    if HOST_EVENTS.iter().any(|(k, _)| *k == kind) {
        return Err(format!("journal schema: `{kind}` events are written only by the hypervisor"));
    }
    let Some((_, fields)) = GUEST_EVENTS.iter().find(|(k, _)| *k == kind) else {
        let known: Vec<&str> = GUEST_EVENTS.iter().map(|(k, _)| *k).collect();
        return Err(format!("journal schema: unknown event type `{kind}` (known: {}, or ext_* for new kinds)", known.join(", ")));
    };
    check_fields(kind, obj, fields)
}
wasm/host/src/hv/journal.rs:73-88

After the check, the hypervisor stamps two fields the image cannot forge: ts, and image, the version that wrote the event. The largest event an image may append is 1 MB. On the reading side, the guest's replay ignores types it does not know. Together those rules mean any image, old or new, can replay the same journal: a new image can invent ext_* events without breaking old ones, and no image can fake a kept verdict for itself. The test journal_schema_and_protected_paths_hold checks both halves: a guest-written image_kept is refused "only by the hypervisor", a def_use missing its fields is refused, and an ext_note passes (spec.rs:362-366).

Sandboxed bash via unshare

The image's bash tool is a real shell on the real machine, because the agent needs one to do real work. That is the one big hole in a WASM wall: bash could just overwrite the journal, the hypervisor's source, or the base prompt. The hypervisor closes it with Linux namespaces. The unshare command starts a process in new namespaces: -r creates a user namespace where the caller appears as root (so it may mount things without real root privileges), -m gives it a private mount table, and -n an empty network namespace. Inside, a tiny script bind- mounts each protected path read-only over itself:

/// Mounts each path in `$CMH_RO` read-only and each in `$CMH_TMPFS` as an
/// empty tmpfs, then runs `$CMH_CMD`.
const SANDBOX_SCRIPT: &str = r#"IFS='
'
for p in $CMH_RO; do [ -e "$p" ] && mount --bind -o ro "$p" "$p"; done
for p in $CMH_TMPFS; do [ -d "$p" ] && mount -t tmpfs -o size=1m tmpfs "$p"; done
c=$CMH_CMD
unset CMH_RO CMH_TMPFS CMH_CMD IFS
exec bash -c "$c""#;

        c.arg("-c").arg(cmd);

    }

For agent bash, the read-only paths are the state dir, wasm/ and base-prompt.md (mod.rs:104), and network stays on. For image builds, the read-only paths are the whole repository plus the state dir, ~/.config is an empty tmpfs, and network is off. Bash output is capped at 20 KB, the timeout is clamped to 1-3600 s, and on timeout the whole process group is killed. The write-file import enforces the same protected paths in plain Rust ("refused: ... is inside protected path ..."). The schema test above also checks the sandbox: echo bad >> STATE/journal.jsonl from the bash tool must fail with Read-only file system, whenever the sandbox is available.

That "whenever" matters. Look at the top of sandboxed: if unshare does not work on this machine, the command runs without any sandbox. The hypervisor prints one warning on stderr, "user namespaces unavailable; bash and image builds run without the read-only sandbox" (sandbox.rs:48), and carries on. In the orbs used for this book, unshare -r -m works, so the sandbox was active.

Tests

cd wasm && cargo test runs offline with the mock provider. On 2026-11-13 it reported 27 tests, all passing: 17 in host/tests/spec.rs, 7 in host/tests/images.rs and 3 provider unit tests. The image tests run real cargo builds, so they are slow: images.rs took 105 s and spec.rs 91 s.

The self-test case deserves a second look. Changing one string literal from "tool" to "toolz" compiles fine and boots fine. Only a behavioral check catches that the agent can no longer see its own tools. That is the reason both self-test and conformance exist.

Limitations

The machinery works in tests. Whether it is useful is a different question, and so far the evidence is thin.

No recorded eval episode used propose_kernel. Across the 48 local WASM eval episodes (16 + 32, logs in evals/results/{iso-pilot,matrix-memory}/logs/wasm.*), a grep finds 0 propose_kernel calls, 0 [image] lines and 0 kernel traps, against 218 forth_eval and 13 propose_def calls. Those logs are gitignored and not part of any committed results file. Kernel self-modification has so far been exercised only by tests, by scripted runs like the one above and by the build-time live runs.

Those same local runs give the only eval numbers for this flavor. In the isolated 16-episode pilot with DeepSeek V4.1 Flash it scored 88%, 14/16 (Forth 100%, Prime Agent 94%; evals/results/iso-pilot/summary.md). In the 32-episode isolated matrix it scored 78%, 25/32, the same as Forth, and both were below the 80% bar (evals/results/matrix-memory/summary.md). Each was a single trial, the files are gitignored, and the roadmap does not cite them. Treat them as indications, not firm results. Chapter 11 covers both runs.

The rest of the list comes from reading the code:

  • It is a stand-in. Real unikernels or microVMs need KVM. A WASM component gives the same discard-and-reboot shape, but it shares a process with the hypervisor, not a hardware boundary.
  • The sandbox can silently be absent. Without unprivileged user namespaces, bash and image builds run unsandboxed after one warning. The notes infer a worse consequence: bash could then also write the cached native code in STATE/cache/*.cwasm, which load_component loads with unsafe on the assumption that bash cannot write the state dir (guest.rs:95-97). With the sandbox off, that is a path to running injected code in the host process.
  • Agent bash keeps the network and has no CPU or memory limits beyond its timeout. The image can also read the whole state dir, journal included, through the preopens.
  • A trap reverts even a kept image. The README describes reverting on a trap "during the trial", but Hypervisor::task calls revert on every trap, and Images::revert skips only v1 and images that are not live (images.rs:372-375). No test covers this.
  • Builds are slow and serialized. The scripted run above took 8.4 s with a warm cache. A cold build takes minutes, and one lock serializes builds across every state dir.
  • No new dependencies. With Cargo.lock fixed, the kernel can only reshape its own Rust using serde_json and wit-bindgen.
  • Kept means "did not fail". Conformance checks SPEC behavior, not quality. As with userspace, an image is kept after three tasks that did not fail, not because it helped.
  • Checkpoints only before tool calls. A trap during prompt composition or the model call resumes from the previous turn's checkpoint, and work done since then is lost.
  • Two copies of the Forth VM. The guest's copy and forth/vm differ by an 824-line diff, so a fix in one must be made in the other.
  • Cosmetic: journal lines are written with sorted keys, so type is not the first field.

Key takeaways

  • Putting the whole harness in a WASM component makes the kernel replaceable: the agent loop, prompts, gate and tools become one image the agent can rebuild, while a small hypervisor with no agent logic holds every real capability.
  • The WIT world is the fixed contract: six exports any image must provide, thirteen imports it may use, and file reads through read-only WASI preopens. The host owns it, so proposals cannot change it.
  • Limits count guest time, not wall time (a 20 s slice and 300 s per call, plus 512 MB of memory), so slow models do not trip them but runaway kernel code does.
  • Recovery means discarding the instance, not repairing it: trap → report → revert → fresh instance → journal replay → resume-task from a checkpoint, with the report delivered to the model as the tool result.
  • propose_kernel runs a full pipeline (edit, sandboxed offline build, scratch boot, self-test, host-owned conformance, trial, kept or reverted), and every stage returns plain feedback such as rustc's own error.
  • The journal outlives every image because its schema belongs to the host: guests write SPEC or ext_* events, only the host writes image_*, and every event is stamped with its writer.
  • The honest result: the machinery is tested (27 passing tests), but no recorded eval episode has used it. Whether agents will rewrite their own kernels when it helps is still an open question.
