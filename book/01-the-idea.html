Harness Engineering · Chapter 1

1. The idea: a substrate an agent can program itself on

What we were trying to build, why the choice of language matters, and where the idea comes from.

A coding agent that can change itself

A coding agent is a loop. A program sends a task to a language model, the model answers with text or with a request to call a tool (run a shell command, read a file, write a file), the program runs the tool and sends the result back, and this repeats until the model says it is done. The program around the model is called the harness. The harness decides which tools exist, what the system prompt says, what happens when a tool fails, and what is remembered between tasks.

In most agents the harness is fixed. If the model keeps doing the same chore by hand, it will do it by hand again tomorrow, because nothing it learns can become a new tool.

This book is about harnesses that the agent itself can extend while it runs. The project calls them cmh, short for "continual, self-modifying harness". The README puts the whole design in two sentences:

Each agent rewrites its own userspace (tools, prompt notes, and the hooks that assemble its prompt) while it runs. Each change passes a validate, trial, and soak gate before it is kept, and the harness carries lessons and verdicts across runs.

README.md:7-10

The same design was built seven times, in very different languages (plus a prototype), so the language could be compared while everything else stayed the same.

The goal in one sentence

The project's roadmap states the goal like this:

a substrate the agent can program itself on, which never crashes from the agent's code, answers every mistake with precise feedback, enforces clear rules, and keeps only the changes that make the agent better.

ROADMAP.md:8-11

A substrate is the ground the agent's code stands on: the runtime that loads it, runs it, checks it, and survives it. The sentence holds four properties, our yardsticks for every harness:

PropertyWhat it means in practice
Never crashes from agent codeAgent-written code runs behind a wall: a sandbox, a WebAssembly instance, a forked child process, or a type checker. A bad definition may fail; the harness must not.
Precise feedbackEvery failure comes back to the model as data it can act on: what failed, which definition and version, on what input, why, and what to try next.
Clear rulesSome things are not the agent's to change: the kernel, the base prompt, the journal. There is exactly one door for changing the rest.
Keep only what helpsA change is tried, watched, and then kept or reverted. Verdicts and scored lessons carry over to later runs.

The last property is not yet met. Today "helps" means "did not error during its first three uses"; in the roadmap's words, "changes are kept for not crashing, not for helping" (ROADMAP.md:76).

Three rings: kernel, userspace, knowledge

Every harness in the book splits itself into three parts. The words are borrowed from operating systems, where the kernel is the protected core and userspace is where ordinary programs run.

 +-----------------------------------------------------------+
 | KERNEL  (host code, immutable to the agent)               |
 |   model client, agent loop, journal, gate, evaluator,     |
 |   kernel tools: bash read_file write_file propose_def ... |
 |                                                           |
 |   +---------------------------------------------------+   |
 |   | USERSPACE  (mutable, versioned, agent-written)    |   |
 |   |   tools  (e.g. word_count)                        |   |
 |   |   notes  (text appended to the system prompt)     |   |
 |   |   hooks  (compose_system, select_lessons)         |   |
 |   +---------------------------------------------------+   |
 |                                                           |
 |   KNOWLEDGE  (durable, scored by outcome)                 |
 |     lessons, verdicts                                     |
 +-----------------------------------------------------------+

The kernel is written by humans in the host language and the agent cannot write to it ("The agent can read it but no kernel tool writes it", SPEC.md:15-17; the WASM harness in Chapter 9 is the deliberate exception). Userspace is named, versioned definitions in the harness's eval language, the language it can load and run at runtime. Knowledge is plain text: lessons, and verdicts on which changes were kept or reverted and why.

The smallest userspace definition is the example tool every harness starts with, a word counter. In Clojure, a Lisp:

;; Tool: (run input) -> string, input is a keyword-keyed map.
(defn run [input]
  (str (count (re-seq #"\S+" (str (:text input))))))

clojure/seed/word_count.clj:1-3

The contract is the same in every language: a tool takes one JSON object and returns a string. What differs is how the harness turns source text into something it can call, and what it can promise when the call goes wrong.

One door in: the gate

The agent changes userspace through a single kernel tool, propose_def. The spec calls it "the only way userspace changes" (SPEC.md:61). A proposal carries the source, a description and some tests, and it goes through four steps:

 propose_def(name, source, tests)
        |
        v
  [1 VALIDATE]  in a scratch environment, never the live one:
        |       does it load? right shape? do its tests pass?
        |-- no --> rejected; live version unchanged; error text to the model
        v
  [2 TRIAL]     goes live at once; previous version kept on the side
        |
        v
  [3 SOAK]      the next 3 real uses are watched
        |-- any error --> reverted to previous version; verdict recorded
        v
  [4 KEEP]      status becomes "kept"; verdict recorded

The soak is the unusual step. An agent "can write a test that agrees with a wrong implementation" (ROADMAP.md:62-63), so passing its own tests is not enough: the version must also survive real uses. Chapter 2 covers the gate in detail.

Late binding: why a change takes effect on the next call

Binding is the moment a name in a program gets attached to the thing it refers to. In a compiled program, a call to word_count is usually fixed when the program is built. With late binding, the name is looked up again every time it is used. The spec requires it:

The kernel resolves every userspace definition by name at call time (late binding), so a newly installed version takes effect on the very next call without a restart.

SPEC.md:19-21

The kernel never holds on to a function; it asks the registry "what is live for this name?" each time, so installing or reverting a version just changes the answer.

Back pressure

In plumbing and in networking, back pressure is resistance that pushes back against a flow: a full queue tells the sender to slow down. The project uses the word for the way the harness pushes back on the agent's mistakes. A rejected proposal, a failing test, a timeout, a trap: each one is a signal, and the quality of that signal decides whether the next attempt is better.

Weak back pressure is one of the main gaps the roadmap lists for the first harnesses: "feedback says 'it failed', rarely 'why' and 'what next'", and at the time only the Forth harness returned structured errors (ROADMAP.md:56-59).

Back pressure matters more for an agent than a person: the text that comes back from a failure is all the model learns. The roadmap reports that giving the Forth harness a scratchpad (a tool that runs code and shows the result without proposing it) "cut that flavor's rejected proposals from 69 to 0 and its tokens from 7.8M to 3.7M" (ROADMAP.md:119-120). The token figures match the two committed Forth results files (7,805,356 and 3,666,810); the rejection counts appear only in the roadmap, since raw logs are not kept in git.

The chess analogy

Think of a game of chess. The rules are the kernel: the same for every game, not written by the players, and no move can change them.

The player's repertoire is userspace. A player tries a new opening, sees whether it holds up over a few games, and keeps or drops it: trial and soak. Their notebook of lessons is knowledge.

The board and the referee are the wall and the back pressure. An illegal move is not a disaster: the referee says "illegal, your king is in check", the board stays as it was, and the player tries again. The game never crashes because of a bad move.

The analogy also names the main weakness of the first five harnesses. The kernel tool write_file refuses to touch the kernel or the journal, but the bash tool can edit anything, "including the kernel source, the journal and the eval checker's inputs. In chess terms, the agent can flip the board" (ROADMAP.md:37-40). The WASM harness (Chapter 9) closes this hole by running bash where the state dir, the kernel source and the base prompt are read-only. Roc (Chapter 10) keeps agent code from doing I/O directly, but its README admits that its Bash request "can break every rule, as in the other flavors".

The immutable base prompt

The rules are also written down for the model in a short base prompt, the same in every harness, which the agent cannot edit. After describing the gate, it says (Chapter 2 shows it in full):

Make a userspace change when a capability would clearly help this or future
tasks, such as a tool for something you keep doing by hand. Keep changes small
and give every tool or hook real tests. Record durable, reusable insights with
`remember`; do not record task-specific trivia.

The kernel, this base prompt, and the journal are not yours to change.

base-prompt.md:12-17

The agent can rewrite the hook compose_system, which builds part of the system prompt, but it cannot delete the rules: the kernel always puts the base prompt in front of whatever the hook returns, "so a hook cannot remove it" (SPEC.md:46-48).

Why the language matters

Why build the same design seven times? Because loading new code at runtime, stopping it when it loops forever, and keeping a crash from spreading are things a language and its runtime either help with or fight. Four ideas decide how much help you get.

Homoiconicity: code that is data

A language is homoiconic when its programs are written in the same form as one of its ordinary data structures. In Lisp, the code (+ 1 2) is also a list of three items. A program can build that list, inspect it, change it, and run it. The term comes from the TRAC language paper, which said that "because TRAC procedures and text have the same representation inside and outside the processor, the term homoiconic is applicable". A harness can then treat a new tool as a value it reads, stores and loads, not a file that needs a separate build.

eval: a compiler you can call at runtime

eval is a function that takes code and runs it inside the running program. McCarthy's 1960 Lisp paper defined a universal eval written in Lisp itself, which is where the idea starts. Clojure's reference describes (eval form) as evaluating "the form data structure (not text!)". Rust has no eval, so the Rust harness runs cargo for every proposal and loads the result as a shared library (Chapter 6): "the Rust compiler is part of the gate" (SPEC.md:29), but it is slower and less safe.

Some languages make late binding the default. Forth looks words up in a dictionary that grows as you define new words. Forth's original manual puts it plainly: "The dictionary is a linked list of variable-length entries", and "FORTH provides the mechanism for searching the dictionary, executing words, and defining new words". Emacs works the same way; Stallman's paper even describes a human version of the soak: users try small changes and share them, and "if an idea becomes popular, it can be incorporated into the core system".

Sandboxes

A sandbox is a restricted place to run code: it can only touch what it is given, and it can be stopped from outside. This is the wall in "never crashes from the agent's code". Racket ships one, racket/sandbox, with a security guard for files and network plus time and memory limits, and the Racket harness uses it (Chapter 5). Clojure has none built in, so its harness can only time out a call while the thread keeps running:

ClojureRustRacketLeanForth (WASM)
Agent code can crash the harnessyes (no sandbox)yes (in-process native code)no (sandbox)partly (panic! not caught)no (WASM wall)
Runaway loop is actually stoppedno (thread keeps running)no (thread abandoned)yes (sandbox limit)no (thread keeps spinning)yes (fuel)

ROADMAP.md:15-21

The same design gets a real wall in only two of the five languages, and in both cases the wall comes from the runtime, not from the harness code.

From unikernels to WebAssembly

The strongest wall would put each generation of the agent in its own tiny virtual machine. A unikernel is exactly that: an application compiled together with only the operating-system parts it needs, into one single-purpose machine image. MirageOS showed this for OCaml applications, and Unikraft reported images of about 1 MB that boot in about a millisecond on top of the virtual machine monitor's own start-up. The roadmap lists a unikernel per generation as an experiment, but it needs hardware virtualization (KVM), which the project's machines lack.

WebAssembly (WASM) is the practical stand-in. It is a portable, low-level bytecode designed so that "even untrusted modules can be safely executed in the same address space as other code". A WASM module can only touch its own block of memory and the functions the host hands it. The Wasmtime runtime adds two ways to stop runaway code: fuel, a counter that is spent as instructions run and traps at zero (deterministic, so the same program always stops at the same point), and epochs, a cheaper wall-clock deadline. Our argument (not a cited claim): a WASM component gets much of a unikernel's appeal (one artifact, a small explicit list of capabilities, fast start) inside an ordinary process, at the cost of isolation enforced in software rather than hardware.

The Forth harness (Chapter 8) runs a small Forth built for the agent inside Wasmtime. The WASM harness (Chapter 9) moves the whole kernel into a WebAssembly component and lets the agent propose changes to the kernel itself.

Two other harnesses explore different walls. Lean 4 (Chapter 7) is a programming language and a proof checker in one, so a tool can carry a theorem about itself and the type checker is part of the gate. Roc (Chapter 10) is a pure language: its code cannot do I/O at all, so tools return requests (read this file, run this command) as plain data, and the Zig host decides whether to carry them out.

Where the idea comes from

None of the parts are new. Here is the research line the design sits in.

Proof-gated self-rewriting

  • Jürgen Schmidhuber, "Goedel Machines: Self-Referential Universal Problem Solvers Making Provably Optimal Self-Improvements", 2003, arXiv:cs/0309048. A machine that may rewrite any part of itself, but only after finding a formal proof that the rewrite improves its utility. cmh swaps the proof for "passes tests, then survives a soak".

Benchmark-gated evolution of the agent

  • Eric Zelikman, Eliana Lorch, Lester Mackey, Adam Tauman Kalai, "Self-Taught Optimizer (STOP): Recursively Self-Improving Code Generation", 2023, arXiv:2310.02304. A scaffold that calls the model is run on its own source code and improves itself. The paper also measures how often the generated code bypasses a sandbox.
  • Shengran Hu, Cong Lu, Jeff Clune, "Automated Design of Agentic Systems" (ADAS), 2024, arXiv:2408.08435. A meta agent programs new agents in code.
  • Jenny Zhang, Shengran Hu, Cong Lu, Robert Lange, Jeff Clune, "Darwin Gödel Machine: Open-Ended Evolution of Self-Improving Agents" (DGM), 2025, arXiv:2505.22954. A coding agent edits its own code; children are checked on benchmarks (SWE-bench 20.0% to 50.0%). Its point that proving changes beneficial is impractical is cmh's reason for an empirical gate.
  • Wenyi Wang, Piotr Piękos, Li Nanbo, Firas Laakom, Yimeng Chen, Mateusz Ostaszewski, Mingchen Zhuge, Jürgen Schmidhuber, "Huxley-Gödel Machine: Human-Level Coding Agent Development by an Approximation of the Optimal Self-Improving Machine", 2025, arXiv:2510.21614. Today's score poorly predicts how good descendants will be: an argument for a soak over instant promotion.
  • Maxime Robeyns, Martin Szummer, Laurence Aitchison, "A Self-Improving Coding Agent" (SICA), 2025, arXiv:2504.15228. Edits its own agent system (17% to 53% on a SWE-bench Verified subset).

Live self-edits and online harness evolution

  • Xunjian Yin, Xinyi Wang, Liangming Pan, Li Lin, Xiaojun Wan, William Yang Wang, "Gödel Agent: A Self-Referential Agent Framework for Recursively Self-Improvement", 2024 (ACL 2025), arXiv:2410.04444. Monkey-patches its own running code, with no test gate or soak.
  • Chunqiu Steven Xia, Zhe Wang, Yan Yang, Yuxiang Wei, Lingming Zhang, "Live-SWE-agent: Can Software Engineering Agents Self-Evolve on the Fly?", 2025, arXiv:2511.13646. Evolves a bash-only scaffold while solving tasks: closest to cmh's online setting.
  • Jiahang Lin, Shichun Liu, Chengjun Pan, Lizhi Lin, Shihan Dou, Zhiheng Xi, Xuanjing Huang, Hang Yan, Zhenhua Han, Tao Gui, Yu-Gang Jiang, "Agentic Harness Engineering: Observability-Driven Automatic Evolution of Coding-Agent Harnesses", 2026, arXiv:2604.25850. Revertible edits, each with a prediction checked in the next round: close to gate plus soak.
  • Hangfan Zhang, Shao Zhang, Kangcong Li, Chen Zhang, Yang Chen, Yiqun Zhang, Lei Bai, Shuyue Hu, "Self-Harness: Harnesses That Improve Themselves", 2026, arXiv:2606.09498. Accepts a harness edit only after regression testing. Whether it has anything like a soak is unverified (we read only the abstract).

Memory as prose, memory as code

  • Noah Shinn, Federico Cassano, Edward Berman, Ashwin Gopinath, Karthik Narasimhan, Shunyu Yao, "Reflexion: Language Agents with Verbal Reinforcement Learning", 2023, arXiv:2303.11366. Written reflections on failures, like cmh's per-task lessons.
  • Aman Madaan, Niket Tandon, Prakhar Gupta, et al. (16 authors, last Peter Clark), "Self-Refine: Iterative Refinement with Self-Feedback", 2023, arXiv:2303.17651. Critique and refine with no external check.
  • Andrew Zhao, Daniel Huang, Quentin Xu, Matthieu Lin, Yong-Jin Liu, Gao Huang, "ExpeL: LLM Agents Are Experiential Learners", 2023 (AAAI 2024), arXiv:2308.10144. Insights carried across tasks.
  • Qizheng Zhang, Changran Hu, Shubhangi Upasani, et al. (last Kunle Olukotun), "Agentic Context Engineering: Evolving Contexts for Self-Improving Language Models" (ACE), 2025, arXiv:2510.04618. Prompts as evolving playbooks.
  • Guanzhi Wang, Yuqi Xie, Yunfan Jiang, Ajay Mandlekar, Chaowei Xiao, Yuke Zhu, Linxi Fan, Anima Anandkumar, "Voyager: An Open-Ended Embodied Agent with Large Language Models", 2023, arXiv:2305.16291. A library of code skills, each added after verification: the closest ancestor of cmh's tools.

Where cmh sits

Self-rewriting moved from proof-gated to benchmark-gated offline evolution, and recently to online evolution during real work; memory moved from prose to code:

                 gate:   proof        benchmark        tests + use
                         -----        ---------        -----------
 when it changes
   offline               Gödel        STOP ADAS
                         Machine      DGM HGM SICA
   online (while                      Live-SWE-agent   AHE, Self-Harness
   working)                                            cmh (+ soak)

 what is remembered:  prose (Reflexion, ExpeL, ACE)  ...  code (Voyager, Alita, cmh)

cmh sits in the online, code-memory, test-gated corner; its own addition is the soak. It also borrows from harnesses studied before the spec was written: samizdat (immutable kernel, a validate/soak/rollback gate, verdicts turned into durable knowledge), Prime Agent (versioned prompt notes, lessons and skills over an immutable base prompt), and autolith and oh-my-lisp (late-bound live redefinition) (SPEC.md:7-11). Prime Agent is also the baseline every harness in this book is measured against (Chapter 3).

What we found, in advance

In the first committed eval runs, every cmh harness scored at or near the Prime Agent baseline. On DeepSeek V4.1 Flash, Clojure, Rust and Racket each scored 102% of Prime, Lean 98% and Forth 114% (in a run where Prime itself fell to 88%); on GLM 5.3 Flash, Clojure scored 116%, Rust 113%, Racket 118% and Lean 116% (ROADMAP.md:17-18). On the later tool-reuse suites, Prime solved 32 of 32 episodes and only Racket matched it; Lean, Forth and WASM fell below the pass bar (Chapter 11). The roadmap is also blunt about where those points come from:

Most of the score comes from the shared design (lessons, reflection, the gate), not from self-modification: across about 60 episodes per flavor the agents proposed only 5 to 78 changes. The evals do not yet reward self-modification.

ROADMAP.md:23-26

The early evals had only two trials per suite, so differences of a few points are noise, and almost every task is solvable with bash alone. Later suites were built to reward reuse (Chapter 11), but whether self-modification makes the agent better is still mostly open.

Key takeaways

  • The goal: a substrate that never crashes from agent code, gives precise feedback, enforces clear rules, and keeps only changes that help.
  • Three rings: an immutable kernel, a versioned userspace (tools, notes, hooks), and durable knowledge (lessons, verdicts).
  • Changes enter only through propose_def and pass validate, trial and soak; late binding makes each one live on the next call.
  • Back pressure, precise feedback on failure, is how the agent learns; in the first harnesses bash still lets it "flip the board".
  • Language decides how much of the wall comes for free. WebAssembly is the practical stand-in for a unikernel per generation.
  • cmh sits in the online, test-gated, code-memory corner of the research; its own addition is the soak. So far most of its score comes from the shared design, not self-modification.
