Harness Engineering · Chapter 4

4. Clojure: eval into namespaces

The agent's code and the harness are written in the same language, and new code goes live as soon as it is evaluated

The first flavor of cmh, the "continual, self-modifying harness" from SPEC.md, is written in Clojure. That makes it a good place to start. The question every flavor has to answer is how text written by a model becomes a function the harness can call. In Clojure the answer is short: the language can already do this at runtime. The harness creates a fresh namespace, evaluates the agent's source inside it, and looks up a function by name. It needs no compiler step, no files on disk, no restart and no plugin system.

The kernel is 1,070 lines of Clojure in nine files under clojure/src/cmh/kernel/, with 214 lines of tests. (All 17 tracked files of the flavor, including tests, seeds, launcher and README, come to 1,427 lines.) It runs on the JVM, and its only runtime dependencies are Clojure 1.12.6 and data.json 2.5.2. This chapter explains the language briefly, then follows the code from the bottom up: how code is loaded, how state is kept, the gate, the loop, the tools, knowledge, hooks, seeds, the provider and the CLI. It ends with what Clojure makes easy and the one big thing it makes hard: keeping the agent's code from hurting the harness.

A tiny Clojure primer

Clojure is a Lisp that runs on the Java Virtual Machine. If you know Java, Python or JavaScript, a few ideas are enough to read every excerpt in this chapter.

Everything is an expression in parentheses. A function call puts the function first, inside the parentheses: (count xs) instead of count(xs), and (+ 1 2) instead of 1 + 2. Commas are optional and count as whitespace.

Data literals. [1 2 3] is a vector (an array-like list). {:name "bash" :kind "tool"} is a map (a dictionary). Words that start with a colon, like :name, are keywords: small interned names used as map keys. A keyword is also a function that looks itself up in a map, so (:name m) means m["name"]. #{"a" "b"} is a set, and a set used as a function tests membership.

Defining things. (defn run [input] ...) defines a function named run with one parameter. (def x 3) defines a value. (let [a 1 b 2] ...) binds local names. #(...) is a short anonymous function whose argument is %.

Data is immutable. (assoc m :k v) returns a new map with one key changed and leaves m alone. To have something that changes over time, Clojure uses an atom: a box holding one immutable value. @a reads the box, and (swap! a f) replaces its contents with (f old). By convention, functions with side effects end in !.

Threading macros. (-> x (f a) (g b)) means (g (f x a) b). It is a pipeline that passes the value along as the first argument. ->> passes it as the last argument instead.

Namespaces and vars. This idea carries the whole chapter. Clojure code lives in namespaces, which are like Java packages or Python modules. Unlike those, a namespace is an ordinary object in the running program: you can create one with create-ns, fill it, look inside it with ns-interns, and delete it with remove-ns. Each defn creates a var, a named, mutable slot in the current namespace that holds the function. Finally, load-string reads a string of Clojure source and evaluates it, just as the REPL (the interactive prompt) does. Clojure compiles each form to JVM bytecode on the fly.

Lisps are homoiconic: programs are written as the language's own data structures (lists, vectors, maps). Chapter 1 explains why that matters for self-modification. In practice it means Clojure ships the parts an agent harness needs, a reader and eval, as ordinary library functions in clojure.core.

Here is a complete userspace tool, the seed word_count. It is three lines long:

;; Tool: (run input) -> string, input is a keyword-keyed map.
(defn run [input]
  (str (count (re-seq #"\S+" (str (:text input))))))
clojure/seed/word_count.clj:1-3

Read it from the inside out: take :text from the input map, make sure it is a string, find every run of non-space characters (re-seq with a regex literal #"\S+"), count them, and turn the count back into a string. Every tool the agent writes has this shape: a function named run that takes a map and returns a string.

How eval into versioned namespaces works

The idea is simple. Every version of every definition gets its own namespace. Evaluating the source there creates the vars, and the kernel finds the entry var by name when it needs it. Switching versions only moves a pointer in the state.

propose_def word_count v2 │ ▼ cmh.scratch.word_count.<uuid> load source, find (defn run ...), (throwaway namespace) run the agent's tests │ ── always remove-ns afterwards │ tests pass ▼ state: :defs "word_count" :live 2 ← only a number changes │ ▼ next call cmh.user.word_count.v2-9f1c03a4b2e7 created and loaded lazily, (one namespace per version) then var "run" is looked up and called

(The hash in the diagram is made up; the real one is the first 6 bytes of the SHA-256 of the source, written as 12 hex digits.)

Loading source into a namespace

Everything goes through one function, load-into!:

(defn load-into!
  "Create namespace ns-sym, which must not exist yet, and evaluate source
  inside it. On failure the namespace is removed again."
  [ns-sym source ms]
  (let [n (create-ns ns-sym)]
    (try
      (with-timeout ms (fn []
                         (binding [*ns* n]
                           (refer-clojure)
                           (load-string source))))
      n
      (catch Throwable e (remove-ns ns-sym) (throw e)))))
clojure/src/cmh/kernel/evaluator.clj:48-59

*ns* is a special var that names "the current namespace". binding sets it temporarily, so every defn in the agent's source lands in the new namespace and not in the kernel's. refer-clojure makes the core library (defn, str, map …) visible there. The agent can also (require ...) any other library on the classpath, and the propose_def description says so.

Finding the entry point is a map lookup. ns-interns returns a map from symbol to var for one namespace:

(defn entry-fn [n sym]
  (let [v (get (ns-interns n) sym)]
    (when (and (var? v) (fn? @v)) v)))
clojure/src/cmh/kernel/evaluator.clj:61-63

The entry names are fixed. Tools define run, and the two hooks define compose-system and select-lessons (a small hooks table, evaluator.clj:27-36).

Scratch validation

Before a proposal goes live, it is loaded into a namespace with a random name and tested there. The finally clause deletes that namespace whatever happens, so a broken proposal leaves nothing behind:

(defn validate-in-scratch
  "Evaluate source in a fresh scratch namespace, check the entry point and
  run the tests. The scratch namespace is always removed, so a failing
  proposal never touches the live version's namespace. nil = ok."
  [{:keys [kind name source tests]} ms]
  (let [ns-sym (symbol (str "cmh.scratch." name "." (random-uuid)))]
    (try
      (let [n (load-into! ns-sym source ms)
            sym (entry-sym kind name)]
        (if-let [v (entry-fn n sym)]
          (run-tests kind name v tests ms)
          (str "source must define (defn " sym " ...)")))
      (catch Throwable e (str "eval failed: " (describe-error e)))
      (finally (when (find-ns ns-sym) (remove-ns ns-sym))))))
clojure/src/cmh/kernel/evaluator.clj:105-118

The {:keys [kind name source tests]} in the parameter list is destructuring: it pulls those four keys out of the map argument into local names. The test late-binding checks afterwards that no namespace starting with cmh.scratch. is left (kernel_test.clj:70-71).

A test is {"input": {...}, "expect": "..."}. It passes when the output contains expect as a substring. Non-string results, such as the id list from select_lessons, are JSON-encoded before the comparison (run-tests, evaluator.clj:89-103).

Late binding: look it up on every call

Live versions are named cmh.user.<name>.v<N>-<hash>. The hash of the source keeps two kernels in one JVM (as happens in the tests) from sharing a namespace by accident. The namespace is created lazily, on the first call:

(defn live-entry
  "Resolve the entry var of a live record, loading its namespace on first use."
  [{:keys [kind name version source]} ms]
  (let [ns-sym (live-ns-sym name version source)
        n (locking load-lock (or (find-ns ns-sym) (load-into! ns-sym source ms)))]
    (or (entry-fn n (entry-sym kind name))
        (throw (ex-info (str "entry point " (entry-sym kind name) " missing in " ns-sym) {})))))
clojure/src/cmh/kernel/evaluator.clj:132-138

The caller, gate/call-live, reads the live record from the state atom at call time, resolves the var, calls it, and records the use:

(defn call-live
  "Late-bound call: look up the live version of name now, call it, record the
  use. Returns {:ok true :value v} or {:ok false :error e}, plus :version,
  :status, or {:missing true} when nothing is live."
  [k name input input-desc]
  (if-let [rec (st/live-record @(:state k) name)]
    (let [res (try {:ok true
                    :value (ev/invoke (:kind rec) name (ev/live-entry rec (:validate-ms k))
                                      (ev/args-for (:kind rec) name input) (:call-ms k))}
                   (catch Throwable e {:ok false :error (ev/describe-error e)}))]
      (record-use! k rec (:ok res) (:error res) input-desc)
      (assoc res :version (:version rec) :status (:status rec)))
    {:ok false :missing true :error (str "no live definition named " name)}))
clojure/src/cmh/kernel/gate.clj:111-123

This is the key design choice of the flavor. The kernel never keeps a function reference between calls. It keeps data (which version is live) and turns that into a function only at the last moment. So going live and reverting are both a change to one number in a map. The late-binding test checks the result directly: right after propose! returns, the very next call in the same process gets "words=3" from v2 and no longer "3" from v1 (kernel_test.clj:62-69).

State and the journal

As Chapter 2 explains, the journal (<state>/journal.jsonl, with the state dir defaulting to .cmh) is the only source of truth. Clojure's immutable data fits this well. The in-memory state is one immutable map, {:defs {} :knowledge {} :order [] :tasks []}, and every change is a pure function from (old state, event) to new state. Here are the two branches that move the live pointer back and forth:

    "def_kept"
    (-> st (set-status name version "kept")
        (assoc-in [:defs name :live] version)
        (assoc-in [:defs name :kept] version)
        (assoc-in [:defs name :uses] 0))

    "def_reverted"
    (let [d (get-in st [:defs name])]
      (-> st (set-status name version "reverted")
          (assoc-in [:defs name :versions version :error] (:error ev))
          (cond-> (= version (:live d)) (assoc-in [:defs name :live] (:kept d)))
          (assoc-in [:defs name :uses] 0)))
clojure/src/cmh/kernel/state.clj:48-59

A revert sets :live back to :kept. If nothing was ever kept, that is nil, and the definition disappears. Replay is a single line, (defn replay [events] (reduce apply-event empty-state events)) (state.clj:92). Live updates use the same function:

(defn emit!
  "Append one event to the journal and apply it. The event is round-tripped
  through JSON first so live state equals replayed state exactly."
  [k ev]
  (locking (:state k)
    (let [line (json/write-str (assoc ev :ts (str (Instant/now))))
          ev' (json/read-str line :key-fn keyword)]
      (with-open [w (io/writer (:journal k) :append true)]
        (.write w (str line "\n")))
      (swap! (:state k) apply-event ev')
      ev')))
clojure/src/cmh/kernel/state.clj:94-104

The JSON round trip is a small but careful detail. The event is written, read back, and only the read-back copy is applied. Anything JSON cannot represent (a keyword value becomes a string, a set becomes a vector) is changed the same way live as it will be on replay. That is why the persistence test can check that a kernel reopened from the journal has exactly the same state map, compared with plain = (kernel_test.clj:137). When the journal is read, unparseable lines are skipped, with the comment "torn final line after a crash" (state.clj:89).

The eleven event types are def_proposed, def_rejected, def_trial, def_use, def_kept, def_reverted, lesson_added, lesson_scored, lesson_retired, task_started and task_finished. Even the soak counters need no event of their own: apply-event increments :uses on a def_use only when the use was ok, the version is live, and its status is trial (state.clj:41-46). Replaying the journal therefore rebuilds the counters for free.

The compiled namespaces are only a cache. A fresh process has none of them, and live-entry reloads each live version the first time it is called.

The gate

propose_def is the only way userspace changes. gate/propose! (gate.clj:57-92) runs in four stages:

  1. Static check (gate.clj:24-39). The name must match [A-Za-z][A-Za-z0-9_-]{0,63}. The kind must be tool, note or hook, and an existing definition cannot change kind. A tool cannot take a kernel tool's name. A hook must be called compose_system or select_lessons. The source must not be empty. Tools and hooks need at least one test. A tool's input_schema must be a map; a missing one defaults to {"type": "object"} (gate.clj:68-69).
  2. Journal the proposal. If the proposal has a name, it is written as def_proposed even when the static check failed. Only nameless proposals are rejected without a journal entry (comment at gate.clj:71-73).
  3. Validate in scratch (not for notes, which are plain text), under the 10-second limit. On failure the gate emits def_rejected and tells the model the error, ending with "(live version unchanged)".
  4. Go live as a trial. If the current live version is itself still a trial, it is reverted first with "superseded by vN". Then def_trial makes the new version live at once.

Models sometimes send structured fields as JSON-encoded strings, so a small helper, parse-json-ish, accepts tests and schemas in either form (gate.clj:17-22).

Soak: kept after three clean uses, reverted on the first error

(defn record-use!
  "Journal one use and run soak accounting for trial versions."
  [k {:keys [name version status] :as rec} ok error input-desc]
  (st/emit! k {:type "def_use" :name name :version version :ok ok :error error})
  (when (= "trial" status)
    (if-not ok
      (revert! k rec error input-desc)
      (let [uses (get-in @(:state k) [:defs name :uses] 0)]
        (when (>= uses (:soak k)) (keep! k rec uses))))))
clojure/src/cmh/kernel/gate.clj:101-109

Only trials are judged. A kept version that throws returns an error to the model but is never reverted (kernel_test.clj:123-126). Both keep! and revert! also write a verdict, a knowledge entry the agent will see in later prompts. The soak-revert test checks this one with a regex:

def word_count v2 ("ratio-based count") reverted: ArithmeticException: Divide by zero on input {"text":""}

Notes are never called, so they soak over tasks instead. soak-notes! (agent.clj:213-220) counts one use for each note that was on trial when the task started and is still that live version. A successful task is a clean use, and a failed one reverts the note with "task failed: …".

rollback_def does not flip any switch. It takes the old version's fields and proposes them again as a new version through the full gate (gate.clj:94-99), so the old code is re-validated. As far as the code shows, it accepts any recorded version, including one that was rejected; the gate would simply reject it again if it still fails.

The agent loop

run-task! (agent.clj:239-251) is short. It makes a random UUID as the task id, selects lessons, snapshots the notes on trial, emits task_started, runs the turn loop, and finishes the task. The loop itself is a Clojure loop/recur over the message list:

  (loop [messages [{:role "user" :content task}] tool-errors [] turn 0 answer ""]
    (if (>= turn (:max-turns k))
      (do (swap! errors conj "max turns exceeded")
          {:stop_reason "max_turns" :answer answer :tool-errors tool-errors})
      (let [resp (try (provider/complete (:provider k)
                                         {:system (system-blocks k errors lesson-ids)
                                          :messages messages
                                          :tools (tool-list k)})
                      (catch Throwable e
                        (swap! errors conj (str "model request failed: " (ev/describe-error e)))
                        (st/trace k "[kernel] model request failed: " (ev/describe-error e))
                        nil))]
clojure/src/cmh/kernel/agent.clj:184-195

Note what is inside the loop: system-blocks and tool-list are rebuilt for every model request. If the agent proposes a new tool in turn 1, the tool is in the tool list of turn 2. If it redefines the compose_system hook, the next request already uses the new system prompt. The tests check both cases (kernel_test.clj:204 and hook-redefinition, :146-159). In a mock run, a three-request task produced three def_use compose_system events.

The loop continues while the response's stop_reason is tool_use and the response contains tool_use blocks. It runs them in order, appends the tool results as the next user message, and recurs. Otherwise it returns. The last non-blank assistant text becomes the answer.

Deciding whether the task succeeded

(defn- finish-task!
  "Journal the outcome, score the selected lessons, soak trial notes and
  reflect. Returns result with :success :error :errors added."
  [k {:keys [id errors lesson-ids trial-notes transcript]} {:keys [stop_reason tool-errors] :as result}]
  (let [error (cond (seq @errors) (str/join "; " @errors)
                    (not= "end_turn" stop_reason) (str "stop_reason " stop_reason)
                    (some true? (take-last 2 tool-errors)) "tool error in final tool results")
        success (nil? error)]
    (st/emit! k {:type "task_finished" :id id :success success :error error})
    (st/trace k "[task] " (if success "success" (str "failed: " error)))
    (kn/score! k lesson-ids success)
    (soak-notes! k trial-notes success error)
    (when (:reflect k)
      (swap! transcript conj (str "OUTCOME: " (if success "success" (str "failed: " error))))
      (reflect! k (str/join "\n" @transcript)))
    (assoc result :success success :error error :errors @errors)))
clojure/src/cmh/kernel/agent.clj:222-237

A task fails if the kernel recorded any error (a failed model request, a failed hook, too many turns), if the model stopped for any reason other than end_turn, or if either of the last two tool results was an error. Otherwise it succeeds. That is a self-report, not a check of the answer; the ROADMAP lists it as a gap.

Prompt assembly and the two hooks

The system prompt has at most two blocks, and the first one is fixed:

(defn system-blocks [k errors lesson-ids]
  (let [sup (supplemental k errors lesson-ids)]
    (cond-> [{:type "text" :text (:base-prompt k)}]
      (not (str/blank? sup)) (conj {:type "text" :text sup}))))
clojure/src/cmh/kernel/agent.clj:106-109

Block 1 is the base prompt from base-prompt.md. Block 2, the "supplemental" prompt, is left out when empty; it is where userspace has a say. supplemental (agent.clj:92-104) collects the source text of every live note and the text of the selected lessons, then calls the compose_system hook with both lists. Afterwards it always appends a "## Verdicts on past userspace changes" section with the last 20 verdicts. No hook can hide the history of the agent's own changes, or remove the base prompt.

The other hook, select_lessons, picks which lessons go into the prompt. It receives the task text and the active lessons as maps with :id :text :score and returns a list of ids. The kernel is suspicious of the answer: it turns every id into a string, drops ids that do not exist, and removes duplicates (agent.clj:82-90). With no active lessons it returns [] without calling the hook at all.

Both hooks go through call-hook, which shows what happens when userspace fails at a moment the kernel cannot skip:

  (loop [tries 0]
    (let [r (gate/call-live k name input desc)]
      (cond
        (:ok r) (:value r)
        (:missing r) (fallback)
        (and (= "trial" (:status r)) (zero? tries)) (recur 1)
        :else (do (swap! errors conj (str name " v" (:version r) ": " (:error r)))
                  (st/trace k "[kernel] hook " name " failed: " (:error r) "; using builtin")
                  (fallback))))))
clojure/src/cmh/kernel/agent.clj:72-80

If a trial version fails, call-live has already reverted it, so the restored version is tried once. If no definition exists, a builtin fallback is used. Any other failure also uses the builtin, but the error is recorded and the task will be marked as failed. A broken hook therefore never stops the agent from working, but it does show up in the score.

Here is the write_file guard. It compares canonical paths, so .. segments and symlinks are resolved before the check:

(defn- write-file [k {:keys [path content]}]
  (cond
    (str/blank? path) {:content "path is required" :is_error true}
    (inside? path (:state-dir k)) {:content "refused: path is inside the state dir" :is_error true}
    (inside? path (:kernel-dir k)) {:content "refused: path is inside the kernel source" :is_error true}
    :else (let [f (io/file path)]
            (when-let [parent (.getParentFile (.getAbsoluteFile f))] (.mkdirs parent))
            (spit f (str content))
            {:content (str "wrote " (count (str content)) " chars to " path)})))

Lessons, verdicts and reflection

knowledge.clj holds two kinds of entries: lessons (ids L1, L2 …) and verdicts (V1 …). A new lesson whose text matches an existing one after normalizing whitespace and case is skipped (knowledge.clj:15-31). recall matches on shared words of three or more letters or digits.

Scoring is crude on purpose:

(defn score!
  "+1 to each selected lesson on success, -1 on failure; retire at <= -3."
  [k ids success?]
  (doseq [id ids]
    (let [l (get-in @(:state k) [:knowledge id])]
      (when (and l (= "lesson" (:kind l)) (not (:retired l)))
        (let [score ((if success? inc dec) (:score l))]
          (st/emit! k {:type "lesson_scored" :id id :delta (if success? 1 -1) :score score})
          (when (<= score retire-at)
            (st/emit! k {:type "lesson_retired" :id id})
            (st/trace k "[lesson] " id " retired at score " score)))))))
clojure/src/cmh/kernel/knowledge.clj:41-51

Every lesson that was put in the prompt shares the credit or the blame for the whole task. A lesson whose score reaches −3 (for a new lesson, three failed tasks in a row) is retired, and retired lessons are neither selected nor scored again (test lesson-scoring).

After each task, reflect! (agent.clj:144-162) makes one more model call with only the base prompt as system and no tools. It sends a compact transcript: the task, assistant texts clipped to 400 characters, one line per tool call with its input and result each clipped to 200, and the outcome. It asks for "only a JSON array of 0 to 3 short, reusable lessons". The kernel takes the text from the first [ to the last ] in the reply, parses it, keeps strings of at most 400 characters, adds up to three of them, and only traces errors. --no-reflect turns this off.

refine is a task like any other, with a fixed prompt built from the last 10 tasks, the last 15 verdicts, the definitions table and the active lessons. The prompt asks for "at most 3 changes" and allows "make no changes and say so" (agent.clj:253-275).

Seeds

A fresh state dir is not empty. When the journal has no events, install-seeds! (agent.clj:25-30) reads seed/seeds.edn (EDN is Clojure's data format, like JSON with keywords and sets) and writes each seed as a def_proposed version 1 followed by def_kept. The seed select_lessons takes up to 8 lessons that share a word of four or more letters with the task, best score first, and falls back to the top 3. Seeds are not special: they are kept version 1 of ordinary definitions, and the agent can replace them through the gate like anything else.

The provider

provider.clj talks to the Anthropic Messages API using the JDK's own java.net.http.HttpClient. This is Java interop: (HttpClient/newBuilder) calls a static Java method, and (.build x) calls an instance method. It forces HTTP/1.1, with a 30-second connect timeout and a 600-second request timeout. The base URL comes from ANTHROPIC_BASE_URL (the eval suite points it at a proxy), and authentication uses an API key or an OAuth token from the environment. Every request asks for max_tokens 32000. Responses are parsed with :key-fn keyword, so tool inputs arrive as keyword-keyed maps, exactly what a run function expects. The retry loop:

         (loop [attempt 0]
           (let [resp (.send client http-req (HttpResponse$BodyHandlers/ofString))
                 status (.statusCode resp)
                 text (.body resp)]
             (cond
               (= 200 status) (json/read-str text :key-fn keyword)
               (and (#{429 500 502 503 529} status) (< attempt 4))
               (do (Thread/sleep (long (* 2000 (Math/pow 2 attempt)))) (recur (inc attempt)))
               :else (throw (ex-info (str "anthropic API error " status ": "
                                          (subs text 0 (min 800 (count text))))
                                     {:status status})))))))}))

It retries up to four times on 429, 500, 502, 503 and 529, waiting 2, 4, 8 and then 16 seconds. Network exceptions (as opposed to error statuses) are not retried. The model defaults to claude-sonnet-5-5, overridden by CMH_MODEL or --model.

The mock provider (provider.clj:18-32) replays a script of response content arrays in order and records every request it receives in an atom. It infers stop_reason from the content (any tool_use block means tool_use). The tests use it to look at exactly what the model would have been sent.

Building and testing

Nothing needs to be built ahead of time; Clojure compiles as it loads. From clojure/:

clojure -X:test                 # or: clojure -M:test
clojure -M:run defs             # print the registry
bin/cmh run "TASK"              # one task, in the current directory

The test alias in deps.edn adds test/ to the path and Cognitect's test-runner (v0.5.1). Running it on the current tree prints:

Ran 10 tests containing 66 assertions.
0 failures, 0 errors.

The run takes under 10 seconds on this orb (Clojure CLI 1.12.6.1673, OpenJDK 27.0.1). The ten tests are seeds-pass-their-own-tests, late-binding, gate-rejection, soak-revert, soak-revert-removes-new-definition, soak-keep, persistence, hook-redefinition, lesson-scoring and end-to-end-run. They cover the eight tests SPEC.md requires, plus the seeds checking themselves and the case where reverting a brand-new definition removes it. Each test uses a temporary directory and the mock provider; all but the last open a kernel directly, with reflection off and a silent trace. The end-to-end test instead drives main/run-cli with *out* and *err* bound to string writers, so it checks what a user would actually see.

The flavor has had two commits, both on 2026-10-29: the first created all 17 files, and a later "simplify for readability" commit (+182/−135 over 9 files) split run-task! into the turn loop, tool uses, outcome and note soak, and added the hook table. Its message records the check used: "No behavior change: tests pass and a mock run gives identical stdout, stderr and journal." Because the journal is deterministic apart from timestamps and ids, it doubles as a regression oracle.

In the committed eval results (Chapter 11), the Clojure flavor solved 48 of 48 episodes on DeepSeek V4.1 Flash (102% of Prime Agent's rate, median 27.6 s per episode, 2,671,200 tokens). On GLM 5.3 Flash it reached 92% overall, 116% of Prime, with 83% learning transfer and 880,669 tokens. These numbers come from two trials and are noisy, and the ROADMAP is blunt about what they mean: "Most of the score comes from the shared design (lessons, reflection, the gate), not from self-modification." It adds that across about 60 episodes per flavor, the agents proposed only 5 to 78 changes. In the later isolated reuse matrix (four reuse suites, one trial, DeepSeek V4.1 Flash), Clojure passed 28 of 32 episodes (88%) against Prime's 32 of 32; Chapter 11 has the details.

The safety wall, and where it stops

The kernel enforces a few clear rules:

  • Kernel tools cannot be redefined, hooks are limited to the two known names, and a definition cannot change kind (gate.clj:30-33).
  • write_file refuses the state dir and src/cmh/kernel/, after resolving the path.
  • Loading and tests get 10 seconds, and live calls get 30.
  • A tool must return a string, and select_lessons a sequence of ids (check-return, evaluator.clj:65-75).
  • Any exception from userspace is caught, becomes an error message for the model, and reverts a trial.
  • The base prompt and the verdicts section are added by the kernel, outside any hook.

Here is the timeout:

(defn with-timeout
  "Run f on another thread; throw TimeoutException after ms."
  [ms f]
  (let [fut (future (f))
        r (try (deref fut ms ::timeout)
               (catch ExecutionException e (throw (or (.getCause e) e))))]
    (when (= r ::timeout)
      (future-cancel fut)
      (throw (TimeoutException. (str "timed out after " ms " ms"))))
    r))
clojure/src/cmh/kernel/evaluator.clj:10-19

There is no sandbox. The agent's code runs in the kernel's own JVM with full access to Clojure and Java. The research for this book confirmed it by running code in a throwaway copy: a proposal that called (spit "/tmp/...") at load time created the file during scratch validation, before any test ran. The same code could read any file or environment variable, including the API key. Judging from the code, it could also call System/exit or redefine kernel vars.

The timeout does not stop anything. future-cancel only interrupts the thread. A busy loop that never checks for interruption keeps running after the TimeoutException; this was also observed. The kernel moves on, but a core keeps spinning until the process exits.

The ROADMAP says the same thing in its status table: "Agent code can crash the harness: yes (no sandbox)" and "Runaway loop is actually stopped: no (thread keeps running)". It adds two gaps that every flavor shares. First, bash can do anything, including editing the kernel source or the journal, which makes the write_file guard a courtesy, not a wall. "In chess terms, the agent can flip the board." Second, old versions leak: remove-ns is only called on scratch namespaces and failed loads, so every superseded cmh.user.* namespace stays in memory. One smaller gap: write_file does not protect ../base-prompt.md, seed/ or bin/. SPEC does not require it to, but the Racket flavor does protect the base prompt.

The proposed fix is to run Clojure userspace out of process, in a forked worker or a WASM module, so a crash or runaway loop only kills the worker. That change would also remove what makes this flavor elegant: calling userspace would no longer be a plain function call.

What Clojure makes easy, and what it makes hard

EasyHard
Loading new code at runtime: create-ns + load-string, all in clojure.coreIsolation: the JVM has no in-process sandbox for this, so the agent's code shares a heap and permissions with the kernel
Late binding: vars are looked up by name, so switching versions is moving a pointerStopping code: JVM threads can only be asked to stop, and interruption is cooperative
One language: userspace is the host language, with the whole standard library and Java behind itUnloading: namespaces hold onto classes, and nothing in the kernel removes old versions
Event sourcing: immutable maps, a pure apply-event, replay with reduceFeedback quality: errors are raw JVM exception text such as ArithmeticException: Divide by zero, not structured diagnostics
Small code: the whole kernel is 1,070 linesNo scratchpad: to try a snippet, the agent must propose a definition and pass the gate

The last row points to an improvement the ROADMAP lists: an eval tool that runs load-string in a throwaway namespace and returns the result. The machinery already exists in validate-in-scratch. The ROADMAP reports that in the Forth flavor the equivalent tool, forth_eval, cut rejected proposals from 69 to 0. In Clojure it would also make the missing sandbox matter more, since arbitrary code would then run on every call to it.

The Clojure flavor gives a clear baseline for the rest of the book. Self-modification can be very cheap when the language already treats code as data and namespaces as values. That cheapness comes from running the agent's code with all the kernel's power. The next chapter keeps the same Lisp idea and adds the piece this one lacks: Racket's sandboxed evaluators, which give the agent's code memory and time limits that are actually enforced.

Key takeaways

  • Every version of every definition is evaluated into its own namespace, cmh.user.<name>.v<N>-<hash>. Proposals are tested first in a throwaway cmh.scratch.* namespace that is always removed.
  • The kernel holds data, not functions: it looks up the live version and its entry var on every call. Going live and reverting each change one number in the state.
  • State is an immutable map updated by a pure apply-event. Live updates and replay use the same function, and a JSON round trip in emit! makes them match exactly.
  • The system prompt and tool list are rebuilt on every model request, so a new tool or hook takes effect on the very next turn.
  • 1,070 lines of kernel and 10 tests with 66 assertions, all passing. The flavor reached 102% of Prime on DeepSeek V4.1 Flash and 116% on GLM 5.3 Flash, mostly thanks to the shared design rather than self-modification.
  • The wall is thin: no sandbox, timeouts that do not stop threads, bash unrestricted, and old namespaces never freed. The ROADMAP's answer is out-of-process userspace and a scratchpad eval tool.
