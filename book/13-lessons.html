Harness Engineering · Chapter 13

13. What we learned and what comes next

Seven harnesses side by side, how the project got here, what is still open, and the experiments that would settle it

Chapters 3 to 10 went one harness at a time. This one sets them side by side. First we compare all seven flavors against the four yardsticks from the start of the book. Then we look at which language suits which goal, retell the project's history from its git log, check the ROADMAP against what was built after it, and end with the questions and experiments that are still open.

A reminder of the goal, as ROADMAP.md puts it in one sentence: "a substrate the agent can program itself on, which never crashes from the agent's code, answers every mistake with precise feedback, enforces clear rules, and keeps only the changes that make the agent better." No flavor meets all four parts. Each one trades some parts for others, and the trades are the most useful thing the project produced.

The seven flavors side by side

The table uses three terms from earlier chapters. Crash safety asks whether agent-written code can kill the harness process. Hang safety asks whether an endless loop in agent code is actually stopped, or only abandoned while its thread keeps burning CPU. Feedback quality describes what the model gets back when its code fails. The eval columns come from two kinds of run. The committed 15-suite runs (Chapter 11) are non-isolated, use 2 trials, and give scores as a percentage of Prime Agent's. The isolated reuse matrix of 12-13 November used one trial on DeepSeek V4.1 Flash and gives passes out of 32.

Prime Agent, the baseline, scored 98% (DeepSeek) and 79% (GLM) on the committed suites, and 32/32 on the reuse matrix with the fewest tokens of anyone (4.54 M).

Read the eval column with care. The reuse matrix ran one trial. Orb pauses hit five of the seven harnesses: every one of the matrix's 9 timeouts overlapped a pause, and 4 of its failures are pause artifacts. Count those four as passes and Forth goes up to 84% (27/32), which clears the 80%-of-Prime bar. Prime and Racket never overlapped a pause, by scheduling luck. Before that, the committed runs showed Prime's own learning-transfer score swinging from 94% to 67% between two runs with the same setup. The differences between flavors are real signals, but they are not rankings.

One column is missing from the table because the answer is almost the same everywhere: bash. Every flavor gives the agent a shell, and in six of them the shell can edit the kernel, the journal and anything else. The ROADMAP's line for this is "In chess terms, the agent can flip the board." Only the WASM flavor runs bash in a mount namespace with the state dir, wasm/ and the base prompt read-only, and only when unprivileged user namespaces are available. Roc checks the paths of its file requests against host rules, but its README admits that a Bash request "can break every rule, as in the other flavors".

Which language suits which goal

The flavors differ less in how well they solve tasks than in what they make cheap. A rough guide:

  • You want live redefinition with the least code: Clojure. load-string plus lookup by name is late binding almost for free, and the kernel is about 1,070 lines. The price is that there is no wall at all: agent code can read any file, any environment variable, or call System/exit.
  • You want a real wall without building one: Racket. racket/sandbox already does time and memory limits, file and network denial, and an exit that only kills the evaluator. It was the only one of the first four flavors whose runaway loops were really stopped, and it tied Prime at 32/32 on the reuse matrix, though with 1.8 times the tokens. If you had to pick one flavor today, this is the strongest case.
  • You want the gate to reject wrong code before it runs: Rust or Lean. In Rust the compiler is part of the gate; in Lean, theorems in the proposal must be proved. Both pay for it at run time: the code runs in process, so neither stops a runaway thread, and Rust cannot survive a segfault. Lean also spent the most tokens in the matrix (16.7 M) and scored lowest (24/32).
  • You want safety and precise feedback by construction: Forth in WebAssembly. A language small enough to write its own VM means every failure can name the word, the stack and the input. Fuel and memory caps make hangs and blow-ups ordinary errors. The price is that the model must write Forth, which it knows far less well than Python.
  • You want the agent to change its own loop: the WASM flavor. It is the only flavor where the agent loop, the reflection prompt and the gate rules are open to change, through propose_kernel. The price is slow image builds (minutes cold), and so far no agent has used it: 48 local eval episodes show 0 propose_kernel calls against 218 forth_eval calls.
  • You want every effect to be visible and checkable: Roc. Pure functions cannot do I/O, so a tool returns a request (read this file, write that one) and the host decides whether to perform it. That makes every effect auditable. The price is a pre-release compiler, a Debug build at about 0.3 s per call round, and syntax the model keeps tripping on ("`then` isn't used in this Roc version").

Under all six choices sits one trade-off the evals made visible: strength of the wall against how familiar the language is to the model. In the reuse matrix, the three flavors with unfamiliar languages (Lean, Forth, WASM's Forth) spent 12.9 to 16.7 M tokens and lost the most passes. Turn-limit hits point the same way: WASM 5 and Forth 4, against 2 at most for every other flavor. Racket is the evidence that the trade-off is not forced: a Lisp the model knows reasonably well, inside a sandbox that came with the language.

The headline finding has not changed. ROADMAP said in October that "most of the score comes from the shared design (lessons, reflection, the gate), not from self-modification": across about 60 episodes per flavor, agents proposed only 5 to 78 changes. The reuse track was built to change that, and Prime, which does not rewrite a kernel in this sense, still scored 32/32 with the fewest tokens. The evals do not yet show self-modification paying off.

Of the thirteen experiments, experiment 1 (the tool-reuse suite) was done. Experiment 11 (a unikernel per generation) was approximated by the WASM component, because orbs have no KVM, and that also partly covers experiment 6 (agent loop as data). Experiment 2, the fresh-state control, was started twice and never finished under isolation. The rest are untouched.

Open questions

  • Does self-modification help at all, on any task? Every eval so far can be solved with bash and memory alone. A task where a self-made tool is clearly the cheapest path, and is measured that way, still does not exist.
  • Is the model-familiarity cost fixable? The scratchpad halved Forth's tokens, and Roc's roc_eval caught syntax mistakes before any proposal (19 of 44 probes failed in the first eval episode). Would a stronger model, or a better cheat sheet, close the gap with Racket? Or is "the language the model already knows" a permanent advantage?
  • Why do agents build narrow tools? In the Roc run, the agent built one tool per question and kept solving the next question in Python. It never built the general QLOG parser that lesson #1 told it to keep. Is that a prompt problem, a gate problem (tests cannot exercise a tool's error paths), or a model habit?
  • Will an agent ever rewrite its own kernel unprompted? WASM made it possible and safe. Nobody did it. That might mean the kernel is good enough, or that the payoff is invisible to an agent that thinks one task at a time.
  • What should "better" mean? Success is self-reported today, and a self-report can be gamed. The eval checkers are an independent verdict, but real work rarely has a checker.
  • How much of the remaining difference between flavors is noise? With one trial, pauses and a single model, we do not know yet.

Next experiments

Six experiments, ordered roughly by cost. The first two make every other number trustworthy.

1. An isolated fresh-state control

The runner already supports it. With --fresh-state, the state dir is wiped before every episode, so nothing carries over:

def run_suite(hname, h, suite_dir, spec, trial, model, port, usage, timeout, logs_dir, fresh_state=False,
              isolate=True):
    state = pathlib.Path(tempfile.mkdtemp(prefix=f"cmh-eval-state-{hname}-"))
    rows = []
    try:
        for number, ep in enumerate(spec["episodes"], start=1):
            if fresh_state:  # control: no memory carried between episodes
                shutil.rmtree(state, ignore_errors=True)
                state.mkdir()
            tag = f"{hname}.{suite_dir.name}.t{trial}.e{number}"
            r = run_episode(h, suite_dir, ep, number, state, model, port, usage, tag, timeout, logs_dir, isolate)
            r.update({"harness": hname, "suite": suite_dir.name, "track": spec["track"], "trial": trial,
                      "episode": number, "transfer": bool(ep.get("transfer")), "isolated": isolate})
            rows.append(r)
            print(f"[{hname}] {suite_dir.name} t{trial} e{number}: {'PASS' if r['passed'] else 'FAIL'} "
                  f"({r['seconds']}s, {r['usage']['requests']} req)", flush=True)
    finally:
        shutil.rmtree(state, ignore_errors=True)
    return rows

The only fresh-state numbers we have come from the non-isolated pilot: memory took Prime from 41% to 91% and Forth from 41% to 78%. Those fresh scores are inflated, because agents read the suites' setup.py files, so the real memory effect is probably larger. The isolated run (matrix-fresh) stopped after the first episode, and since rows are written per finished suite, it recorded nothing. Running it to completion is the cheapest way to learn how much of every learning number is memory and how much is the model.

2. More trials, and a fairer clock

Run the matrix and the control with three or more trials and report confidence intervals. Fix the instruments at the same time. The timeout uses wall-clock time, so orb pauses count against episodes; it should be monotonic and pause-aware, or the orb should be kept awake. Usage should keep errors that arrive after an episode ends: the matrix's "API errors 0" hides 3 upstream read timeouts. Cache-read tokens should be reported separately, since they dominate the token totals.

3. Scratchpads everywhere

This is the experiment with the largest measured effect per line of code. In Forth, forth_eval cut tokens from 7.81 M to 3.67 M, and ROADMAP reports rejected proposals falling from 69 to 0. In local logs, agents call it about 20 times as often as they propose (692 against 32). Roc's roc_eval caught syntax errors before any proposal. Clojure (a throwaway namespace), Racket (a throwaway evaluator), Lean (a scratch environment) and Rust (a throwaway worker) still make the agent propose a definition just to try code. Add the tool to each, then measure proposals, rejections and tokens before and after.

4. Tool search for self-made tools

Every flavor sends every live userspace tool on every request: "Userspace tools are added to the tool list on every model request, rebuilt from the live registry each time" (SPEC.md). That is fine for a few tools. It is the wrong shape for a harness meant to accumulate them over hundreds of tasks. Chapter 12 showed the alternative several harnesses use: tool search, where most tools are deferred and the model searches a catalog (usually with BM25 ranking) to load only the ones it needs. Anthropic reports gains on MCP evaluations from this, and deferred tools leave the prompt cache intact. Agent-written tools are exactly that long, growing tail. The experiment: defer userspace tools behind a search tool in one flavor, run a long-horizon sequence, and compare tokens and reuse against the eager list. It might also help with the narrow-tool problem, if searching shows the agent the tools it already has.

5. Fitness-based keeping

Today a trial version is kept once it has been used enough times without an error. Here is the whole rule in the Rust kernel:

    /// Records one use of a live definition and applies the soak rules.
    fn record_use(&mut self, name: &str, version: u32, error: Option<&str>, input: &Value) {
        self.rec("def_use", json!({"name": name, "version": version, "ok": error.is_none(), "error": error}));
        let Some(def) = self.state.defs.get(name) else { return };
        let Some(live) = def.live_version().filter(|l| l.version == version && l.status == "trial") else { return };
        let desc = live.description.clone();
        if let Some(err) = error {
            let verdict = format!("def {name} v{version} ({desc:?}) reverted: {} on input {}", first_line(err, 200), compact(input, 200));
            let restored = self.revert(name, version, err, verdict);
            let now = restored.map_or("definition removed".into(), |r| format!("live: v{r}"));
            trace(&format!("[gate] {name} v{version} reverted: {} ({now})", first_line(err, 100)));
        } else if def.soak_uses >= self.cfg.soak {
            let verdict = format!("def {name} v{version} ({desc:?}) kept after {} clean uses", def.soak_uses);
            self.rec("def_kept", json!({"name": name, "version": version, "verdict": verdict}));
            trace(&format!("[gate] {name} v{version} kept"));
        }
    }
rust/src/kernel/mod.rs:323-339

Nothing in it asks whether the change helped. The ROADMAP's fix is a fitness score per task (success from an independent checker where one exists, plus tokens, wall time and tool errors), with a change kept only if its score over the trial window is not worse than the previous version's. The eval checkers already give an independent success signal, so the evals are a natural first place to try it. The question is whether fewer but better changes stick.

6. A release build of Roc

The Roc flavor ships as a Debug build because a release build "needs more than 6 GB of RAM for the LLVM step and was OOM-killed in a 7.8 GB orb". Every Roc number so far carries that handicap: about 0.3 s per call round, gate runs of 17.7 s and 51.6 s in the eval, and 7 s just for the seed select_lessons in the gate. Building it with more memory (once, then reusing the binary) and rerunning the reuse track would separate the language's cost from the build's cost, and give Roc its first complete eval.

Key takeaways

  • Crash and hang safety are solved in four flavors (Racket, Forth, WASM, Roc) and unsolved in three (Clojure, Rust, Lean). bash is still the hole in all but WASM.
  • Only Forth and WASM give structured feedback. Only Forth, WASM and Roc have a scratchpad, and the scratchpad is the cheapest large win measured.
  • The main trade-off is wall strength against how familiar the language is to the model. Racket shows that you can have both.
  • Most of the score still comes from the shared design (lessons, reflection, the gate). No eval yet shows self-modification paying off, and the one flavor that can rewrite its own kernel has never done so in an eval.
  • The results are noisy: one trial, orb pauses, one model. An isolated fresh-state control and more trials come before any ranking.
  • The next experiments are concrete and mostly small: finish the control, add trials, add scratchpads everywhere, put self-made tools behind tool search, keep changes by fitness, and build Roc in release mode.
