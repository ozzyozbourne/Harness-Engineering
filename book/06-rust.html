6. Rust: a compiled library per definition

No eval, so the compiler becomes a subprocess and the dynamic loader becomes the hot-swap button

The Clojure and Racket flavors had it easy. Both languages can take a string of source code at run time and turn it into a working function, so "the agent proposes a new tool" becomes "the kernel evaluates the text". Rust has no such thing. A Rust program is compiled ahead of time into machine code, and once it is running there is no compiler inside it to call.

The Rust flavor of cmh (the shared harness design from chapter 2) still lets the agent write new Rust and use it a moment later, without restarting. It does this with two ordinary pieces of the Rust toolchain: cargo, run as a child process, and the operating system's dynamic loader, reached through the libloading crate. Each version of each definition becomes its own tiny shared library. This chapter walks through how that works, what it costs, and where it falls short.

Why Rust cannot just eval

An eval function takes program text and runs it inside the current process. Lisps have one because their compiler or interpreter is part of the runtime. In Rust, the compiler (rustc) is a separate, very large program. The binary you ship contains only machine code; the type checker and code generator stayed on the build machine.

So the question for this flavor was not "how do we eval Rust" but "what is the cheapest way to get new machine code into a running process". The answer most native programs use for plugins is a shared library: a file of compiled code (.so on Linux, .dylib on macOS, .dll on Windows) that a running program can open and call into. Rust can produce one if a crate is declared with crate-type = ["cdylib"], which means "a C-compatible dynamic library".

SPEC.md describes the Rust flavor in one line: userspace is "compiled by cargo into a cdylib and hot-loaded with libloading; the Rust compiler is part of the gate". The rest of the chapter unpacks that sentence.

agent: propose_def word_count v2 (Rust source) | v kernel writes <state>/build/word_count_v2/ Cargo.toml (generated, cdylib, depends on serde_json) src/lib.rs (generated wrapper: C ABI + catch_unwind) src/user.rs (the agent's source, verbatim) | v cargo build --offline ---- compile error? ----> trimmed rustc output | back to the model v libcmh_us_word_count_<hash>.so | v libloading: dlopen, look up cmh_abi / cmh_call / cmh_free | v run the tests on a worker thread (15 s timeout) | v trial goes live; the next call by name uses it

The approach: one generated crate per definition version

The design is stated at the top of userspace.rs, the file that does all the compiling and loading:

//! Userspace code: each definition version becomes a tiny generated cdylib
//! crate, compiled by `cargo` and hot-loaded with `libloading`.
//!
//! Generated crate (`<state>/build/<name>_v<N>/`):
//! - `src/user.rs`: the agent's source, verbatim (compiler errors point here).
//! - `src/lib.rs`: a kernel-written wrapper that exports C-ABI functions taking
//!   and returning JSON strings, frees its own allocations, and runs the user
//!   function under `catch_unwind` so panics become errors.
//!
//! Why one cdylib per version: a new version is a new library file with its
//! own symbols, so loading it never touches code an older version may still
//! be running, and replacing a definition needs no restart.
//!
//! Libraries are never unloaded (old versions are leaked on purpose), so
//! function pointers stay valid for the life of the process.
rust/src/kernel/userspace.rs:1-15

A crate is Rust's unit of compilation, roughly a package. For every proposed version the kernel writes a fresh one on disk. The agent only ever supplies src/user.rs. Everything around it is written by the kernel, so the agent cannot change how its code is called.

A few details matter here. The only dependency is serde_json, because every call passes JSON in and out. Debug info and incremental compilation are turned off to keep builds small and fast. The contracts

Userspace code must provide one function with a fixed signature. Which one depends on what kind of definition it is (README.md lists them):

pub fn run(input: &serde_json::Value) -> Result<String, String>                // tool
pub fn compose_system(notes: &[String], lessons: &[String]) -> String           // hook

The kernel does not parse the agent's Rust to check this. It writes a wrapper that calls user::run(&input) (or the hook function), and lets rustc complain if the signature is wrong. A type mismatch is a compile error, and a compile error rejects the proposal. The language's type system becomes a free static check. One of the spec tests proposes a tool whose body is just 42 and checks exactly that:

The C-ABI wrapper and catch_unwind

Rust does not have a stable binary interface between separately compiled Rust libraries, but it can export functions that follow the C calling convention, which every loader understands. The wrapper exports three such functions: cmh_abi() returns a version number for the wrapper itself, cmh_call(input) takes a C string of JSON and returns a C string of JSON, and cmh_free(p) frees a string that cmh_call returned. The library allocated the result, so the library must free it; mixing allocators across a library boundary is a classic source of crashes.

Agent code panics sometimes. A Rust panic is the language's way of aborting the current operation on a bug, such as an unwrap() on a missing value; by default it unwinds the stack, running cleanup code as it goes. Unwinding across an extern "C" boundary is not allowed, so the wrapper catches panics inside the library with std::panic::catch_unwind and turns them into ordinary errors. Because the wrapper is itself generated by a Rust format! string, its braces are doubled:

pub extern "C" fn cmh_call(input: *const c_char) -> *mut c_char {{
    static QUIET: std::sync::Once = std::sync::Once::new();
    QUIET.call_once(|| std::panic::set_hook(Box::new(|info| {{
        let at = info.location().map(|l| format!(" at {{}}:{{}}", l.file(), l.line())).unwrap_or_default();
        PANIC_AT.with(|p| *p.borrow_mut() = at);
    }})));
    let raw = unsafe {{ CStr::from_ptr(input) }}.to_string_lossy().into_owned();
    let result = match std::panic::catch_unwind(std::panic::AssertUnwindSafe(|| entry(&raw))) {{
        Ok(r) => r,
        Err(p) => {{
            let msg = p.downcast_ref::<&str>().map(|s| s.to_string())
                .or_else(|| p.downcast_ref::<String>().cloned())
                .unwrap_or_else(|| "non-string panic payload".into());
            Err(format!("panic: {{msg}}{{}}", PANIC_AT.with(|p| p.borrow().clone())))
        }}
    }};
rust/src/kernel/userspace.rs:320-335

The panic hook, installed once, records the file and line of the panic in a thread-local variable, so the error that reaches the model reads panic: empty text at FILE:LINE (spec test 3 checks for the panic: empty text part). The result goes back as {"ok": ...} or {"err": ...}.

Running cargo

The build is an ordinary cargo build subprocess. It runs offline first, because the usual case is that serde_json is already in the local cache and touching the network would only slow things down. Only if the failure mentions being offline does it try once more online:

    fn cargo_fetching_once(&self, dir: &Path) -> Result<std::process::Output, String> {
        let out = self.cargo(dir, true)?;
        // `--offline` fails with a message that mentions "offline" (for example
        // "you're using offline mode" or "--offline was specified") when a
        // dependency is not in the local registry cache yet, as on a fresh
        // machine. Fetch once then. Any other failure is a real compile error
        // and is reported as is (a compile error that happens to contain the
        // word only costs one redundant retry).
        if !out.status.success() && String::from_utf8_lossy(&out.stderr).contains("offline") {
            return self.cargo(dir, false);
        }
        Ok(out)
    }
rust/src/kernel/userspace.rs:141-153

The cargo call honors $CARGO, sets CARGO_TARGET_DIR to a shared directory, removes CARGO_BUILD_TARGET_DIR and CARGO_MANIFEST_DIR so the kernel's own environment does not leak into the child build, and turns colors off (userspace.rs:155-169). When the build fails, trim_compiler_output drops cargo's progress lines ("Compiling", "Downloading" and so on) and the generic "could not compile" line, caps the text at 4,000 bytes and prefixes it with compile error:. What remains is rustc's own diagnostic, pointing at lines in src/user.rs, which is exactly the agent's source. That is the back pressure: the model gets the same error a human would.

The content-hash cache

There is a subtle trap in loading shared libraries. If you ask the loader to open a file path it has already opened, it hands back the library it already has, not whatever is on disk now. If version 2 and version 3 of a tool were both built to libword_count.so, version 3 would silently run version 2's code. The kernel avoids this by naming every library after a hash of everything that goes into it:

/// Content hash of everything that goes into a library. It names the package
/// and the library file, so different code never shares a file name (the
/// dynamic loader would hand back the already-loaded one) and identical code
/// is compiled only once.
fn fnv1a(parts: &[&str]) -> u64 {
    let mut h: u64 = 0xcbf2_9ce4_8422_2325;
    for p in parts {
        for b in p.bytes().chain(std::iter::once(0)) {
            h ^= u64::from(b);
            h = h.wrapping_mul(0x100_0000_01b3);
        }
    }
    h
}

FNV-1a is a small, fast, non-cryptographic hash. It covers the wrapper version, the entry kind, the name and the source, so different code always gets a different file name, and identical code (a rollback, or the same seed in a new state directory) is compiled only once.

fn atomic_copy(from: &Path, to: &Path) -> Result<(), String> {
    if let Some(parent) = to.parent() {
        std::fs::create_dir_all(parent).map_err(|e| e.to_string())?;
    }
    // Copy to a fresh inode and rename over, so an already-mapped library is
    // never rewritten in place.
    let tmp = to.with_extension(format!("tmp{}", std::process::id()));
    std::fs::copy(from, &tmp).map_err(|e| format!("copy {} -> {}: {e}", from.display(), tmp.display()))?;
    std::fs::rename(&tmp, to).map_err(|e| format!("rename {}: {e}", to.display()))
}

All generated crates share one cargo target directory (<state>/target by default, or $CMH_TARGET_DIR), so serde_json is compiled once. After that, according to the README, "a typical proposal builds in about 0.1–0.3 s". The gate prints the cargo wall time of every build it triggers as [gate] cargo build NAME vN: X.Xs. The build directory is only a cache: if it is deleted, the kernel rebuilds each library from the source stored in the journal (spec test 5 does exactly this).

Loading with libloading

libloading is a thin, cross-platform wrapper over dlopen/dlsym (and their Windows equivalents). Opening a library and looking up its symbols is unsafe in Rust, because the compiler cannot check that the function in the file really has the signature you claim. The kernel's justification is that it wrote the wrapper itself and checks a version marker before trusting anything else:

    let lib = unsafe { Library::new(path) }.map_err(|e| format!("load {}: {e}", path.display()))?;
    let lib: &'static Library = Box::leak(Box::new(lib));
    // SAFETY: the symbols are exported by the generated wrapper with exactly
    // these signatures; the ABI marker guards against stale wrappers.
    unsafe {
        let abi: libloading::Symbol<unsafe extern "C" fn() -> u32> =
            lib.get(b"cmh_abi\0").map_err(|e| format!("missing cmh_abi: {e}"))?;
        if abi() != WRAPPER_ABI {
            return Err("stale userspace library (wrapper ABI mismatch)".into());
        }
        let call: libloading::Symbol<CallFn> = lib.get(b"cmh_call\0").map_err(|e| e.to_string())?;
        let free: libloading::Symbol<FreeFn> = lib.get(b"cmh_free\0").map_err(|e| e.to_string())?;
        Ok(Loaded { call: *call, free: *free })
rust/src/kernel/userspace.rs:186-198

Note Box::leak. It turns the library handle into a &'static reference that lives until the process exits, which means libraries are never unloaded. This is deliberate. Unloading a library while a function pointer into it still exists, or while an abandoned thread is still running inside it, would be a use-after-free in machine code. Leaking one library per version (the ones the tests built in rust/target are 840 KB to 1 MB each) is the safe trade. WRAPPER_ABI (currently 1) is part of the hash and is checked at load time, so changing the wrapper code invalidates every cached library.

Calling with a timeout

A model can write a loop that never ends. To keep that from freezing the whole agent, each call runs on a fresh worker thread with a 64 MB stack, and the kernel waits on a channel with a deadline. The call timeout is 15 seconds (call_timeout: Duration::from_secs(15) in mod.rs:98):

        let raw = match rx.recv_timeout(timeout) {
            Ok(r) => r?,
            Err(mpsc::RecvTimeoutError::Timeout) => {
                return Err(format!("timeout: no result after {:.1}s", timeout.as_secs_f64()));
            }
            Err(mpsc::RecvTimeoutError::Disconnected) => return Err("userspace worker died".into()),
        };
rust/src/kernel/userspace.rs:235-241

Both a caught panic and a timeout come back as an Err, and the gate counts an error as a failed use, so a bad trial is reverted. But read the timeout branch closely: it returns an error and walks away. Rust has no safe way to kill a thread, so the runaway thread is abandoned and keeps running (and burning CPU) until the process exits. The doc comment says so plainly: "the runaway thread is abandoned".

Why a library per version, not one library rebuilt each time? The comment in userspace.rs gives the reason: "a new version is a new library file with its own symbols, so loading it never touches code an older version may still be running, and replacing a definition needs no restart." Old and new versions coexist in memory, which is also what makes instant revert cheap: the kept version is still loaded.

The agent loop

Kernel::run_task (mod.rs:499-556) is the loop from chapter 2, written out plainly:

  1. Journal task_started and call the select_lessons hook to pick which lessons go in the prompt.
  2. For up to 40 turns (max_turns: 40): rebuild the system prompt and the tool list from scratch, call the model, and collect any text.
  3. If the model did not stop to use a tool, the loop ends. Otherwise run every tool_use block and send the results back, each with an is_error flag.
  4. Decide success, update notes, score lessons, journal task_finished, and reflect.

Rebuilding the prompt and tool list on every turn is what makes changes take effect mid-task. The end of the loop is worth reading because it shows how "success" is defined:

        let tail_ok = tool_errors.iter().rev().take(2).all(|e| !e);
        let success = kernel_error.is_none() && stop == "end_turn" && tail_ok;

        self.soak_trial_notes(task_id, task, success);
        self.score_lessons(task_id, &selected, success);
        let summary = first_line(&answer, 200);
        self.rec("task_finished", json!({"task_id": task_id, "success": success, "error": kernel_error, "summary": summary}));
        trace(&format!("[task] {task_id} {}", if success { "succeeded" } else { "failed" }));
        transcript.push(format!("OUTCOME: {}", if success { "success" } else { "failure" }));
        if self.cfg.reflect {
            self.reflect(&transcript.join("\n"));
        }
        TaskOutcome { success, answer, error: kernel_error }
    }
rust/src/kernel/mod.rs:543-556

A task succeeds only if the kernel saw no error (such as the turn limit or a failed model request), the model ended its turn normally, and neither of the last two tool results was an error. That last rule catches the common failure where a model's final command fails and it declares victory anyway.

Late binding

Late binding means a name is looked up when it is used, not when the calling code was written. Every userspace call goes through one function that looks up the live version by name, loads it (a hash-map hit after the first time), calls it and records the use:

    pub fn call_def(&mut self, name: &str, input: &Value) -> Result<String, String> {
        let Some(live) = self.state.live(name) else {
            return Err(format!("no live definition `{name}`"));
        };
        let version = live.version;
        let (_, lib) = self.userspace.load(name, version, &live.kind, &live.source);
        let result = lib.and_then(|lib| lib.call(input, self.cfg.call_timeout));
        self.record_use(name, version, result.as_ref().err().map(String::as_str), input);
        result
    }
rust/src/kernel/mod.rs:344-353

That is the whole hot-swap mechanism: keeping, reverting or rolling back only changes which version is live, and the next call_def picks it up.

Tools

The nine kernel tools are the same as in every flavor: bash, read_file, write_file, list_defs, show_def, propose_def, rollback_def, remember and recall. A few Rust-specific details:

  • bash runs bash -c in its own process group with stdin closed and stdout and stderr merged into one pipe. The timeout defaults to 60 s and is clamped to 1–3600 s. On timeout the whole process group is killed with kill -9, so background children die too. After the command exits, the kernel waits at most 2 seconds for the pipe to close. Output is truncated to 20 KB.
  • A nonzero exit is a tool error. That matters for the success rule above:
    match status {
        Some(st) if st.success() => Ok(format!("{out}\n[exit code: 0]")),
        Some(st) => Err(format!("{out}\n[exit code: {}]", st.code().map_or("signal".into(), |c| c.to_string()))),
        None => Err(format!("{out}\n[timed out after {timeout}s]")),
    }
rust/src/kernel/tools.rs:113-117
  • read_file truncates at 50 KB. write_file refuses paths under the state directory, the whole kernel source rust/src, and base-prompt.md. Paths are normalized and their existing prefix resolved through symlinks before the check, so .. tricks and symlinked parents do not slip past.
  • list_defs shows soak progress as "(k/N clean uses)".
  • remember ignores a lesson whose trimmed, lowercased text is already stored. recall matches words of three or more characters across active lessons and verdicts.

The propose_def tool description tells the model it may use "std and serde_json only" (tools.rs:28). That is a hard limit: the generated Cargo.toml has no other dependencies, and the agent cannot edit it.

The gate: validate, trial, soak, keep or revert

The gate is where the Rust compiler earns its place. validate runs two stages.

Shape checks need no compiler (mod.rs:208-244): a lowercase name of at most 48 characters that is not a kernel tool, a known kind that never changes between versions, non-empty source, an object input_schema for tools, and at least one test with an object input and a string expect. Notes skip everything after the source check.

Build and test come next. The proposed version is compiled into its own library and loaded, without touching the live registry, and each test is run with the same timeout. A test passes if the output contains the expected string:

If anything fails, the kernel journals def_rejected and returns "rejected: … The live version is unchanged." to the model, with the compiler or test output attached. If it passes, the version becomes a trial: it is live right away, but on probation. If another trial of the same name was still soaking, that one is reverted first with a verdict saying it was "superseded by vN before its soak finished".

The soak rules live in record_use, which runs after every call:

    fn record_use(&mut self, name: &str, version: u32, error: Option<&str>, input: &Value) {
        self.rec("def_use", json!({"name": name, "version": version, "ok": error.is_none(), "error": error}));
        let Some(def) = self.state.defs.get(name) else { return };
        let Some(live) = def.live_version().filter(|l| l.version == version && l.status == "trial") else { return };
        let desc = live.description.clone();
        if let Some(err) = error {
            let verdict = format!("def {name} v{version} ({desc:?}) reverted: {} on input {}", first_line(err, 200), compact(input, 200));
            let restored = self.revert(name, version, err, verdict);
            let now = restored.map_or("definition removed".into(), |r| format!("live: v{r}"));
            trace(&format!("[gate] {name} v{version} reverted: {} ({now})", first_line(err, 100)));
        } else if def.soak_uses >= self.cfg.soak {
            let verdict = format!("def {name} v{version} ({desc:?}) kept after {} clean uses", def.soak_uses);
            self.rec("def_kept", json!({"name": name, "version": version, "verdict": verdict}));
            trace(&format!("[gate] {name} v{version} kept"));
        }
    }
rust/src/kernel/mod.rs:324-339

Any error during the trial reverts it to the last kept version (or removes the definition if there was none) and writes a verdict naming the error and the input that caused it. After three clean uses (the default soak: 3) the trial is kept. Errors from a version that is already kept do not revert it; spec test 4 checks that. Notes cannot be "called", so they soak over tasks instead: each finished task counts as one use of every trial note, and a failed task counts as an error.

rollback_def does not just flip a pointer. It copies an old version's record under a new version number and sends it through the whole gate again, compile and tests included.

The journal and replay

Every change of state is an event appended to <state>/journal.jsonl, one JSON object per line, stamped with type and ts. The kernel never changes state any other way. The live process appends an event and then feeds it to State::apply; startup reads the journal and feeds every event to the same function. The file header of state.rs says this is "so replay reproduces exactly the state the process had".

State::apply is a reducer: a function that takes the current state and one event and produces the next state. Here is the arm that counts soak uses:

A few properties fall out of this design:

  • On an empty journal, open writes a def_trial and a def_kept (marked "seed": true) for each seed. Seed keeps produce no verdict.
  • Verdicts are stored as a verdict field on def_kept and def_reverted events and rebuilt into State.verdicts on replay.
  • def_proposed and def_rejected are "history only": they change nothing in the state.
  • read_all skips lines it cannot parse, so a line torn by a crash mid-write does not stop startup.

Spec test 5 shows that compiled code is only a cache. It deletes <state>/build, reopens the kernel, asserts the replayed state equals the state before, and checks that the rebuilt library still answers and the soak counter continues from 1 to 2.

Lessons, reflection and refine

Lessons are the knowledge ring from chapter 2. After each task, every lesson that was in the prompt gets +1 if the task succeeded and −1 if it failed; a lesson that falls to −3 is retired (mod.rs:595-606).

Reflection is one extra model call after each task, with only the base prompt as system and no tools. The prompt carries a compact transcript of TASK, ASSISTANT, TOOL and OUTCOME lines, capped at 12,000 bytes, and asks for "only a JSON array of 0 to 3 short, reusable lessons". The parser is forgiving on purpose: it takes the text between the first [ and the last ], so a model that wraps the array in prose still counts:

Hooks and seeds

Two hooks let the agent change how its own prompt is built: compose_system (turn notes and lessons into the supplemental prompt) and select_lessons (pick lesson ids for a task). They are ordinary userspace definitions with fixed names, compiled and gated like any tool.

A fresh state directory starts with three kept seeds: the two hooks and one example tool. The example tool is the smallest possible userspace program:

// Seed tool `word_count`: {"text": string} -> number of whitespace-separated words.
pub fn run(input: &serde_json::Value) -> Result<String, String> {
    let text = input
        .get("text")
        .and_then(|v| v.as_str())
        .ok_or("missing string field `text`")?;
    Ok(text.split_whitespace().count().to_string())
}
rust/seed/word_count.rs:1-8

The seed compose_system writes a "## Notes" section (each note trimmed, as a paragraph) and a "## Lessons" section of "- " bullets. The seed select_lessons keeps words of four or more alphanumeric characters, sorts lessons by score (highest first, then by id), and returns up to 8 lessons that share a word with the task, or else the top 3.

The neat trick is that each seed hook file is compiled twice. It is embedded as text with include_str! and installed as userspace version 1, and it is also compiled straight into the kernel as a module:

// The seed hooks double as the kernel's fallbacks when a hook fails, so the
// default behavior exists in exactly one place.
#[path = "../../seed/compose_system.rs"]
mod seed_compose_system;
#[path = "../../seed/select_lessons.rs"]
mod seed_select_lessons;

So when the agent's own hook fails (it panics, times out or fails to load), the kernel calls the same seed code natively, and "the default behavior exists in exactly one place". Even a broken hook cannot leave the agent without a working prompt.

The provider

The model client is about 80 lines over ureq 2, a small blocking HTTP client, built with only its tls and json features (which bring in rustls and ring for TLS). No async runtime is needed because the agent does one thing at a time. The HTTP timeout is 600 seconds.

Credentials come from the environment. A non-empty ANTHROPIC_API_KEY is sent as x-api-key. Otherwise a non-empty CLAUDE_CODE_OAUTH_TOKEN is sent as authorization: Bearer … together with the header anthropic-beta: oauth-2025-04-20. With neither, every request fails with "no credentials".

OAuth tokens come with one extra rule from the shared spec: the first system block must be the Claude Code identity line. Empty system blocks are dropped:

fn system_blocks(texts: &[String], oauth: bool) -> Vec<Value> {
    let mut blocks = Vec::new();
    if oauth {
        blocks.push(json!({"type": "text", "text": CLAUDE_CODE_IDENTITY}));
    }
    blocks.extend(texts.iter().filter(|t| !t.trim().is_empty()).map(|t| json!({"type": "text", "text": t})));
    blocks
}

Status codes 429, 500, 502, 503, 504 and 529 are retried with sleeps of 2, 4 and 8 seconds, for four attempts in total; transport errors get three attempts with 2-second sleeps. Error bodies are cut to 1,000 characters. The model defaults to claude-sonnet-5-5, overridden by CMH_MODEL or --model.

Limitations

The wall is thin. Userspace is native machine code running inside the kernel's own process. catch_unwind catches panics and the timeout bounds hangs, but nothing stops code that crashes the process outright.
Failure in agent codeWhat happens
Panic (unwrap on None, index out of range, panic!)Caught in the wrapper, returned as an error, reverts a trial.
Infinite loop or very slow codeTimed out after 15 s and reverts a trial, but the thread is abandoned and keeps running.
Segfault, std::process::abort, std::process::exitKills the whole agent. ROADMAP: "a segfault or abort kills everything".
Stack overflow past the guard page, memory exhaustionNot caught (inferred); the process dies.
File or network access through stdAllowed. No source filter exists, and unsafe is not banned either (inferred).

Other limits, all recorded in ROADMAP.md or visible in the code:

  • Old libraries leak. Every superseded .so stays mapped until exit, by design.
  • bash can break every rule. write_file protects the kernel source and the journal, but bash can edit anything. Only its process-group kill on timeout limits it.
  • Only std and serde_json. Userspace cannot add crates, and one definition cannot use code from another; each crate is built alone.
  • Every proposal is a full cargo build. Fast once warm (0.1–0.3 s), but the first build in a fresh target directory compiles serde_json, and a cold, offline machine needs one online fetch.
  • No scratchpad. To try a snippet, the agent must propose a definition. ROADMAP suggests a Rust scratchpad that "compile[s] and run[s] in a throwaway worker".

The fix ROADMAP proposes for the first limit is to stop loading native code in-process: "Rust can compile userspace to wasm32 and reuse the Forth host's Wasmtime wall instead of loading .so files." WebAssembly would turn a segfault into a trapped error and a runaway loop into a fuel limit, at the cost of a different build target. Chapter 8 describes that wall.

Aside: the compile-time idea (not built)

Not built. Nothing in this section exists in the repository. It describes an alternative design. Only the build.rs form is recorded, as a proposed experiment in ROADMAP.md; the proc-macro variant appears nowhere in the repository.

Hot-loading shared libraries is one way to get new Rust into a running agent. The other is to stop trying to change the running process at all, and instead build a new one. Rust already has machinery that runs code at compile time: a build.rs build script runs before a crate compiles and can generate source files, and a procedural macro (proc macro) is a Rust function the compiler calls while compiling, which reads code and emits more code. Either one could read the agent's journal and splice every kept definition directly into the kernel binary, as ordinary functions checked by the same compiler pass as the kernel.

ROADMAP.md lists the build.rs form as experiment 9, "Compile-time Rust generations": "Each kept change triggers a rebuild whose build.rs reads the journal; the core then execs into the new binary. Compare the cost and safety with in-process hot loading." A proc-macro version, which ROADMAP.md does not mention, would differ only in where the generated code is produced, inside the compiler rather than in a script before it.

The trade-offs follow from the design (these are inferences, not measurements):

  • Gains: no unsafe symbol lookup, no C ABI, no JSON round trip for each call, no leaked libraries, and definitions could call each other and use richer types. Because the journal already rebuilds all state on startup, an exec into the new binary would lose nothing but in-flight work.
  • Costs: each generation is a rebuild of the whole kernel crate, much slower than the 0.1–0.3 s cdylib builds. Trials would need a binary of their own or a way to switch back, since one binary holds one set of definitions.
  • Safety: unchanged inside a generation, because agent code is still native code in the same process. The gain is at the edges: a supervisor could keep the last good binary and fall back to it if a new generation crashes on start.

It stays on the list of things to try. The cdylib approach fits the shared spec better: one process keeps running and swaps definitions one at a time.

Key takeaways

  • Rust has no eval, so the Rust flavor runs cargo as a subprocess and loads each definition version as its own cdylib with libloading.
  • The agent writes only src/user.rs. A kernel-written wrapper fixes the C ABI, frees its own memory and turns panics into errors with catch_unwind.
  • The Rust compiler is part of the gate. Wrong types, wrong signatures and borrow errors reject a proposal, and the trimmed rustc output goes back to the model.
  • Libraries are named by a content hash, so the loader never confuses versions and identical code is built once. A shared target directory keeps warm builds to about 0.1–0.3 s.
  • Libraries are leaked on purpose and calls run on a worker thread with a 15 s timeout. Hangs are bounded but not stopped.
  • The journal plus one reducer, State::apply, is the source of truth. Build output is a cache that can be deleted.
  • Seed hooks are compiled into the kernel too, so a broken agent-written hook falls back to the same code.
  • The weak point is the wall: native code in-process means a segfault or abort kills the agent. Compiling userspace to WebAssembly is the proposed fix, and compile-time generations are an unbuilt alternative.
